# Detalles técnicos

> Antifaz está en desarrollo (v0.1). Esta página crece con cada issue.

## Ponerlo en marcha (desarrollo)

```bash
make install   # dependencias + hooks de pre-commit
make check     # lint + tipos + tests (también los de contrato) + gitleaks + zizmor
make contract  # solo los tests de contrato: SDK oficiales contra Antifaz, sin red
make audit     # vulnerabilidades conocidas en las dependencias (uv audit, experimental)
make licenses  # licencias de lo que se distribuye
make openapi   # regenera docs/openapi.json desde la app (un test comprueba que está al día)
make dev       # API en http://localhost:8000 (uvicorn --factory; necesita .env, ver abajo)
make e2e       # extremo a extremo con Docker: imagen real + init + Compose + proveedor falso
make panel-check  # el panel en Chromium, Firefox y WebKit (grupo panel; PANEL_BROWSERS=chromium)
make panel-captures  # 28 capturas del panel real en build/panel-captures/ (Chromium)
make up        # construye la imagen desde el clon y la arranca con Compose (necesita .env)
```

## Docker (issue 7, parte 7a)

La guía para instalarlo en una empresa, paso a paso (bash y PowerShell, clientes, Claude Code, apagarlo, tráfico que no pasa por la pasarela, actualizar, rotar claves y problemas frecuentes), está en [instalacion.md](instalacion.md) ([in English](install.md)). Esta sección explica cómo está hecho.

### Ponerlo en marcha desde cero

Desde la v0.2.0, sin clonar (issue 42, ver «Una sola orden en la imagen»):

```bash
curl -LO https://github.com/miquel-moreno/antifaz/releases/download/v0.2.0/docker-compose.yml
docker run --rm -it -v "$PWD:/work" -w /work --user "$(id -u):$(id -g)" --network none \
  ghcr.io/miquel-moreno/antifaz:0.2.0 init
docker compose up -d
```

A mano, desde un clon (es el camino de la 0.1.1 publicada; también vale con la 0.2.0):

```bash
git clone https://github.com/miquel-moreno/antifaz && cd antifaz
cp .env.example .env
# En .env: ANTIFAZ_API_KEY con un valor aleatorio (openssl rand -hex 32) y la clave de cada
# proveedor que uses; borra la línea del proveedor que no uses (sin clave, su ruta da 503).
# ANTIFAZ_ADMIN_TOKEN: otro valor aleatorio distinto de la clave, o borra la línea (panel
# apagado). La 0.1.1 la ignora; la 0.2.0 no arranca si sigue con el valor de ejemplo.
docker compose up -d                 # la imagen publicada; `make up` la construye desde el clon
curl http://127.0.0.1:8000/healthz   # {"status":"ok","version":"0.1.1"}
```

El flujo a mano con `docker compose up -d --build` se comprobó el 2026-10-01 desde un clon limpio (Docker 29.8, Compose 5.5); desde el issue 42 la construcción local va en `compose.build.yml` (`make up`). Con los valores de ejemplo (`change-me...`) Antifaz se niega a arrancar: es a propósito (ADR-0015). Como Compose usa `restart: unless-stopped`, el contenedor se reinicia una y otra vez, cada vez con más espera entre intentos, y `docker compose ps` lo muestra como `restarting`. El motivo está en `docker compose logs antifaz` (un mensaje sin ninguna clave); se arregla `.env` y se vuelve a lanzar `docker compose up -d`. En `.env` no uses `$` en los valores: Compose intentaría sustituirlo.

### Cómo está hecha la imagen

| Decisión | Por qué |
|---|---|
| Imagen final **distroless** (issue 54, [ADR-0019](adr/0019-imagen-distroless.md)): `gcr.io/distroless/cc-debian13:nonroot`, que solo trae glibc, las librerías de GCC (libgcc, libstdc++, libgomp), OpenSSL, zlib, zstd, certificados raíz, tzdata y poco más. Sin shell (`sh`, `bash`, `dash`, `busybox`), sin `apt` ni `dpkg`, sin coreutils ni curl | Menos superficie de ataque: quien consiga ejecutar código dentro no tiene shell ni gestor de paquetes. Y menos paquetes que vigilar: 14 paquetes de Debian en vez de 87 (SBOM de Syft del 2026-10-16) |
| Tres etapas: uv construye un virtualenv con `uv sync --frozen --no-dev --no-editable`; una etapa `python` recorta el CPython 3.12 de la imagen oficial; la final solo copia `python3.12`, `libpython3.12.so.1.0`, la biblioteca estándar y el virtualenv. **La etapa final no tiene ningún `RUN`** | En la imagen no hay uv, ni código fuente, ni herramientas de desarrollo, ni compiladores. Las versiones son exactamente las de `uv.lock`. El Python de distroless sería el de Debian (3.13), no el 3.12 que fija el proyecto: por eso se copia el CPython de la imagen oficial, construido para la misma glibc (Debian 13) |
| Imágenes base fijadas por digest: `python:3.12-slim-trixie` (3.12.15, `sha256:a6e34c59…edc11b1`, el mismo índice que `python:3.12-slim`, comprobado el 2026-10-16), `gcr.io/distroless/cc-debian13:nonroot` (`sha256:e792ab3d…f1c2`, resuelto el 2026-10-16) y `ghcr.io/astral-sh/uv:0.13.0` (`sha256:cdc60931…a168`, resuelto el 2026-10-16), con `docker buildx imagetools inspect` | Una etiqueta se puede mover a otra imagen; un digest no. Dependabot (ecosistema `docker`) propone las actualizaciones; con una etiqueta que no es una versión (`nonroot`) mantiene la etiqueta y renueva el digest. Las líneas `FROM` van escritas enteras (sin `ARG`) para que Dependabot las entienda. Un test comprueba que las dos de Python son iguales y que `trixie` y `debian13` nombran el mismo Debian; python y distroless llegan en PR separados, y si uno cambiara de Debian ese test falla |
| Fuera de la biblioteca estándar: pip, setuptools, wheel, `ensurepip`, IDLE, tkinter/turtle, los módulos de pruebas de CPython y los módulos compilados cuya librería de sistema no está en distroless: `_ctypes` (libffi), `_sqlite3`, `_lzma`, `_bz2`, `readline`, `_curses`/`_curses_panel`, `_dbm`, `_gdbm`, `_uuid`, `_crypt` y `_tkinter` (con los paquetes que solo los envuelven: `ctypes`, `sqlite3`, `curses`) | Ningún paquete instalado los necesita: `make e2e` importa **cada módulo de cada paquete del virtualenv** (dependencias incluidas) y de `antifaz`, y solo admite fallos por paquetes opcionales que no están instalados (trio, h2, gunicorn…) o por módulos solo de Windows (`click._winconsole`). Copiar esas librerías obligaría además a copiar su registro de dpkg para que los escáneres las vean. El extra `ner` sí necesitará `ctypes` (torch carga sus librerías con él): la futura etiqueta `-ner` lo volverá a traer |
| Cada librería compartida de la imagen pertenece a un paquete que los escáneres ven | En distroless no hay `/var/lib/dpkg/status`: cada paquete tiene su registro en `/var/lib/dpkg/status.d/<paquete>` (con su `.md5sums`), y así lo leen Syft y Grype. `make e2e` recorre la imagen y falla si un `.so` no está en un `.md5sums`, ni es parte de CPython (Syft lo identifica por el binario `python3.12` y `libpython3.12.so.1.0`), ni está en el `RECORD` de un paquete del virtualenv. La CI comprueba además que los escáneres siguen viendo los paquetes del sistema (`scripts/check_scan_sees.py`: la estructura bloquea, la CVE conocida solo avisa; ver «Escaneo de la imagen») |
| Sin el extra `ner` | torch y el modelo añaden más de 1 GB. Habrá una etiqueta aparte `-ner` (con `--extra ner` y el modelo montado de solo lectura) más adelante |
| Usuario fijo sin privilegios `10001:10001` (no el `65532` de distroless), sin entrada en `/etc/passwd`, sin home ni shell | Si alguien consigue ejecutar código dentro, no es root. El UID fijo, el mismo de antes, permite usarlo en `securityContext` de Kubernetes y no cambia los permisos de los volúmenes ni el `--user` documentado. Nada de la pasarela necesita la entrada de `/etc/passwd` |
| El virtualenv es de root y no se puede escribir; bytecode compilado al construir y `PYTHONDONTWRITEBYTECODE=1` | Nada se escribe en tiempo de ejecución: la imagen funciona con el sistema de archivos de solo lectura |
| `.dockerignore` como lista de permitidos (`pyproject.toml`, `uv.lock`, `README.md`, `LICENSE`, `NOTICE`, `src/`), más exclusiones explícitas (`.env*`, `models/`, `evals/`, `.git`, `.venv`, cachés) por si la lista crece por error | Un `.env`, un modelo, un dataset o un archivo nuevo no entran en la imagen por despiste. Ninguna clave va en la imagen: todas llegan como variables de entorno al arrancar |
| Sin pip, setuptools, wheel ni `ensurepip`: se borran en la etapa `python`, antes de copiar | La pasarela no instala nada al ejecutarse; un instalador es una herramienta más para un atacante y más paquetes que escanear. Como se borran antes de copiar a la imagen final, sus bytes ya no están en ninguna capa (`make e2e` comprueba que `python -m pip` falla) |
| Sin `apt-get upgrade` | En distroless no hay apt ni shell. Los parches de Debian llegan con un digest nuevo de la base, que propone Dependabot |
| `HEALTHCHECK` con `python -m antifaz.healthcheck` en forma exec (sin curl ni shell) | La imagen no lleva curl, wget ni shell (un `CMD-SHELL` no podría ejecutarse). El healthcheck pide `/healthz` en `127.0.0.1:8000` con una cabecera `Host` sacada de `ANTIFAZ_ALLOWED_HOSTS`, así lo acepta la comprobación de host sea cual sea la configuración. No usa nunca un proxy aunque haya `HTTP_PROXY`/`HTTPS_PROXY` en el entorno. Cada comprobación (cada 30 s) deja una línea `INFO` de la petición a `/healthz` en el log de Antifaz: es ruido esperado y no lleva datos |
| `ENTRYPOINT ["antifaz"]` y `CMD ["serve"]`; `antifaz serve` arranca uvicorn con `--factory antifaz.api.app:create_app`, `0.0.0.0:8000`, sin log de acceso, sin `X-Forwarded-*`, sin cabecera `Server` y 20 s de apagado limpio | La app se construye al arrancar, así una configuración insegura impide arrancar. Sin log de acceso de uvicorn (Antifaz tiene el suyo, sin datos). `X-Forwarded-*` se ignoran: ver "Proxy inverso". Hasta la 0.1.x (0.1.0 y 0.1.1) el `ENTRYPOINT` era el propio `uvicorn` con esos parámetros (ver «Una sola orden en la imagen») |

Tamaño medido el 2026-10-16 con `docker image inspect --format '{{.Size}}'` en Docker Desktop 29.8 (la misma medida que `make e2e`): **143,5 MB** la imagen distroless, frente a **249,1 MB** la imagen sobre `python:3.12-slim` construida desde `main` ese mismo día. Por capas: la base distroless, 42,9 MB; el virtualenv, 55,6 MB; la biblioteca estándar recortada, 16,6 MB; `libpython3.12.so.1.0`, 6,65 MB. `make e2e` lo vuelve a medir en cada ejecución y falla por encima de 160 MB (antes, 300 MB).

**Depurar sin shell**: `docker compose exec antifaz sh` ya no funciona. `antifaz doctor` y `antifaz verify` sí (`docker compose exec antifaz antifaz doctor`). Para mirar dentro, un contenedor temporal con herramientas pegado al de Antifaz: ver «Problemas frecuentes» en [instalacion.md](instalacion.md).

### Compose

`docker-compose.yml` arranca un único servicio `antifaz` con la **imagen publicada** `ghcr.io/miquel-moreno/antifaz:${ANTIFAZ_VERSION:-X.Y.Z}` (por defecto, la versión de `pyproject.toml`, que en `main` es la última publicada; un test lo comprueba). Para construirla desde el clon, `compose.build.yml` añade `build:` e `image: antifaz:local` encima (`make up`, `make e2e`). No hay `command:`: corre el `CMD` de la imagen.

- **Claves**: se leen de `.env` (`env_file`) al arrancar el contenedor; nunca están en la imagen ni en el archivo de Compose. `ANTIFAZ_ENV_FILE` permite usar otro archivo (lo usan los tests de extremo a extremo para no leer nunca tu `.env`).
- **Puerto**: solo en `127.0.0.1:${ANTIFAZ_PORT:-8000}`. Desde otra máquina no se llega; para eso, un proxy inverso con HTTPS (abajo).
- **Solo lectura**: `read_only: true` y un `tmpfs` en `/tmp` (16 MB, `noexec`, `nosuid`, `nodev`).
- **Sin privilegios**: `cap_drop: [ALL]` y `no-new-privileges`.
- **Límites**: 512 MB de memoria, 1 CPU y 128 procesos (con el NER activado hace falta más memoria: el modelo ocupa más de 1 GB por proceso).
- **Una sola fuente de configuración**: todo sale de `.env`; el archivo de Compose no tiene `environment:` que pueda pisar lo que pone allí el administrador.
- **Hosts**: `.env.example` trae `ANTIFAZ_ALLOWED_HOSTS=localhost,127.0.0.1,[::1],antifaz`. `antifaz` es el nombre del servicio, para que otros contenedores de la misma red de Compose lleguen en `http://antifaz:8000`.
- Healthcheck, reinicio `unless-stopped` (con una configuración rechazada, se reinicia en bucle con espera creciente: ver el motivo con `docker compose logs antifaz`), 25 s para apagarse limpio y logs rotados (3 × 10 MB).

### Una sola orden en la imagen (issue 42, ADR-0017)

La imagen tiene `ENTRYPOINT ["antifaz"]` y `CMD ["serve"]`. Sin argumentos sirve; con argumentos, la misma imagen ejecuta otra orden de la CLI:

```bash
# Escribir .env en la carpeta actual (desde la v0.2.0). En Windows, sin --user;
# en PowerShell, -v "${PWD}:/work".
docker run --rm -it -v "$PWD:/work" -w /work --user "$(id -u):$(id -g)" --network none \
  ghcr.io/miquel-moreno/antifaz:0.2.0 init

# Servir sin Compose, con el mismo endurecimiento que docker-compose.yml (vale con la 0.1.1)
docker run -d --name antifaz --env-file .env -p 127.0.0.1:8000:8000 \
  --read-only --tmpfs /tmp:size=16m,mode=1777,noexec,nosuid,nodev \
  --cap-drop ALL --security-opt no-new-privileges \
  --memory 512m --cpus 1 --pids-limit 128 --restart unless-stopped \
  ghcr.io/miquel-moreno/antifaz:0.1.1
```

| Decisión | Por qué |
|---|---|
| `antifaz serve` (`src/antifaz/cli/serve.py`) llama a `uvicorn.run` con los parámetros fijos del `ENTRYPOINT` anterior, más `workers=1`, y no acepta opciones | Un test (`tests/unit/test_cli_serve.py`) fija los parámetros y otro compara, valor a valor, lo que habría ejecutado la línea de órdenes de uvicorn con los argumentos antiguos: solo cambian `app_dir` (uvicorn añadía la carpeta actual a `sys.path`; ahora solo se importa el paquete instalado) `headers` (`[]` frente a `None`: ninguna cabecera extra en los dos casos) y `workers` (antes `None`, un proceso salvo que hubiera `WEB_CONCURRENCY`; ahora siempre 1) |
| `uvicorn.run` en vez de la línea de órdenes de uvicorn | La línea de órdenes leía variables `UVICORN_*` del entorno (por ejemplo `UVICORN_FORWARDED_ALLOW_IPS`), y el entorno sale de `.env`; `uvicorn.run` no las lee. La configuración de uvicorn todavía lee dos variables sin prefijo: `WEB_CONCURRENCY` solo si no se da `workers` (se da: 1) y `FORWARDED_ALLOW_IPS`, que se lee pero no tiene efecto porque las cabeceras de proxy están desactivadas. Así nada de `.env` cambia cómo se sirve. Lo comprueban dos tests (con `WEB_CONCURRENCY=4` y `FORWARDED_ALLOW_IPS=*`) |
| `docker-compose.yml` sin `command:` | Corre el `CMD` de la imagen, así el mismo archivo vale para la 0.1.x (cuyo `ENTRYPOINT` era uvicorn y no entiende `serve`) y para las siguientes |
| Versión por defecto en Compose = la de `pyproject.toml` | En `main` es la última publicada (la 0.2.0 todavía no existe en ghcr.io), y el commit de cada release sube las dos a la vez. Un test las ata. `ANTIFAZ_VERSION=X.Y.Z` elige otra |
| `init` en el contenedor con `--rm`, `--network none` y `--user` | `--rm`: la clave que imprime `init` queda en el log del contenedor, que desaparece con él. `--network none`: `init` no usa la red. `--user`: en Linux, el `.env` lo crea tu usuario y no el `10001` de la imagen (con `0600`, si no, no podrías leerlo). En Docker Desktop para Windows no hace falta |
| Las claves por **nombre** de variable (`-e NOMBRE` en docker, sin valor) | Con `docker run -e NOMBRE`, docker toma el valor de su propio entorno: la clave no aparece en los argumentos ni en `ps`. Así lo hace `make e2e` |

### Proxy inverso (HTTPS)

Antifaz habla HTTP sin cifrar: para usarlo desde otras máquinas, ponlo detrás de un proxy inverso con HTTPS (Caddy, nginx, Traefik) en la misma máquina o red privada, y no publiques el puerto en `0.0.0.0`.

- Añade a `ANTIFAZ_ALLOWED_HOSTS` el nombre que usan los clientes (por ejemplo `antifaz.empresa.internal`).
- uvicorn arranca con `--no-proxy-headers`: la pasarela no se fía de `X-Forwarded-For` ni `X-Forwarded-Proto` y no los usa (no construye URLs). La única excepción es el panel (ADR-0018, desde el PR 11b-2a): la puerta del panel usa la IP del cliente **solo** para el límite de intentos de login (ya en uso), y el esquema para exigir HTTPS fuera de `localhost` y elegir la cookie. Esas dos cabeceras solo cuentan si la conexión llega de una IP de `ANTIFAZ_TRUSTED_PROXIES` (vacía por defecto); de cualquier otra, se ignoran. uvicorn sigue igual. Ver [Puerta del panel: entrar](#puerta-del-panel-entrar-11b-2a).
- El proxy no debe guardar los cuerpos de las peticiones en sus logs: llevan los datos personales antes de enmascararse.

### Extremo a extremo: `make e2e`

**Requisito: Docker Engine 28 o posterior, con Compose v2 (la orden `docker compose`).** El aislamiento de red de abajo depende de esa versión.

No forma parte de `make check` (necesita Docker y tarda alrededor de un minuto). Hace esto:

1. Construye la imagen con `docker compose build` (`docker-compose.yml` + `compose.build.yml`, la imagen `antifaz:local`).
2. Arranca Compose con `tests/e2e/docker-compose.no-egress.yml` y `tests/e2e/docker-compose.e2e.yml` encima de esos dos: añade un **proveedor falso** (`tests/e2e/fake_upstream.py`, solo biblioteca estándar) que corre en la propia imagen de Antifaz (no se descarga ninguna otra), guarda los bytes que recibe y devuelve el texto que le llega.
3. Las claves son aleatorias y nuevas en cada ejecución, en un archivo temporal que se borra al final; tu `.env` no se lee nunca. Las URL de los proveedores apuntan al falso con `http://` dentro de la red de Compose: las URL base son configuración del administrador y Antifaz no les exige HTTPS.
4. Comprueba, con un DNI y un email sintéticos, que el proveedor solo ve marcadores y el cliente recibe sus valores (OpenAI Chat y Anthropic Messages, con y sin streaming, con los marcadores partidos entre eventos); que el proveedor recibe su clave y nunca la de Antifaz; que sin clave se responde 401; que el contenedor está `healthy`, corre como `10001`, no puede escribir fuera de `/tmp`, no tiene capacidades y su puerto declarado es de `127.0.0.1`; que la imagen no tiene `.env` (ni en `/app` ni en ningún sitio), ni pytest, ni shell, ni apt, ni curl, ni wget, ni pip; y que los logs no tienen el DNI, el email ni ninguna clave, tampoco cuando el DNI va en la query (`/v1/models?after_id=…`, 400) o en una ruta inventada (`/v1/<DNI>`, 404).
5. La instalación en un minuto (issue 42, `tests/e2e/test_image_cli.py`): que la imagen tiene `ENTRYPOINT ["antifaz"]` y `CMD ["serve"]`, que `--help` funciona y que `serve` no acepta opciones; ejecuta `init --non-interactive` dentro de la imagen como dice el README (`-v carpeta:/work -w /work`, `--user` en Linux y macOS, `--network none`, `--read-only`, `--cap-drop ALL`), con claves falsas pasadas por nombre (`-e NOMBRE`), en una carpeta temporal que se borra al final; comprueba que ninguna clave sale por pantalla, que el `.env` tiene las claves (y en POSIX es del usuario y `0600`) y que una segunda ejecución sin `--force` no lo toca; y con ese `.env` arranca Compose (otro proyecto, sin proveedor falso, en la red interna con el relé) y el `docker run` endurecido de una línea (con `--network none`), y los dos responden `/healthz`.

**Los tests nunca pueden llegar a un proveedor real** (sin salida a internet), porque un fallo aquí gastaría dinero y mandaría datos fuera. Hay varias capas:

- **Red interna.** La pasarela y el proveedor falso solo están en `e2e-internal` (`tests/e2e/docker-compose.no-egress.yml`), una red con `internal: true`: Docker no les da ninguna ruta hacia fuera, así que ni con una URL base equivocada sale una petición. Además lleva `com.docker.network.bridge.inhibit_ipv4` (Docker 28 o posterior): el host no tiene dirección en esa red, así que tampoco se llega a los servicios del propio host (un proxy escuchando en `0.0.0.0` sería una salida). Al declarar `networks:`, la pasarela no entra en la red por defecto de `docker-compose.yml`. El `ports:` de `docker-compose.yml` sigue declarado, pero Docker no lo enlaza en una red interna. El stack que arranca con el `.env` de `init` (que apunta a los proveedores reales) usa el mismo archivo, con otra subred.
- **Relé.** Docker no publica puertos desde una red interna y los tests hablan con la pasarela (y con `/_e2e/received` del falso) desde el host. Lo resuelve `tests/e2e/relay.py` (biblioteca estándar, en la misma imagen y con el mismo endurecimiento: `read_only`, `cap_drop: ALL`, `no-new-privileges`, memoria, `cpus: 0.5` y procesos limitados): está en la red interna y en una normal, publica solo en `127.0.0.1` y copia bytes de cada puerto a una **IP fija** dentro de la subred interna (la subred y las IP de la pasarela y del falso son fijas por stack; un destino fuera de la subred se rechaza al arrancar y no se resuelve ningún nombre al conectar). No abre nunca una conexión donde le pida el cliente, así que no es un proxy que la pasarela pueda usar para salir. Tiene límites: 5 s para conectar, 64 conexiones a la vez y cierre de las conexiones inactivas. Se eligió frente a meter el cliente de los tests dentro de la red (habría que llevar pytest y el repo a un contenedor) porque los tests siguen igual; solo cambia el puerto.
- **Canario** (`tests/e2e/test_no_egress.py` y el stack de `init`). Desde dentro de la pasarela y del falso intenta una conexión TCP (3 s, sin mandar ni un byte) a los proveedores por nombre, a sus IP **resueltas en el host** (así no depende de que falle el DNS dentro), a `1.1.1.1`, `8.8.8.8` y `2606:4700:4700::1111`, y al lado del host: la pasarela de cada red de Docker (la normal del relé y el `bridge` por defecto) en los puertos 80, 443, 3128 y 8080. Cada resultado se juzga con una lista de permitidos: `unreachable` (ENETUNREACH/EHOSTUNREACH) o `no-address` (el contenedor no tiene direcciones de esa familia), y `dns-failed` solo para nombres. Un `timeout` falla: sin ruta, el núcleo rechaza al instante, así que un timeout significa que un SYN salió del contenedor. Un `refused` también falla (alguien contestó), igual que un error desconocido o una línea que falte. Cada destino, con su resultado y su errno, sale al final de `make e2e`. También se comprueba que la red es interna, que no da dirección al host, que la pasarela y el falso solo están en ella y no publican puertos, y que el relé solo escucha en `127.0.0.1`.
- **Configuración efectiva.** Dentro de la pasarela que está corriendo, `Settings()` imprime solo booleanos (nunca valores): las dos URL base son `http`, a `fake-upstream`, puerto 9000. El test comprueba también que la sonda dice `False` con la URL de un proveedor real.
- **Guardia de la configuración.** Antes de arrancar Compose, `conftest.py` relee el archivo de entorno temporal y para la sesión (`pytest.exit`) si `ANTIFAZ_OPENAI_BASE_URL` o `ANTIFAZ_ANTHROPIC_BASE_URL` falta o no es exactamente `http://fake-upstream:9000…`: sin usuario, sin consulta ni fragmento, solo ASCII visible (`urlsplit` se come tabuladores y saltos de línea) y el puerto escrito `9000`. Es una función pura con tests unitarios (`tests/unit/test_e2e_egress.py`).
- **`docker run` sin red.** Todos los contenedores sueltos usan `--network none` (el archivo estático del panel y el `docker run` de una línea del README se comprueban desde dentro del contenedor). Un test unitario estático lee `tests/e2e/*.py` con listas de permitidos: solo opciones conocidas antes de la imagen (`-p`, `-P`, `--privileged` o cualquier opción nueva fallan), la única red es `none` (un `--network bridge` posterior falla), y `run`, `create` y `container run` cuentan; `compose … run`, `shell=True` o un texto con una orden `docker run` fallan siempre. El ayudante `docker()` aplica la misma comprobación a los argumentos reales antes de llamar a docker.

En Linux con Docker anterior a la 28, un puerto publicado en `127.0.0.1` (el del relé, por ejemplo) podía alcanzarse desde otra máquina de la misma red local enviando paquetes directamente a la IP del contenedor; Docker 28 lo corrigió y también es el que trae `inhibit_ipv4`, por eso es un requisito (ver arriba), y la CI imprime `docker version` y `docker compose version` antes de `make e2e`.

Lo que se comprueba dentro de la imagen se hace con su propio `python -c` (`tests/e2e/image_probes.py`), nunca con un shell ni con `id`, `ls`, `find` o `which`: así los tests valen igual con una base sin shell (distroless, issue 54), y un test unitario (`tests/unit/test_e2e_without_shell.py`) falla si vuelve a aparecer uno. Una guardia más (`tests/e2e/test_image_imports.py`) importa dentro de la imagen los módulos con código compilado (`ssl`, `zlib`, `hashlib`, `uvloop`, `httptools`, `pydantic_core`, `markupsafe._speedups`, `websockets.speedups`), `jinja2` y `antifaz.api.app`, y construye `create_app()` con claves de usar y tirar y el panel activo, sin red. `make e2e` lanza pytest con `-vv` (el `-q` de `addopts` anula un `-v`), así el log de la CI nombra cada test; un test unitario lo comprueba.

Desde la imagen distroless (issue 54, PR B2; `tests/e2e/test_image_distroless.py` y `test_image_imports.py`):

- `docker run --entrypoint sh|bash|dash|busybox IMAGEN -c true` falla con «executable file not found», y `shutil.which` no encuentra `sh`, `bash`, `dash`, `busybox`, `apt`, `apt-get`, `dpkg`, `curl`, `wget` ni `pip`;
- `/etc/debian_version` empieza por `13`, como la etapa de construcción (trixie);
- `/var/lib/dpkg/status.d` existe y lista `zlib1g`, `libssl3t64` y `libc6`, y ninguna librería compartida queda sin paquete que la declare (ver «Cómo está hecha la imagen»);
- los módulos quitados (`_ctypes`, `_sqlite3`, `_lzma`… y `ctypes`, `sqlite3`, `curses`, `tkinter`, `idlelib`, `ensurepip`, `pip`, los de pruebas) no existen, y cada módulo compilado que queda en `lib-dynload` importa;
- se importa **cada módulo de cada paquete del virtualenv** (desde `importlib.metadata`: `packages_distributions()` y el `RECORD` de cada uno, 953 módulos el 2026-10-16) y de `antifaz` con todos sus subpaquetes (`pkgutil.walk_packages`, también los del NER). Hacen falta al menos 900. Ningún módulo de `antifaz` ni ningún nombre de primer nivel puede fallar; los demás solo pueden fallar por un paquete opcional de la lista `EXPECTED_MISSING` (`tests/e2e/image_probes.py`, cada uno con su motivo: trio, h2, gunicorn…) o por ser solo de Windows, y un paquete de la lista que ya no falte también hace fallar el test, para que la lista siga siendo verdad;
- el contexto TLS por defecto confía en los certificados raíz (`SSL_CERT_FILE`, declarado en el Dockerfile) y nada busca el usuario en `/etc/passwd` al arrancar (el `10001` no tiene entrada);
- el NER: el extra `ner` (gliner, torch, transformers) no está en la imagen, así que el modelo real no se puede cargar en ella. Se comprueba que la maquinaria del NER funciona sin shell (el pool de procesos con `spawn`, tuberías y JSON, con el backend falso) y que con `ANTIFAZ_NER_ENABLED=true` y sin modelo `serve` se para con el mensaje fijo de ADR-0016 («ANTIFAZ_NER_MODEL_DIR is not set…» o «…does not match the model manifest: model file missing: gliner_config.json»), sin ningún `ImportError` y sin la clave en la salida.

Resultado el 2026-10-16: **41 de 41 tests en verde** (Windows 11, Docker Desktop 29.8). Imagen: 143,5 MB sin comprimir.

Los mismos puntos de la imagen y de Compose (digest, usuario, healthcheck, `.dockerignore`, solo lectura, puerto…) también se comprueban sin Docker en `tests/unit/test_container_files.py`, dentro de `make check`.

### CI de la imagen

Job `image` de `ci.yml` (solo `contents: read`): construye la imagen con `docker buildx build --load --tag antifaz:local .`, con el mismo contexto y etiqueta que `compose.build.yml` (un test lo comprueba), así `make e2e` la reutiliza (este job no publica nada: lo hace `release.yml`, ver «Publicación»), ejecuta `make e2e`, genera el SBOM en CycloneDX con Syft (`anchore/sbom-action`, se sube como artefacto y se guarda 30 días) y la escanea con Grype (`anchore/scan-action`, ver «Escaneo de la imagen»). Las acciones van fijadas por SHA y Syft (v1.51.1) y Grype (v0.118.0) por versión exacta. La procedencia y el SBOM adjuntos a la imagen los pone el workflow de publicación (ver «Publicación»).

### Escaneo de la imagen

Grype solo se ejecuta en la CI, no en `make e2e` ni en local. La política:

| Decisión | Por qué |
|---|---|
| La CI falla solo con vulnerabilidades **altas o críticas que tienen arreglo** (`only-fixed: true`) | Una vulnerabilidad que Debian no arregla («won't fix» o sin versión corregida) no se puede quitar desde el repo: con ella la CI estaría siempre en rojo y se dejaría de mirar. Las que tienen arreglo sí se pueden quitar, y esas paran el merge |
| Sin `apt-get upgrade` desde la imagen distroless (hasta el issue 54, la etapa final lo hacía) | En distroless no hay apt ni shell. Los parches de Debian solo llegan con un digest nuevo de `gcr.io/distroless/cc-debian13` (y de `python:3.12-slim-trixie` para CPython). Mientras tanto, lo que Debian ya ha arreglado y la base todavía no trae aparecería en el filtro (alta o crítica con arreglo) y pararía el merge hasta actualizar el digest |
| Dependabot (ecosistema `docker`) propone cada digest nuevo de las imágenes base | Las reconstrucciones de las bases traen los parches de Debian ya incluidos. Fuera de Docker Hub (gcr.io, ghcr.io) Dependabot no conoce la fecha de publicación, así que ahí no espera el `cooldown`. No hay entrada `docker-compose`: el único servicio usa la imagen de Antifaz, cuya versión sube con cada release (un test la ata a `pyproject.toml`) |
| El informe completo (todas las vulnerabilidades, con o sin arreglo) se genera en tabla y en JSON y se sube como artefacto `grype-report` en cada ejecución, también cuando la CI falla, y se guarda 30 días | El filtro de la CI no esconde nada: lo que no rompe la CI sigue a la vista |
| Antes del filtro, `scripts/check_scan_sees.py` (solo biblioteca estándar). **La estructura bloquea**: la CI falla si el informe JSON de Grype no ve Debian 13 (`distro`) o no casa ningún paquete `deb`, o si el SBOM no lista `libc6`, `libssl3t64` y `zlib1g` como paquetes de Debian (`pkg:deb/debian/…`) o no lista CPython 3.12.x. **La CVE solo avisa**: si falta CVE-2026-85091 en `zlib1g`, la CI sigue en verde con una línea `::warning::` | En distroless los paquetes de Debian solo se ven por sus registros de `/var/lib/dpkg/status.d`. Si se perdieran, los escáneres verían menos y el filtro pasaría por el motivo equivocado. CVE-2026-85091 solo da un aviso porque Debian puede arreglarla o reclasificarla (CPython enlaza libz de forma dinámica, así que hoy sigue en la imagen); cuando desaparezca, conviene elegir otra. La prueba negativa es `scripts/check_scan_negative.py` (a mano, con Docker; Syft v1.51.1, unos 29 MB de descarga, sin base de datos de vulnerabilidades): construye una copia de la imagen sin `/var/lib/dpkg` y comprueba que la parte del SBOM pasa en la imagen real y falla en la copia (el 2026-10-16: faltan `libc6`, `libssl3t64` y `zlib1g`). La parte de Grype necesita su base de datos y la cubre la CI |
| Las excepciones van en `.github/grype-gate.yaml` (solo la usa el filtro, no el informe). **Hoy no hay ninguna**: la de CVE-2026-82049 (Python 3.12.14, arreglo solo en 3.14) estuvo del 2026-10-01 al 2026-10-12 y se quitó porque Grype ya no la da para Python 3.12.15 (informe completo del PR #58) | Cada excepción lleva motivo y fecha y se revisa al cambiar la imagen base |

Estado real el 2026-10-01 (CI de la rama `feat/7a-docker`, Grype v0.118.0): después del `apt-get upgrade` el informe sigue listando **13 vulnerabilidades altas sin arreglo en paquetes de sistema de Debian** (unas 50 líneas, porque cada una afecta a varios paquetes: util-linux y su familia, libc, perl, ncurses, zlib, acl y las librerías de gcc) y **una en Python 3.12** que solo está arreglada en 3.14 (ya no aparece con Python 3.12.15, el 2026-10-12). Ninguna está en el código de Antifaz. La pasarela no ejecuta la mayoría de esas herramientas (mount, login, perl, ncurses…): están porque vienen con Debian.

Con la imagen distroless (2026-10-16, en local, Syft v1.51.1 y Grype v0.118.0 con la misma base de datos de ese día para las dos imágenes; contando cada CVE una vez): la imagen sobre `python:3.12-slim` tenía **87 paquetes de Debian, 14 CVE altas, 29 medias, 5 bajas y 26 despreciables** (166 líneas, ninguna alta o crítica con arreglo); la distroless tiene **14 paquetes de Debian, 5 CVE altas, 16 medias, 3 bajas y 8 despreciables** (38 líneas, ninguna alta o crítica con arreglo). Las 5 altas, todas sin arreglo en Debian: CVE-2026-85091 en `zlib1g` (sigue: CPython enlaza libz de forma dinámica y Debian no tiene versión corregida; solo se irá con un digest nuevo de distroless que la traiga), dos en `libc6` y dos en las librerías de GCC (`gcc-14-base`, `libgcc-s1`, `libgomp1`, `libstdc++6`). Las 7 con arreglo son de CPython 3.12.15 (6 medias y 1 despreciable) y solo se arreglan en 3.13 o posterior. La CI vuelve a medirlo en cada ejecución.

### Publicación (issue 7, parte 7c)

La imagen se publica en `ghcr.io/miquel-moreno/antifaz` con un workflow aparte, `.github/workflows/release.yml`, que **solo** arranca con un tag `vX.Y.Z`.

**El primer tag, solo cuando el repo sea público.** En GitHub Free las atestaciones de procedencia necesitan un repo público: con el repo privado la imagen se subiría y el paso de la atestación fallaría, y quedaría una release a medias (imagen publicada sin procedencia). Antes del primer tag, en la configuración del repo (lo hace Miquel):

- environment `release`: Miquel como revisor obligatorio (*required reviewers*), sin saltarse la protección como administrador (*allow administrators to bypass* desactivado) y con *prevent self-review* desactivado, porque hay un solo mantenedor y si no nadie podría aprobar;
- un *ruleset* de tags que limite quién puede crear tags `v*`.

Cómo va una release:

1. En `main`, con la CI en verde: la versión de `pyproject.toml` y la sección `## [X.Y.Z]` del `CHANGELOG.md` ya están puestas. **En el mismo commit, justo antes del tag**, se sube también la versión por defecto de `docker-compose.yml` (`${ANTIFAZ_VERSION:-X.Y.Z}`, un test la ata a `pyproject.toml`) y la versión de la vía manual del README (EN y ES).
2. El tag y la publicación necesitan el OK explícito de Miquel cada vez. Puede delegar en el agente el tag o la aprobación del environment release caso a caso, nunca como permiso permanente. (`git tag -a vX.Y.Z -m "vX.Y.Z" && git push origin vX.Y.Z`)
3. El job `publish-image` espera en el environment protegido `release`: solo lo pueden usar tags `v*` y, cuando el repo sea público, pide la aprobación manual de Miquel antes de recibir ningún permiso.
4. Comprueba que el commit del tag está en `main` (si no, falla), que el tag es exactamente `vX.Y.Z`, que coincide con `pyproject.toml` y que el `CHANGELOG.md` tiene su sección; si no, falla sin construir nada.
5. Construye la imagen sin caché y la sube como `:X.Y.Z` y `:X.Y`, con el SBOM y la procedencia completa (`provenance: mode=max`) adjuntos por buildx.
6. Firma una atestación de procedencia SLSA con la identidad OIDC del job (Sigstore) y la sube junto a la imagen.
7. Job `release-asset` (issue 42), después de `publish-image` (`needs`) y sin environment propio: solo arranca si `publish-image`, que ya esperó la aprobación en `release`, terminó bien, así que cada release se aprueba **una vez**. No tiene secretos, solo `contents: write`: genera el `docker-compose.yml` de la release con `python3 -m scripts.release_compose` (solo biblioteca estándar y sin token: copia el del repo y cambia solo la línea `image:` a `ghcr.io/miquel-moreno/antifaz:X.Y.Z@sha256:…`, con el digest que sale del paso de construcción; falla si la versión o el digest no tienen la forma esperada) y lo sube a la GitHub Release del tag con `gh release upload --clobber`. Si Miquel todavía no ha creado la release (`gh release view` responde exactamente `release not found`), crea un **borrador** (`--draft --prerelease --verify-tag`, nunca un tag nuevo): Miquel escribe las notas (la sección del CHANGELOG) y lo publica. Cualquier otro error al leer la release (red, token, límite de peticiones) hace fallar el job en vez de crear otra. El borrador sale marcado como *pre-release* (Antifaz es beta); cuando se publique una versión que no lo sea, hay que desmarcarlo al publicarlo.

**Parche desde un tag antiguo** (así salió la 0.1.1): la rama `release/0.1.1` sale del tag `v0.1.0`, lleva solo el cambio del parche y se fusiona en `main` con un **merge commit normal**, así el commit que lleva el tag queda en `main`. No se puede fusionar con *squash* ni con *rebase*: los dos crean commits nuevos, el commit del tag no llegaría a `main` y `release.yml` fallaría en `git merge-base --is-ancestor` con `origin/main` (paso 4). Ojo: un tag ejecuta el `release.yml` **de su propio commit**, no el de `main`. El de la 0.1.1 era el de la v0.1.0, que todavía no tenía el job `release-asset`: por eso la release 0.1.1 no tiene `docker-compose.yml` adjunto ni se creó un borrador, y Miquel creó la release a mano, igual que la de la 0.1.0.

Comprobar que una imagen salió de este repo y de este workflow:

```bash
gh attestation verify oci://ghcr.io/miquel-moreno/antifaz:0.1.1 \
  --repo miquel-moreno/antifaz \
  --signer-workflow miquel-moreno/antifaz/.github/workflows/release.yml
docker buildx imagetools inspect ghcr.io/miquel-moreno/antifaz:0.1.1 --format "{{ json .SBOM }}"
```

`--repo` y `--signer-workflow` exigen que la firma sea de este repo **y** de `release.yml`, no de cualquier workflow de la cuenta.

| Decisión | Por qué |
|---|---|
| Workflow de publicación separado de la CI y sin escáneres ni herramientas de terceros (solo acciones de GitHub y Docker, fijadas por SHA) | Es el único sitio con permiso para publicar. Un escáner comprometido (como trivy-action en marzo de 2026) no puede tocar la imagen publicada. Los escaneos (Grype, gitleaks, zizmor, CodeQL) ya pasaron en `ci.yml` sobre el mismo commit |
| Solo `GITHUB_TOKEN` y OIDC, sin tokens guardados | El token dura lo que la ejecución y solo vale para este repo. No hay contraseña del registro que pueda filtrarse |
| Permisos de `publish-image`: `contents: read`, `packages: write`, `id-token: write`, `attestations: write` | Lo justo para leer el código, subir la imagen y firmar la procedencia. Nada de `contents: write` |
| `contents: write` solo en el job pequeño `release-asset`, sin más acciones que `actions/checkout` (sin credenciales guardadas) y el `gh` que trae el runner; el digest le llega como salida del otro job y entra en los scripts por `env`, nunca con `${{ }}` dentro del script | Adjuntar el `docker-compose.yml` necesita escribir en la release. Separado, el job con permisos para el registro y la firma no puede tocar el repo, y el que puede tocarlo no ejecuta nada de terceros. El script del repo se ejecuta sin el token; solo el paso de `gh` lo recibe. zizmor sin hallazgos |
| La página de la GitHub Release la escribe Miquel a mano (copiando la sección del CHANGELOG); el workflow solo crea un borrador si falta | El workflow no publica releases: un borrador no lo ve nadie hasta que Miquel lo publica |
| El `docker-compose.yml` de la release fija la imagen por digest | Quien lo descarga ejecuta exactamente la imagen construida, probada y atestada, aunque alguien moviera la etiqueta `X.Y.Z` después |
| Etiquetas `X.Y.Z` y `X.Y`, sin `latest` | Antifaz es beta (0.x): quien la usa elige versión a propósito y una versión nueva no le llega sin querer. Ojo: `0.1` se mueve con cada `0.1.x` (recibe los parches); `0.1.0` no cambia nunca |
| Solo se publica un commit que ya está en `main` (`git merge-base --is-ancestor`) | Un tag puesto en una rama sin revisar no llega a la imagen |
| Anotaciones OCI en el manifiesto y en el índice (`DOCKER_METADATA_ANNOTATIONS_LEVELS: manifest,index`) | Con el SBOM y la procedencia, buildx crea un índice; así ghcr.io enlaza ambos con el repo |
| Solo `linux/amd64` | Es lo único probado (CI y `make e2e`). `arm64` se añadirá cuando tenga pruebas |
| Sin caché de construcción | Nada de una ejecución anterior (ni de un PR) puede acabar en la imagen publicada |
| Sin registro de almacenamiento (`create-storage-record: false`) en la atestación | Pediría otro permiso y no cambia la verificación con `gh attestation verify` |
| Una release cada vez y nunca se cancela a medias (`concurrency` sin cancelación) | Evita dos publicaciones pisándose las etiquetas |
| PyPI, en la v0.2 (trusted publishing con OIDC, en este mismo workflow) | En la v0.1 se distribuye solo la imagen. La firma con cosign y el Scorecard llegan en la v1.0 |

## Arquitectura

Una pieza por responsabilidad, cada una en su paquete de `src/antifaz/`:

| Pieza | Paquete | Hace |
|---|---|---|
| Puerta | `api/` | Endpoints, auth, límites, `request_id`; errores que nunca repiten el cuerpo recibido |
| Detector | `detect/` | Validadores con dígito de control, patrones, NER, diccionarios |
| Política | `policy/` | Qué hacer con cada tipo de dato: `mask`, `surrogate`, `block`, `allow`, `route_local` |
| Tabla de marcadores | `vault/` | Valor ↔ marcador, solo durante la petición |
| Enmascarador | `mask/` | Cambia los valores por marcadores |
| Guardia de salida | `guard/` | Segunda comprobación sobre los bytes finales; si encuentra algo, bloquea |
| Enrutador | `providers/` | OpenAI, Anthropic, Ollama; destinos fijos |
| Restaurador | `restore/` | Vuelve a poner los valores, también en streaming |
| Evidencias | `audit/` | Registro encadenado sin datos personales (v0.2) |

El docstring de cada paquete dice qué hace y qué tiene prohibido. Las decisiones (aceptadas) están en [`docs/adr/`](adr/README.md) y las amenazas en [`docs/security/threat-model.md`](security/threat-model.md).

## Detector: identificadores con dígito de control (issue 2, PR 2a)

`antifaz.detect.scan(text)` devuelve la lista de spans `(start, end, type, layer, confidence)`: dónde hay un dato y de qué tipo, **nunca el valor** (ADR-0009).

| Tipo | Validación | Fuente |
|---|---|---|
| `ES_DNI` | 8 cifras + letra `TRWAGMYFPDXBNJZSQVHLCKE[n mod 23]` | Ministerio del Interior |
| `ES_NIE` | X/Y/Z → 0/1/2 + regla del DNI | Ministerio del Interior |
| `ES_NIF` (K/L/M) | 7 cifras + letra del DNI | RD 1065/2007 (sin algoritmo publicado; como python-stdnum) |
| `ES_CIF` | Luhn sobre las 7 cifras, como dígito o como letra `JABCDEFGHI` (ambas formas) | Orden EHA/451/2008 (sin algoritmo); ADR-0009 |
| `ES_NSS` | mod 97; si el número < 10^7, `(número + provincia·10^7) mod 97` | Sin fuente oficial de la TGSS; vectores en `tests/data/nss_vectors.md` |
| `ES_CCC` | Dos dígitos mod 11, pesos 1, 2, 4, 8, 5, 10, 9, 7, 3, 6 | AEB (2001) |
| `IBAN` | ISO 13616 mod 97 + estructura del país; los ES exigen además un CCC válido | Registro IBAN (vía python-stdnum) |
| `IT_CODICE_FISCALE`, `EU_VAT` | python-stdnum | — |

**Invariante 10:** en `tests/property/`, cada validador español se compara con python-stdnum en 5.000 casos generados (una parte con el control correcto calculado por stdnum, para probar también el lado "válido"). El NSS, que stdnum no tiene, se prueba con vectores documentados y con la propiedad "cambiar cualquier cifra lo invalida".

**En el texto:** cada patrón solo propone candidatos; un span se devuelve si su validador lo acepta. Los patrones siguen el ADR-0008 (repeticiones acotadas, cuantificadores posesivos, límites que impiden encontrar un DNI dentro de una tira más larga de cifras; ver ADR-0014 para los tipos que pueden tocar letras) y hay pruebas con textos maliciosos de al menos 50.000 caracteres. El IBAN se corta a la longitud de su país, sacada del registro IBAN, y se busca avanzando carácter a carácter tras un candidato falso, para que ningún candidato tape a otro IBAN. Se aceptan mayúsculas y minúsculas y los separadores habituales (espacio, punto, guion; barra en el NSS). La resolución de solapamientos es O(n log n): un texto con 4 veces más DNI cuesta unas 4 veces más, nunca 16 (ver «Cómo se prueba la velocidad»).

### Patrones con contexto (issue 2, PR 2b)

Para los datos sin dígito de control, `patterns/personal.py` busca la forma del dato y, en los más ambiguos, una palabra clave en los 40 caracteres anteriores (`patterns/context.py`, con límites de palabra reales: "hotel" no cuenta como "tel").

| Tipo | Cómo se detecta | Contexto | Confianza |
|---|---|---|---|
| `EMAIL` | Caracteres de RFC 5322 y letras Unicode (RFC 6531) en la parte local; dominio con TLD de 2+ letras o `xn--` | No | Alta |
| `IP` | IPv4 con octetos 0–255, no dentro de una serie más larga | No | Media |
| `PHONE` | España: `+34`/`0034`/`(+34)` o `34` pegado opcional, empieza por 6, 7, 8 o 9, 9 cifras en bloques con el mismo separador. Cada serie de cifras se parte en bloques y los teléfonos se montan bloque a bloque, así que un teléfono junto a otro número también se encuentra. Excluye números de empresa (800, 900, 901, 902, 905) y de tarificación adicional (803, 806, 807; CNMC) | Sube a alta con "tel", "teléfono", "móvil", "llamar", "WhatsApp" | Media / alta |
| `CREDIT_CARD` | 13–19 cifras (separador espacio, guion o punto), Luhn y prefijo conocido (Visa, Mastercard, Amex, Discover, JCB, Diners, UnionPay). No empieza en mitad de un número agrupado de 3+ cifras (evita leer parte de un teléfono como tarjeta) | No | Alta (validador) |
| `ES_PASSPORT` | 3 letras + 6 cifras (formato observado, sin norma citada) | Obligatorio ("pasaporte"…) | Media |
| `ES_PLATE` | 4 cifras + 3 consonantes sin vocales, Ñ ni Q (anexo XVIII del RD 2822/1998) | Obligatorio ("matrícula", "coche"…) | Media |
| `DATE_OF_BIRTH` | dd/mm/aaaa (también con - o . y año de 2 cifras), ISO aaaa-mm-dd, "12 de marzo de 1985", "12 marzo 1985", "1 de marzo del 1985"; fecha real | Obligatorio ("nacido", "F. nac."…) | Media |
| `ADDRESS` | Tipo de vía (castellano, catalán y gallego, con abreviaturas) + nombre + número (`nº`, `n.º`, `s/n`) + piso/puerta + CP 01000–52999 opcionales. Con tipos inequívocos (C/, Calle, Carrer, Avda…) el nombre puede ir en minúsculas; con tipos que también son palabras comunes (Camino, Ronda, Paseo, "C.") debe empezar por mayúscula | No | Media; alta con CP |
| `PT_NIF`, `FR_NIR`, `DE_IDNR` | Solo cifras, validados con python-stdnum | Obligatorio, del propio país | Alta (validador) |

Los identificadores de la UE que son solo cifras necesitan contexto porque, sin él, un NIF portugués de 9 cifras es indistinguible de un teléfono español.

**Solapamientos (ADR-0010):** si una detección contiene por completo a otra, gana la que contiene; así un email con un DNI dentro se enmascara entero, no solo el DNI.

### Normalización previa y formatos raros (ADR-0014, red team ronda 1)

Antes de buscar, `detect/normalize.py` crea una vista normalizada del texto con un mapa de posiciones; el texto original no se toca:

- Se quitan los caracteres de formato invisibles (categoría Unicode Cf: espacio de ancho cero, ZWNJ/ZWJ, guion blando, BOM, word joiner, marcas de dirección…), las marcas combinantes (Mn: acentos escritos aparte, selectores de variante) y los rellenos hangul.
- Los caracteres cuyo NFKC es **una** letra o cifra ASCII pasan a ese carácter (cifras y letras de ancho completo, letras matemáticas, superíndices). Los ordinales `º` y `ª` se quedan como están (los usan las direcciones).
- Tabulador, espacio duro (NBSP) y los demás espacios Unicode pasan a un espacio normal. Los saltos de línea se conservan.
- Homoglifos: las letras cirílicas `А В Е К М Н О Р С Т Х У З` y griegas `Α Β Ε Ζ Η Ι Κ Μ Ν Ο Ρ Τ Υ Χ` (y sus minúsculas) pasan a la latina que imitan (tabla `HOMOGLYPHS`; `З` y `Ζ` → `Z`).

Cada carácter se sustituye por uno o se elimina, así que las posiciones se devuelven al original con un mapa monótono (bisección sobre los caracteres eliminados): el marcador cubre los caracteres originales, incluidos los invisibles que haya **dentro** del valor, y `restore()` devuelve el texto exacto. Un texto ASCII sin tabuladores no se copia.

**Separadores:** DNI, NIE y NIF K/L/M aceptan un solo espacio, punto o guion entre grupos (`12 345 678 Z`, `12.345.678-Z`, `X 1 234 567 L`) y **un** salto de línea (`\n` o `\r\n`) en cualquier punto de las cifras o antes de la letra. El IBAN acepta un salto de línea entre grupos. Los recuentos siguen siendo exactos (8 o 7 cifras) y la letra o el mod 97 siguen siendo obligatorios; dos saltos de línea o dos espacios seguidos no valen.

**Límites relajados para los tipos con control fuerte:** DNI, NIE, NIF K/L/M e IBAN pueden ir pegados a letras (`DNI12345678Z`, `NIEX1234567L`, `ref abc12345678Zxyz`, `IBANES91…`), pero nunca a cifras: un DNI dentro de una tira más larga de cifras sigue sin ser un DNI. Tampoco se relaja dentro de una tira toda hexadecimal de 16 caracteres o más (hashes): con 20.000 valores aleatorios, 0 falsos DNI en SHA-1 y SHA-256 y 2 en UUID v4 (sus grupos tienen como mucho 12 caracteres; coste aceptado, se enmascara de más). Si hay separador antes de la letra de control, la letra no puede ir seguida de otra letra (en "12345678 casas" la "c" no es la letra de control). CIF, NSS, CCC, codice fiscale y NIF-IVA mantienen los límites estrictos (controles más débiles; "DNI és 16257107-V" sigue sin ser un CIF).

**Cuerpos muy anidados:** un JSON con más de 100 niveles de objetos o listas se bloquea (`NestingTooDeep`, 400 `antifaz_blocked`) antes de cualquier recorrido recursivo; la comprobación de adjuntos es iterativa. Una respuesta del proveedor igual de profunda da un 502 `bad_upstream_response` fijo. Un `arguments` con JSON demasiado profundo se trata como texto y se enmascara como tal.

**Limitaciones conocidas:**
- Cifras de otros sistemas de numeración (árabes, devanagari…) no se convierten: su NFKC no es ASCII. Solo se cubren los homoglifos de la tabla; otros alfabetos parecidos (armenio, cherokee…) no.
- Un valor partido entre dos cadenas JSON distintas, o codificado (base64, hexadecimal, URL, HTML, al revés, rot13), no se detecta (tests `xfail` del red team).
- Las direcciones se buscan con un patrón al estilo español (tipo de vía y nombre con mayúscula); las que no siguen ese formato quedan para el NER (issue 6). La ciudad no se incluye.
- IPv6 y pasaportes de otros países, fuera de alcance por ahora.
- El contexto solo se busca **antes** del valor y en 40 caracteres: no sirve una cabecera de CSV ni una palabra clave detrás ("AAB123456 (pasaporte)"). Propuesto como issue aparte.
- No se detectan: fechas con solo el año ("nacido en 1985"), matrículas provinciales antiguas (B-1234-XY), emails ofuscados ("juan (at) ejemplo.es"), teléfonos con doble espacio o con el prefijo entre paréntesis ("(93) 123 45 67"), direcciones en euskera con el tipo detrás ("Nagusia kalea 3") ni NIR corsos (2A/2B).
- Algunos números normales se detectan como teléfono o IP con confianza media ("700000000 unidades", "versión 1.2.3.4"): la política decide qué hacer con la confianza media.
- Controles débiles implican falsos positivos: NSS 1/97, CCC 1/121, Luhn 1/10. Es un fallo seguro (se enmascara de más).
- "CCC" aquí es la cuenta bancaria, no el código de cuenta de cotización de la Seguridad Social.
- Faker genera NSS con otra fórmula cuando el número empieza por 0: no sirve de referencia (se tendrá en cuenta en el benchmark).

## Librería: `mask()` y `restore()` (issue 4, PR 4a)

```python
from antifaz import mask, restore

result = mask(["Mi DNI es 12345678Z", "¿y el 12345678Z?"])  # también acepta un solo str
result.texts  # ("Mi DNI es [[ES_DNI_1]]", "¿y el [[ES_DNI_1]]?")
result.hidden  # (EntityType.ES_DNI,)
restore(respuesta_del_modelo, result.vault)
```

- Marcadores `[[TIPO_N]]`, numerados por tipo y por primera aparición en todos los textos; el mismo par (tipo, texto exacto) recibe siempre el mismo marcador ([ADR-0012](adr/0012-escape-and-same-value.md), propuesta).
- Los `[[` que ya escribe el usuario se escapan con un `!` detrás; `restore()` lo quita en una sola pasada y solo restaura marcadores de **esta** petición. Hypothesis comprueba `restore(mask(x)) == x`.
- Política por defecto (`DEFAULT_POLICY`, versión `builtin-1`): enmascara todos los tipos salvo el CIF de empresa.
- Si el detector falla o devuelve spans mal formados: `DetectorFailed`, con un mensaje fijo sin el texto. Nunca sale texto en claro.
- `Vault` no se puede imprimir (solo `Vault(entries=N)`), recorrer, serializar ni copiar. Protege contra fugas **accidentales** (logs, `repr`, pickle), no contra código del mismo proceso que lea sus atributos privados.
- Cada respuesta se restaura solo con la tabla de **su** petición: todas numeran desde 1, así que con la tabla de otra petición `[[ES_DNI_1]]` daría el DNI de otra persona. La pasarela lo garantiza en el issue 5.
- El restaurador solo reconoce marcadores en ASCII: parecidos como `[[ıp_1]]` se dejan tal cual.

## Guardia de salida y CLI (issue 4, PR 4b)

```python
from antifaz.guard import check

check(cuerpo_final_en_bytes, result.vault)  # lanza EgressBlocked si ve un valor oculto
```

- Si el cuerpo es JSON, revisa cada cadena, clave y número decodificados (así ve los escapes Unicode de JSON: una barra invertida seguida de `u0031` es el dígito 1); si no lo es, el texto crudo. Bytes que no son UTF-8 válido, o un JSON demasiado profundo para revisarlo: bloquea.
- Normaliza igual el valor y el texto: NFKC (cifras de ancho completo), sin caracteres de formato Cf (espacio de ancho cero, guion blando), sin acentos (NFD sin marcas Mn, así `İbrahim` = `ibrahim`), `casefold()` y espacios seguidos reducidos a uno.
- Valores con 6 o más letras y cifras: se comparan quitando **todo** lo que no es letra ni cifra y **sin límites de palabra**, así que `DNI12345678Z`, `X12345678ZY`, `12.345.678-Z` o `xana@example.com` bloquean.
- Valores más cortos: con límites alfanuméricos (ni letra ni cifra justo antes o después), para que "Ana" no salte en "semana".
- Se normaliza cada texto una sola vez: 1 MB de JSON con 200 valores ocultos se revisa en unos 0,04 s si es ASCII y unos 0,35 s con acentos (test con límite de 2 s).
- **Un falso positivo bloquea**: la guardia falla cerrada a propósito. No tiene opción para desactivarla.
- `EgressBlocked` lleva un mensaje fijo, sin valores y sin `__context__`.

Limitaciones de la guardia (es una **segunda capa**, no un DLP completo):

- No decodifica otras codificaciones: base64, URL (`%31`), entidades HTML, hexadecimal ni el valor escrito al revés.
- No ve un valor partido entre dos cadenas JSON distintas.
- Solo busca el valor tal como se detectó: un DNI copiado sin la letra, o un teléfono oculto con prefijo (`0034612345678`) que luego aparece sin él, pueden pasar. Al revés sí se detecta: el teléfono oculto sin prefijo bloquea aunque aparezca con `0034` pegado.
- Los falsos positivos bloquean la petición, por diseño.
- Invariante 2 (`tests/property/test_egress_invariant.py`): **sin llamar a la guardia**, un proveedor falso que guarda los bytes no recibe ningún valor oculto, ni tal cual, ni normalizado ni compactado, con `ensure_ascii` activado y desactivado.

CLI (`uv run antifaz ...`):

```bash
antifaz scan fichero.txt   # una línea por detección: TIPO inicio fin (nunca el valor)
antifaz mask fichero.txt   # el texto con marcadores (nunca la tabla)
antifaz mask -             # lee de stdin
antifaz verify             # planta datos falsos con tu configuración (ver "antifaz verify")
antifaz init               # escribe un .env con una clave nueva (ver "antifaz init")
antifaz doctor             # revisa la configuración, la pasarela y, si se pide, las claves (ver "antifaz doctor")
```

Si no puede leer el fichero como UTF-8 o el detector falla: mensaje genérico en stderr y código 2, sin repetir el contenido.

## Proxy compatible con OpenAI Chat (issue 5, PR 5a)

Configura `.env` a partir de `.env.example`: `ANTIFAZ_API_KEY` (la clave que usan tus clientes), `ANTIFAZ_OPENAI_API_KEY` y, si quieres otro servidor compatible, `ANTIFAZ_OPENAI_BASE_URL`. Todas las variables de Antifaz empiezan por `ANTIFAZ_`: así no se mezclan con las que usan Claude Code o los SDK en la misma terminal (si no, Antifaz podría llamarse a sí mismo y enviar su propia clave). Sin `ANTIFAZ_API_KEY` válida, Antifaz no arranca; sin la clave del proveedor, esta ruta responde 503 (ver [La puerta](#la-puerta-cerrada-por-defecto-issue-20)).

```bash
curl http://localhost:8000/v1/chat/completions   -H "Authorization: Bearer $ANTIFAZ_API_KEY" -H "Content-Type: application/json"   -d '{"model": "gpt-4o-mini", "messages": [{"role": "user", "content": "Mi DNI es 12345678Z"}]}'
```

Con el SDK de OpenAI basta con `base_url="http://localhost:8000/v1"` y `api_key=<ANTIFAZ_API_KEY>`.

Qué hace con cada petición ([ADR-0013](adr/0013-proxy.md), aceptada):

1. La puerta ya comprobó la clave de Antifaz, el `Origin` y el `Content-Type` (ver [La puerta](#la-puerta-cerrada-por-defecto-issue-20)). Esa clave **nunca** llega al proveedor; tampoco ninguna otra cabecera del cliente.
2. Lee el cuerpo con un tope (`ANTIFAZ_MAX_BODY_BYTES`, 4 MiB por defecto): más grande → 413; no es un objeto JSON en UTF-8 → 400.
3. Reúne **todas** las cadenas del cuerpo (mensajes, partes de texto, `name`, resultados de herramientas y cualquier campo nuevo) y llama a `mask()` una sola vez. Los `arguments` de las llamadas a herramientas se parsean como JSON y se enmascaran sus valores. Las claves de los objetos no se cambian: si alguna contiene un dato, la petición se bloquea.
4. Solo pasan partes de tipo `text`, `refusal` o `function`: imágenes, documentos, audio, ficheros, `file_id`, claves como `source` o `data`, o un texto con una URL `data:...;base64,` → 400 `antifaz_blocked`. Los números pasan por el detector: si uno es un dato (un teléfono escrito como número), se bloquea. `NaN`/`Infinity` o un `stream` que no sea booleano → 400.
5. Serializa una vez y la guardia de salida revisa **esos mismos bytes** justo antes de enviarlos.
6. Envía a `ANTIFAZ_OPENAI_BASE_URL` con `ANTIFAZ_OPENAI_API_KEY`. La URL nunca sale del cliente.
7. Restaura `content`, `refusal` y los `arguments` de las herramientas (parseando el JSON, así siguen siendo JSON válido aunque el dato tenga comillas). El resto de campos pasa sin tocar.

Errores:

| Caso | Respuesta |
|---|---|
| Sin clave, clave incorrecta, cabecera de clave repetida o `Authorization` y `x-api-key` en conflicto | 401 `unauthorized` |
| Cabecera `Origin` no permitida | 403 `origin_not_allowed` |
| `Content-Type` que no es `application/json` (UTF-8) | 415 `unsupported_media_type` |
| Claves repetidas en el JSON (también si solo cambian en mayúsculas y es una clave que Antifaz lee) | 400 `invalid_request` |
| `Host` que no está en `ANTIFAZ_ALLOWED_HOSTS` | 400 `Invalid host header` (texto) |
| La respuesta del proveedor repite una clave configurada o un trozo reconocible de una (también escapados en JSON; ver abajo) | 502 `bad_upstream_response` |
| El proveedor responde 401 o 403 (rechaza su propia clave) | El mismo estado con `upstream_auth_failed` y mensaje fijo, **nunca** su cuerpo (issue 76) |
| Dato en un sitio que no se puede enmascarar, adjunto, detector roto o guardia | 400 `antifaz_blocked`, mensaje fijo |
| `stream: true` | La respuesta llega en streaming, restaurada al vuelo (ver [Streaming](#streaming-issue-5-pr-5c)) |
| `stream_options` con algo que no sea `include_usage` o `include_obfuscation` a `true`/`false` | 400 `invalid_request` |
| El proveedor tarda más de `ANTIFAZ_UPSTREAM_TIMEOUT_SECONDS` | 504 `upstream_timeout` |
| No se puede conectar | 502 `upstream_unavailable` |
| El proveedor responde con una redirección (3xx) | 502 `upstream_redirect` (no se sigue) |
| El proveedor responde con otro error (4xx/5xx) en JSON | Su cuerpo **tal cual**, como `application/json`: solo vio texto enmascarado, así que puede mostrar marcadores `[[TIPO_N]]` |
| El proveedor responde con error que no es JSON (una página HTML) | 502 `bad_upstream_response` |
| Ruta que no existe / método que la ruta no tiene (con clave) | 404 `not_found` / 405 `method_not_allowed`, mensaje fijo |

**Trozos de una clave (invariante 13, issue 76).** Un proveedor que rechaza su clave puede citar parte de ella en el error (`sk-proj-****...abcd`). Por eso:

- Un **401 o 403** del proveedor se responde siempre con el mismo estado y un cuerpo fijo `upstream_auth_failed` ("el proveedor rechazó las credenciales de la pasarela o el acceso de la cuenta (HTTP 401/403): revisa la clave del proveedor y sus permisos"; un 403 puede ser un modelo o una región que la cuenta no puede usar, no solo una clave mala), en todas las rutas que llaman a un proveedor (chat, mensajes, `count_tokens`, `/v1/models`), con y sin streaming. Se cambian **todos** los 401/403, no solo los que citan la clave: solo la pasarela se autentica ante el proveedor (la clave del cliente nunca le llega), así que ese error siempre habla de la clave del operador, y su detalle es para el operador, no para el cliente. Se mantiene el estado (y no un 502) porque así el SDK lanza su error de autenticación o de permisos y **no reintenta**; el código distingue este caso del 401 de la propia puerta. El log solo guarda el estado (`antifaz.upstream`), nunca el cuerpo. «En directo» lo cuenta como `upstream_error`, sin nada más.
- Cualquier otra respuesta (error o éxito, entera o en streaming) que lleve un **trozo reconocible** de una clave configurada se descarta igual que si llevara la clave entera (502 fijo, o el evento de error fijo en streaming). Trozo reconocible (`api/key_fragments.py`): **10 caracteres seguidos** de la parte secreta de la clave (la clave sin su prefijo genérico: `sk-`, `sk-proj-`, `sk-ant-api03-`…, que es igual para todas las claves y nunca cuenta), o la forma enmascarada del proveedor, con **de 4 a 9** caracteres de la parte secreta a la vista en un extremo: los últimos justo detrás de una máscara (dos o más `*`, `•`, `·`, `.`, o un `…`) y sin nada que los continúe detrás (letra, dígito, `*` o `•`), como `sk-proj-****...abcd`; o los primeros seguidos de una máscara y sin letra, dígito ni carácter de máscara delante, como `sk-proj-AbCd****`. Así `**abcd**` (negrita de markdown) no cuenta. Diez caracteres son al menos 40 bits incluso en una clave hexadecimal (unos 59 en letras y dígitos), así que un texto normal no coincide por azar; los 4 últimos solos ("acaba en abcd") no cuentan, solo esa forma. Búsqueda de texto simple, sin expresiones regulares (una tira enorme de puntos no se atasca), y rápida porque se hace en cada evento del stream: los tramos de 10 están en un conjunto y el texto se sondea cada 5 caracteres con trozos de 5 de la parte secreta (cualquier tramo de 10 contiene entero uno de esos sondeos, así que no se escapa ninguno); solo un sondeo que acierta se confirma. Las formas enmascaradas buscan primero, con un `in`, los 4 primeros o últimos caracteres. Medido con cuatro claves realistas y 2.000 eventos: unos 0,16 ms por evento frente a 0,07 ms de la comprobación de la clave entera (antes del arreglo, 0,94 ms); un test lo vigila como proporción de tiempo de CPU, nunca con un límite de reloj.
- Un error del proveedor que no menciona la clave pasa como antes (`tests/redteam/test_key_fragments.py` lo comprueba).
- Las claves deben ser **aleatorias**. Con una clave elegida a mano y poco aleatoria (palabras, `mi-clave-de-empresa-2026`), un tramo de 10 caracteres puede aparecer en un texto normal y la respuesta acabaría en 502 por un falso positivo. Usa `openssl rand -hex 32` (lo que hace `antifaz init`) para la clave de Antifaz y el token del panel; las de los proveedores ya lo son. No se añade un aviso al arrancar: la clave ya tiene que tener 32 caracteres y 8 distintos, y una regla de "parece aleatoria" avisaría también de claves propias válidas.

Ningún log escribe cuerpos, cabeceras ni claves; `httpx` y `httpcore` quedan en `WARNING`. Un test (invariante 8) pasa un DNI centinela por respuestas, errores del proveedor, tiempos agotados y bloqueos de la guardia, con todos los loggers en `DEBUG`, y comprueba que no aparece ni en los logs ni en los cuerpos de error. Otro (invariante 2) quita la guardia **solo en el test** y comprueba que el proveedor falso no recibe ningún valor oculto, tampoco en argumentos ni resultados de herramientas.

## Proxy de Anthropic Messages (issue 5, PR 5b)

Configura `ANTIFAZ_API_KEY` y `ANTIFAZ_ANTHROPIC_API_KEY` en `.env` (y `ANTIFAZ_ANTHROPIC_BASE_URL` solo si usas otro servidor; va **sin** `/v1`). Sin la clave de Anthropic, estas rutas responden 503.

```bash
curl http://localhost:8000/v1/messages   -H "x-api-key: $ANTIFAZ_API_KEY" -H "anthropic-version: 2023-06-01" -H "Content-Type: application/json"   -d '{"model": "claude-sonnet-4-5", "max_tokens": 200, "messages": [{"role": "user", "content": "Mi DNI es 12345678Z"}]}'
```

Con el SDK de Anthropic: `base_url="http://localhost:8000"` y `api_key=<ANTIFAZ_API_KEY>`. **Claude Code**: `ANTHROPIC_BASE_URL=http://localhost:8000` y la clave de Antifaz en `ANTHROPIC_AUTH_TOKEN` (llega como `Bearer`, sin la pregunta de aprobación de `ANTHROPIC_API_KEY`); `antifaz setup claude-code` pone la URL (ver [su sección](#antifaz-setup-claude-code-issue-31)). Claude Code usa streaming, soportado desde la parte 5c (probado con el proveedor falso; la prueba documentada con Claude Code de verdad sigue pendiente). Antifaz no lee esas variables (solo las que empiezan por `ANTIFAZ_`), así que se puede arrancar en la misma terminal.

Rutas: `POST /v1/messages` y `POST /v1/messages/count_tokens`. Los pasos son los mismos que en OpenAI (clave, tope de tamaño, un solo `mask()`, una sola serialización revisada por la guardia, errores); el código de esos pasos es compartido (`api/proxy.py` y `providers/json_walk.py`). Lo propio de Anthropic:

1. **Clave**: en `x-api-key` (lo que envían Claude Code y el SDK) o en `Authorization: Bearer`, comprobada por la puerta como en todas las rutas. Al proveedor solo le llega `x-api-key` con `ANTIFAZ_ANTHROPIC_API_KEY`.
2. **Cabeceras**: solo se reenvían `anthropic-version` y `anthropic-beta`, y solo si su valor son letras, dígitos, `.`, `_`, `-` y comas (hasta 200 caracteres); si no → 400 `invalid_header`. Si el cliente no manda `anthropic-version`, Antifaz no se la inventa (el proveedor devolverá su error).
3. **Bloques permitidos** en `messages[].content`: `text`, `tool_use`, `tool_result`, `thinking` y `redacted_thinking`. En `system` y dentro de `tool_result.content`, solo `text`. Cualquier otro (`image`, `document`, `search_result`, `container_upload`, `server_tool_use`, resultados de herramientas del servidor, `citations` o uno nuevo) → 400 `antifaz_blocked`. `cache_control` no pasa por la lista. La `input` de `tool_use` puede tener cualquier `type` (son datos para la herramienta), pero las claves de adjunto (`source`, `data`, `file_id`…) y las URL `data:...;base64,` se bloquean también ahí. Ajustes con claves fijas: `thinking` solo `type` y `budget_tokens`; `tool_choice` solo `type`, `name` y `disable_parallel_tool_use`; otra clave → bloqueo. En `tools` no hay lista de tipos (hay herramientas del servidor como `web_search_20250305`), pero fuera de `input_schema` las claves de adjunto bloquean; dentro de `input_schema` no, porque una propiedad puede llamarse `data` o `file`, y solo se bloquea un objeto con `"type": "base64"`, que no es un tipo de JSON Schema (más las URL `data:` que se bloquean en todo el cuerpo). Todos sus textos se enmascaran. `metadata.user_id` y cualquier campo nuevo se enmascaran como texto.
4. **Razonamiento (invariante 9)**: los bloques `thinking` y `redacted_thinking` de los mensajes se copian **sin tocar**, con su `signature` o `data`: no se enmascaran ni se escapan (sus `[[` siguen igual). Vienen del modelo, que solo vio texto enmascarado, así que llevan marcadores, no datos. Aun así se pasan por el detector: si uno lleva un dato que hay que ocultar (alguien lo editó), la petición se bloquea, porque no se puede enmascarar sin romper la firma. La guardia sigue revisando todos los bytes. Solo se aceptan sus claves exactas (`thinking`: `type`, `thinking`, `signature`; `redacted_thinking`: `type`, `data`), todas de texto; otra clave → bloqueo. `signature` y `data` son opacos (firma y razonamiento cifrado) y no se pueden revisar: riesgo aceptado en el ADR-0013. Los marcadores que ya lleva el razonamiento (de un turno anterior) se **reservan**: un dato nuevo de esta petición no recibe ese número (si `[[ES_DNI_1]]` está en el razonamiento, el DNI nuevo es `[[ES_DNI_2]]`), y como los reservados no están en la tabla, la respuesta los deja tal cual en vez de poner un valor equivocado. Un bloque con forma de `thinking` dentro de la `input` de una herramienta no cuenta: se enmascara como cualquier dato.
5. **Respuesta**: se restauran los bloques `text` y los textos de `tool_use.input` (los valores, no las claves). `thinking`, `redacted_thinking`, las firmas y los bloques desconocidos pasan sin tocar.
6. **`count_tokens`**: se enmascara igual que `/v1/messages` y la respuesta del proveedor (solo números) se devuelve tal cual. `stream` se comprueba igual: no booleano → 400; `true` → 400 `streaming_not_supported`, por coherencia (`count_tokens` no tiene streaming).
7. `stream: true` → la respuesta llega en streaming (ver [Streaming](#streaming-issue-5-pr-5c)). El código de estado 2xx del proveedor se devuelve igual (en las dos rutas). Un texto con un sustituto suelto de UTF-16 (`"\ud800"`), que no se puede enviar en UTF-8, → 400 `invalid_request`.

"Sin tocar" quiere decir que las cadenas son idénticas: el proxy trabaja con el JSON parseado, así que el formato (espacios, escapes `é`) puede cambiar al volver a serializar, pero no el contenido ni la firma. Los tests comparan el bloque serializado dentro de los bytes enviados y de la respuesta.

## Streaming (issue 5, PR 5c)

Con `"stream": true` en `/v1/chat/completions` o en `/v1/messages`, la respuesta llega como eventos SSE (`text/event-stream`) y Antifaz pone los datos en su sitio **al vuelo**. La petición se trata igual que sin streaming: un solo `mask()`, y la guardia revisa los bytes exactos justo antes de enviarlos. Si el proveedor responde con error (429, 5xx…), se devuelve su cuerpo tal cual, como en 5a y 5b (después de comprobar que no repite una clave). `count_tokens` no tiene streaming: `stream: true` ahí → 400 `streaming_not_supported`.

Cómo se restaura ([ADR-0013](adr/0013-proxy.md)):

- **Texto**: cada trozo sale en cuanto llega, salvo el final que **podría** ser el principio de un marcador o de un escape (`[`, `[[`, `[[ES_D`, `[[ es_dni_1 `…), con el mismo patrón que `restore()`. Solo se retiene lo que todavía puede acabar siendo un marcador **de esta petición**: `[[ES_D` se retiene si esta petición emitió `[[ES_DNI_1]]`, pero un enlace wiki `[[Pagina_De_Ejemplo]]`, `[[EMAIL_1` sin emails en la petición o una ristra de letras salen al momento (`restore()` los dejaría igual). De un tramo de `[` seguidos solo se retienen los dos últimos. Tope de seguridad: 64 caracteres (`MAX_HOLDBACK`); solo se pasa con muchos espacios o tabuladores dentro de `[[ ... ]]`, y entonces se suelta el texto tal cual (sale como marcador, nunca como un valor equivocado) sin cortar el stream. Da igual cómo lleguen cortados los trozos: el texto final es el mismo que con `restore()` (invariante 3; tests de propiedades con cortes al azar, también en mitad de un carácter UTF-8, que se decodifica poco a poco).
- **OpenAI**: `delta.content` y `delta.refusal` de cada `choice`. Los `arguments` de `tool_calls` (y del antiguo `function_call`) se acumulan por (choice, índice de la herramienta) y se envían restaurados **en un solo delta**, en el chunk que cierra la choice (`finish_reason`). El primer delta de cada llamada sigue llevando `id`, `type` y `name`, con los `arguments` vacíos. `[DONE]` vacía lo que quede. `stream_options` solo admite `include_usage` e `include_obfuscation`, con `true` o `false`; otra cosa → 400 `invalid_request`.
- **Anthropic**: `text_delta` por índice de bloque. `input_json_delta` se acumula por bloque y sale restaurado como **un** `input_json_delta` justo antes de `content_block_stop` (siempre JSON válido, invariante 4). `thinking_delta` y `signature_delta` pasan **byte a byte** (invariante 9), igual que los bloques `thinking` y `redacted_thinking`. `ping`, `error`, `message_start` y `message_delta` pasan sin tocar; `message_stop` vacía lo que quede.
- **Eventos o campos desconocidos**: pasan sin tocar (ni se restauran ni se bloquean) y se cuentan en memoria (`app.state.stream_counters`, solo el número).
- Si el proveedor ignora `stream` y responde con JSON, se restaura como una respuesta normal.

El formato SSE lo lee un módulo propio y pequeño (`providers/sse.py`, sin dependencias): finales de línea CRLF, LF o CR (también partidos entre dos trozos), `data:` en varias líneas, comentarios y campos desconocidos. Un evento que no se cambia sale **tal cual llegó**, byte a byte.

**Fallos a mitad del stream** (el 200 ya se envió): sale el texto que ya es seguro (restaurado; un marcador a medias sale tal cual, porque es un marcador y no un dato), después **un** evento de error con el formato del proveedor y un mensaje fijo, y se cierra. Unos argumentos de herramienta a medias no se envían.

| Caso | `code` en OpenAI |
|---|---|
| Se agota el tiempo de lectura | `upstream_timeout` |
| Se corta la conexión | `upstream_unavailable` |
| SSE mal formado, UTF-8 inválido, una línea de más de 1 MiB o un evento de más de 4 MiB | `bad_upstream_response` |
| Más de 4 MiB de argumentos de herramientas acumulados | `stream_limit_exceeded` |
| Un evento repite una clave configurada | `bad_upstream_response` |
| El stream acaba sin `[DONE]` o sin `message_stop` | `upstream_stream_cut` |

En OpenAI el error es `data: {"error": {"message": ..., "type": "antifaz_error", "code": ...}}`; en Anthropic, `event: error` con `{"type": "error", "error": {"type": "api_error", "message": ...}}`. Ningún mensaje repite lo recibido; el log solo guarda el `code`.

**Claves (invariante 13).** Se revisa lo que llega del proveedor y, sobre todo, **lo que Antifaz envía** después de restaurar (unos argumentos con la clave escrita como `\u0063...` quedarían en claro al parsearlos y volver a serializarlos). Cada evento se revisa tal cual y decodificado hasta tres capas (JSON dentro de cadenas y escapes deshechos). Además, cada cadena de cada evento se une al final de la misma cadena en los eventos anteriores, con **un final por campo** (índice de choice o de bloque más el nombre del campo, conocido o no: `content`, `refusal`, `reasoning_content`, `thinking`, `cited_text`…), así una clave partida entre dos deltas se detecta aunque lleguen otros campos o choices en medio. Lo mismo vale para los **trozos** de una clave (10 caracteres seguidos de su parte secreta, o `****...abcd`; issue 76, ver arriba). Si la cabecera `Content-Type` del proveedor ya lleva una clave → 502 antes de empezar. Sin streaming se hace lo mismo con la respuesta ya restaurada (`tool_calls[].function.arguments`, `tool_use.input`): 502 `bad_upstream_response` fijo.

**Cierre.** Si el cliente se va a mitad, la respuesta cierra la conexión con el proveedor aunque esté esperando datos (`RelayResponse`; hay un test con una desconexión ASGI de verdad).

Tests: `tests/unit/test_stream_restore.py`, `test_sse.py`, `test_stream_transformers.py`; propiedades en `tests/property/test_stream_restore_property.py`, `test_sse_property.py` y `test_stream_protocol_property.py`; ataques en `tests/redteam/test_streaming.py` (429 y 5xx, proveedor lento, cortes en mitad de un marcador, UTF-8 partido o inválido, marcadores de otra petición, razonamiento, eventos desconocidos, claves y desconexión del cliente).

Hay tests de que ese revisor sí detecta cada caso.
- Los SDK son dependencias **solo de desarrollo** (grupo `dev`, no se distribuyen); sus licencias están en [licencias.md](licencias.md).

## `antifaz verify` (issue 5, PR 5d, primera versión)

Para que quien instala Antifaz compruebe **con su configuración** que los datos no salen, sin gastar nada:

```bash
uv run antifaz verify
```

- Lee la configuración como el servidor (variables `ANTIFAZ_*` y `.env`) y comprueba primero que arrancaría (mismas reglas que `create_app`); si no, código 2 y el nombre de la variable, nunca su valor.
- **Nunca llama al proveedor.** Levanta la pasarela dentro del proceso (`httpx.ASGITransport`) con un proveedor falso (`httpx.MockTransport`) que guarda los bytes que recibe y responde con los marcadores que ha visto. Para la prueba cambia las URL y las claves de los proveedores por unas falsas (así da igual que falten o que sean reales) y acepta un `Host` más (`antifaz-verify.invalid`).
- Siembra seis tipos de dato sintéticos (DNI, NIE, IBAN, email, teléfono y tarjeta) en 16 peticiones (más 2 para las claves): en OpenAI, mensaje de sistema, de usuario, parte de contenido, argumentos de una herramienta y su resultado, con y sin streaming; en Anthropic, `system` (texto y bloques), mensaje de usuario, bloque de texto, `tool_use.input` y `tool_result`, con y sin streaming, y `count_tokens`.
- Falla (código 1) si un valor sembrado llega al proveedor falso (tal cual o con otros espacios y mayúsculas), si la clave de Antifaz llega al proveedor, si una respuesta trae alguna clave configurada (hay una petición por ruta en la que el proveedor falso devuelve las cabeceras que recibió), si la pasarela bloquea o da error en una petición que debía pasar (el enmascarador dejó un valor y la guardia lo paró), si un valor no vuelve en la respuesta, o si una petición no llega al proveedor falso exactamente una vez (`NO UPSTREAM`: la pasarela contestó sin preguntar y la prueba no demostraría nada). Las 2 peticiones de claves, además, tienen que acabar en 502.
- Si `ANTIFAZ_MAX_BODY_BYTES` es tan pequeño que algunas peticiones de prueba dan 413, sale con código 2 ("could not verify", súbelo y repite): no es un fallo de privacidad, porque esas peticiones no salieron.
- El informe solo dice **tipos y sitios** (`LEAK ES_DNI, IBAN reached the provider -- openai chat: tool result`), nunca valores ni claves. Si todo va bien, un `PASS` de cinco líneas.
- Usa la misma política que el servidor (hoy la de fábrica). Un tipo que la política deja pasar (`allow`) no se comprueba y aparece como nota.
- No usa la comprobación de claves de la propia pasarela (`api/proxy.py`) para decidir: tiene la suya, para ver lo que la pasarela se deje.
- Tests: `tests/unit/test_verify.py`, también con la pasarela saboteada (enmascarador ciego → `LEAK` y código 1; enmascarador que deja un valor → `BLOCKED`; comprobación de claves desactivada → `KEY`; clave de Antifaz reenviada, en las dos rutas → `LEAK`; respuesta sin restaurar → `RESTORE`; `count_tokens` contestado sin proveedor → `NO UPSTREAM`). En estos tests y en los de contrato, cualquier búsqueda de nombre o conexión de socket que no sea a la propia máquina falla.

Limitaciones de esta primera versión: los valores sembrados son fijos (los mismos que usan los tests), la política no se lee todavía de un fichero, y no revisa lo que se escribe en los logs (eso lo cubren los tests de las invariantes 8 y 13).

## `antifaz init` (issue 41)

Decisión en [ADR-0017](adr/0017-instalacion-y-secretos-en-la-cli.md) (aceptada). Escribe un `.env` listo para arrancar sin que ninguna clave pase por la línea de órdenes:

```bash
uv run antifaz init                       # pregunta las claves de los proveedores (ocultas)
uv run antifaz init --path /srv/antifaz   # en otra carpeta (por defecto, la actual)

# CI o scripts: nada de preguntas; las claves, por el NOMBRE de una variable o por stdin
OPENAI_FOR_ANTIFAZ=... uv run antifaz init --non-interactive --openai-key-env OPENAI_FOR_ANTIFAZ
uv run antifaz init --non-interactive --anthropic-key-stdin < clave.txt
uv run antifaz init --non-interactive --force --allowed-hosts antifaz.internal,localhost
```

- **Clave de Antifaz**: `secrets.token_hex(32)`, hecha en la máquina (se saca otra si no pasara la comprobación de arranque). Se muestra **una vez**, solo si la salida es un terminal, o con `--show-key`. Si no, se dice que está en `.env`.
- **Claves de proveedores**: con `getpass` (no se ven al escribir) o, con `--non-interactive`, de `--openai-key-env VAR` / `--anthropic-key-env VAR` o de `--openai-key-stdin` / `--anthropic-key-stdin` (como mucho una por stdin). Ninguna opción acepta una clave: `--*-key-env` solo acepta un nombre de variable válido, y si se le pasa algo que parece una clave lo rechaza sin repetirlo. Se quitan espacios, comillas, una marca BOM y un `Bearer ` delante. Por stdin, como mucho 4 KiB, y nunca desde un terminal (hay que usar una tubería, o el modo interactivo). Si `getpass` no puede ocultar lo que se escribe, `init` se para. Los mensajes no repiten el nombre de `--*-key-env` (hay claves con forma de nombre, como `gsk_…`) ni la ruta de `--path`. Error (nombrando la variable, nunca el valor) si la clave es la de ejemplo, no es ASCII imprimible o lleva `"`, `'`, `#`, `$`, `\` o espacios; solo un aviso si no empieza por `sk-` (OpenAI) o `sk-ant-` (Anthropic). Un proveedor sin clave no tiene línea (su ruta da 503). Las variables `ANTIFAZ_*_API_KEY` del entorno **no** se copian solas.
- **`.env` existente**: en interactivo hay que escribir `yes`; con `--non-interactive` hace falta `--force`; si no, código 2 y no cambia nada. Antes se guarda `.env.bak-AAAAMMDD-HHMMSS` (con `-1`, `-2`… si ya existe: una copia nunca pisa otra), creada con `O_EXCL` y `0600`. Si `.env` es un enlace o una carpeta, no se toca.
- **Escritura atómica**: temporal `0600` con `O_EXCL` en la misma carpeta → `fsync` → validación con `check_safe_to_start` leyendo **solo ese archivo** (las variables de entorno del proceso no cuentan) → copia de seguridad → `os.replace` (en Windows se reintenta si el archivo está bloqueado). Pase lo que pase (también Ctrl-C), se borra el temporal; el `.env` anterior queda igual, con un mensaje genérico (si la copia ya se había hecho, dice cómo se llama).
- **Formato**: `VAR=valor` sin comillas, sin comentarios detrás del valor y sin `$`, saltos de línea LF y sin BOM. Lo leen igual pydantic-settings y `docker --env-file` (un test lo compara). La plantilla va en el paquete (`src/antifaz/cli/env_template.py`) porque en la imagen no hay `.env.example`; un test comprueba que tienen las mismas variables en el mismo orden.
- **Sin terminal**: en modo interactivo, si stdin no es un terminal, código 2 y "usa `-it` o `--non-interactive`".
- **Sin red**: no habla con nadie (un test lo comprueba quitando los sockets).
- **Códigos de salida**: 0 escrito; 2 uso incorrecto, `.env` existente sin permiso o un valor malo (no se escribe nada); 1 no se pudo escribir o validar (el `.env` anterior sigue igual).
- **Dentro de Docker** (issue 42): con `-it` la clave se imprime y Docker la guarda en `docker logs` mientras exista el contenedor, así que usa siempre `--rm`. En Linux, añade `--user "$(id -u):$(id -g)"` para que el `.env` sea tuyo y no del usuario del contenedor.
- **Copias y rotación**: las copias `.env.bak-…` contienen las claves antiguas. Después de rotar una clave, borra las copias que la contienen.
- **Permisos en Windows**: `0600` no existe; el archivo hereda los permisos de la carpeta (en el perfil del usuario, solo él). No ejecutes `init` en una carpeta compartida.
- Tests: `tests/unit/test_cli_init.py` (claves canario que nunca salen por stdout, stderr ni logs, también en los errores; `getpass`; copias; fallo de `os.replace` y de validación; `0600` en POSIX; terminal y `--show-key`; Hypothesis para la clave generada). El job `cli-windows` de CI pasa los tests de la CLI en Windows.

## `antifaz doctor` (issue 43)

Parte de [ADR-0017](adr/0017-instalacion-y-secretos-en-la-cli.md): `init` no usa la red y comprobar que las claves funcionan es trabajo de `doctor`, solo si se pide.

```bash
docker compose exec antifaz antifaz doctor               # dentro del contenedor que ya corre
docker compose exec antifaz antifaz doctor --providers   # y además prueba las claves (gratis)
uv run antifaz doctor --path /srv/antifaz --url http://127.0.0.1:8000 --timeout 5
```

Tres comprobaciones, en orden:

1. **Configuración**: lee lo mismo que la pasarela (el `.env` de `--path`, por defecto la carpeta actual, y encima las variables `ANTIFAZ_*` del entorno, que ganan, como en pydantic-settings) y pasa `check_safe_to_start`. Si un valor no se puede leer, solo nombra la variable (el error de Pydantic repite el valor, así que no se muestra). Dice qué proveedores tienen clave (solo los nombres) y si el NER está activado. Ojo: con Compose la pasarela solo lee `.env`; si tu terminal tiene variables `ANTIFAZ_*`, `doctor` desde fuera puede ver otra configuración. Dentro del contenedor (`docker compose exec`) ve exactamente la de la pasarela. Si el `.env` no es UTF-8 (por ejemplo, guardado en cp1252 con una `ñ`) o no se puede abrir: "cannot read .env as UTF-8 text", sin traza (el error lleva bytes del archivo). Si `ANTIFAZ_OPENAI_BASE_URL` o `ANTIFAZ_ANTHROPIC_BASE_URL` llevan usuario o contraseña (`https://usuario:clave@host`), avisa nombrando la variable y con `--providers` no llama a ese proveedor.
2. **Pasarela**: `GET {url}/healthz`, que es pública: **no se envía ninguna clave**. Sin proxy (`trust_env=False`: se ignoran `HTTP(S)_PROXY` y `NO_PROXY`, la pasarela es local), sin seguir redirecciones, con tiempo máximo y leyendo como mucho 64 KiB. Pide `Accept-Encoding: identity` y rechaza cualquier otra `Content-Encoding` (fallo genérico): así el límite de 64 KiB es de bytes reales y no de bytes descomprimidos. Como `trust_env=False` también ignora `SSL_CERT_FILE` y `SSL_CERT_DIR`, con una `--url` `https://` firmada por una CA propia la comprobación falla aunque la pasarela esté bien; en ese caso, usa la URL local (`http://127.0.0.1:8000`) o `docker compose exec`. El `Host` es el de `--url` si está en `ANTIFAZ_ALLOWED_HOSTS`; si no, el primero de la lista que no es comodín (o el comodín con `healthcheck.` delante, como el healthcheck del contenedor). Si no hay configuración legible, el de `--url`. Muestra la versión solo si tiene forma de versión, y el estado del NER (`starting` es un aviso; `circuit_open`, `closed` o uno desconocido, fallo). Un 400 suele ser `ANTIFAZ_ALLOWED_HOSTS` distinto en la pasarela (no se ha reiniciado tras cambiar `.env`). Si no responde: "docker compose up -d".
3. **Proveedores**, solo con `--providers`: para cada proveedor con clave, `GET` de su lista de modelos directamente al proveedor (OpenAI `{base}/models` con `Authorization: Bearer`; Anthropic `{base}/v1/models` con `x-api-key` y `anthropic-version: 2023-06-01`). Listar modelos no cuesta nada. Sin redirecciones (una clave nunca sigue a un `Location`: un 3xx es error), con tiempo máximo y **sin leer nunca el cuerpo** de la respuesta (un proveedor puede repetir la clave en el error): solo cuenta el código. 200 bien; 401/403 clave rechazada; 3xx redirección no seguida; tiempo agotado; no se puede conectar; otro código. Una clave con formato imposible no se envía. Estas peticiones **sí** respetan `HTTP(S)_PROXY`, igual que el cliente de la propia pasarela (`providers/http.py`, httpx por defecto): así se prueba el mismo camino que usará la pasarela detrás de un proxy corporativo.

- **`--timeout` es un plazo total por petición** (conectar, cabeceras y cuerpo juntos), no por lectura como el de httpx: la petición va en un hilo aparte con plazo fijo (`time.monotonic()`), y el cuerpo de `/healthz` también mira el plazo mientras lee. Un servidor que manda un byte cada poco no retiene a `doctor`.
- **Nunca imprime** valores, claves, cuerpos, excepciones ni URL base (una URL puede llevar `usuario:contraseña`); `--url` con usuario, consulta o fragmento se rechaza sin repetirlo. Mensajes fijos que nombran variables. Mientras corre, los loggers `httpx` y `httpcore` (`QUIET_LOGGERS` de `antifaz/logging.py`) se quedan en WARNING, así que no registran la línea de cada petición aunque `doctor` se use como librería con logs en DEBUG; al acabar se dejan como estaban.
- **Salida**: texto plano con `✓`/`✗`; si la consola no puede escribirlos (cp1252 en Windows), `OK`/`FAIL`. Al final, los pasos siguientes: `antifaz verify`, `antifaz setup claude-code` (issue 31) y la documentación.
- **Códigos de salida**: 0 todo bien; 1 algo falla; 2 uso incorrecto (`--path` que no existe, `--url` mala, `--timeout` fuera de 0–120 s).
- Tests: `tests/unit/test_cli_doctor.py` (claves canario que nunca salen por stdout, stderr ni logs, también cuando el proveedor las repite en el cuerpo, en una cabecera o en la excepción; `MockTransport` para 200, 401, 403, 307, 500, tiempo agotado y error de conexión; `/healthz` caído, 503, 400, cuerpo raro o enorme; elección del `Host`; sin `--providers` no hay ninguna petición a proveedores; con servidores reales en 127.0.0.1, que `/healthz` no pasa por el proxy y los proveedores sí; plazo total con un servidor que gotea byte a byte en cabeceras y cuerpo; respuesta gzip rechazada; `.env` en cp1252; URL base con usuario; sin líneas de httpx en los logs; consola cp1252; códigos de salida). También en el job `cli-windows`. E2E en `tests/e2e/test_doctor.py`: desde el host contra el puerto publicado y con `docker compose exec ... doctor --providers` contra el proveedor falso, que comprueba que cada proveedor recibe su clave y nunca la de Antifaz.

## NER: la infraestructura (issue 6, PR 6a)

Decisión en [ADR-0016](adr/0016-ner-en-procesos-aparte.md) (propuesta). Esta parte trae todo lo que rodea al modelo de nombres **sin el modelo**: el modelo real (GLiNER), su descarga y su manifiesto llegan en 6b. Hasta entonces el NER está apagado y, si se enciende, Antifaz no arranca.

**Recorrido.** `mask()` pide al detector todos los textos de la petición de una vez (`Scanner.scan_many`). Para cada texto se construye la vista normalizada del ADR-0014; los patrones y el NER leen esa misma vista y sus posiciones vuelven al original con el mismo mapa:

1. **Caché** (`detect/ner/cache.py`): si el texto ya pasó por el NER con el mismo modelo, etiquetas, umbral y troceador, se usan sus spans. Clave BLAKE2b con una clave secreta aleatoria por proceso; guarda solo posiciones y tipos; LRU con `ANTIFAZ_NER_CACHE_ENTRIES` entradas y, además, como mucho 200.000 spans en total (unos pocos textos llenos de nombres no llenan la memoria).
2. **Ventanas** (`detect/ner/chunker.py`): 200 tokens que se solapan 50 (un token es una palabra de hasta 40 letras o cifras, o un signo). GLiNER lee como mucho 384 palabras y corta el resto sin avisar; con el solape, una entidad de menos de 50 tokens en la frontera se ve entera en alguna ventana.
3. **Pool de procesos** (`detect/ner/pool.py` y `worker.py`): procesos propios con `spawn`, que cargan el modelo una vez. Hablan JSON por un `Pipe` (nunca `pickle`) con tamaño máximo; el hijo escribe en el dispositivo nulo, sin logging, sin red (`HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`) y solo devuelve códigos de error fijos.
4. **Comprobación** (`detect/ner/engine.py`): una lista por ventana, `[inicio, fin, etiqueta, puntuación]` con enteros dentro de la ventana, una etiqueta pedida y una puntuación entre 0 y 1. Cualquier otra cosa → `DetectorFailed` → 400 `antifaz_blocked`.
5. **Solapamientos**: el NER es la capa con menos prioridad, y el perdedor de un solapamiento parcial se recorta en vez de descartarse (sus trozos sin letras ni cifras se tiran). Todo carácter alfanumérico que alguna capa detectó queda enmascarado.
6. **Propagación** (`mask/propagate.py`): cada valor que encontró el NER se enmascara en todos los textos de la petición, con la regla de la guardia (normalizado; 6 o más letras y cifras sin límites de palabra; más corto, con límites, y un vecino que se va a enmascarar cuenta como límite). Así la guardia no bloquea una petición porque el modelo vio un nombre en un mensaje y no en otro. Solo se propagan valores enteros (que empiezan y terminan en límite de palabra: no los trozos que quedan al recortar alrededor de un DNI) y de 3 o más letras y cifras; más de 200 valores distintos del NER en una petición la bloquean. La propagación normaliza carácter a carácter y la guardia la cadena entera: coinciden en letras, cifras, acentos, homoglifos y espacios (test de propiedad); en secuencias raras cuya forma NFKC depende del vecino, la guardia ve lo que la propagación no vio y bloquea (falla cerrada).

**Límites por petición.** `ANTIFAZ_NER_TIMEOUT_SECONDS` es el tiempo del NER para **toda la petición**, no por llamada: un único plazo (reloj monotónico) cubre esperar un proceso libre, esperar a uno que aún carga el modelo, todas las llamadas por lotes y recibir la respuesta **entera** (un vigilante mata el proceso al llegar el plazo, así que una respuesta que se queda a medias tampoco retiene la petición). Además, una petición de más de 1.024 ventanas (~1 MB de texto) se bloquea antes de llegar al modelo.

**Fallos.** Si el plazo se agota, el proceso se mata (`kill()`), se arranca otro y la petición se bloquea con 400. Lo mismo si el proceso muere, no carga el modelo o responde algo mal formado. Si el backend lanza una excepción, el proceso sigue vivo y la petición se bloquea. Un proceso nuevo que todavía carga no se mata: la petición se bloquea y la siguiente lo usa. Tras 3 fallos seguidos se abre el **cortacircuitos**: toda petición se bloquea al momento durante 1 s, 2 s, 4 s… (máximo 60 s) y luego se vuelve a probar; se cierra con la primera respuesta buena. El log solo dice qué pasó ("replaced", "circuit open"), nunca el texto, y `/healthz` añade `"ner": "ok" | "starting" | "circuit_open" | "closed"` cuando el NER está encendido. Al parar, los procesos se matan sin cerrar la tubería que otro hilo está leyendo. `ProcessPoolExecutor` no sirve: no mata un proceso colgado hasta Python 3.14.

**En la API**, `mask_request` corre en un hilo (`anyio.to_thread.run_sync`) con un limitador propio de 8 hilos (`MASK_THREADS`): ni los patrones ni la espera al NER bloquean el bucle de eventos ni ocupan los hilos compartidos de anyio. Arrancar y parar los procesos usa otro limitador aparte, así que una pasarela ocupada no retrasa su propia parada. Los procesos arrancan con la app (si el modelo no carga, la app no arranca) y se paran con ella.

**Manifiesto** (`detect/ner/manifest.json` y `manifest.py`): cada archivo del modelo con su tamaño y SHA-256. Antes de cargar se exige que el directorio tenga **exactamente** esos archivos (ni uno de menos, ni uno de más). Se recorre sin seguir enlaces y se rechaza cualquier enlace simbólico, unión de Windows (junction) u otro punto de reanálisis, y todo lo que no sea un archivo normal o una carpeta. La pasarela lo comprueba al arrancar y **cada proceso del pool lo vuelve a comprobar** (también el hash del propio manifiesto) justo antes de cargar el modelo, cada vez que arranca: un archivo cambiado después del arranque detiene ese proceso y la petición se bloquea. Queda un instante entre esa comprobación y la carga (TOCTOU); aprovecharlo exige poder escribir en la carpeta del modelo, que debe ser de solo lectura para el usuario de la pasarela. El hash del manifiesto entra en la clave de la caché. El de 6a no tiene archivos: rechaza cualquier directorio.

**Variables** (todas opcionales; el NER está apagado por defecto):

| Variable | Por defecto | Qué hace |
|---|---|---|
| `ANTIFAZ_NER_ENABLED` | `false` | Enciende el NER. Con `true`, si el modelo falta o no coincide con el manifiesto, o el backend no está instalado, Antifaz no arranca |
| `ANTIFAZ_NER_MODEL_DIR` | vacía | Carpeta del modelo descargado (comando de descarga en 6b) |
| `ANTIFAZ_NER_TIMEOUT_SECONDS` | `10` | Tiempo máximo del NER para toda la petición (todas sus ventanas, en lotes de 16) |
| `ANTIFAZ_NER_WORKERS` | `1` | Procesos del pool; cada uno ocupa la memoria de un modelo |
| `ANTIFAZ_NER_THRESHOLD` | `0.5` | Puntuación mínima de una entidad (mayor que 0, como mucho 1) |
| `ANTIFAZ_NER_CACHE_ENTRIES` | `10000` | Textos en la caché; `0` la apaga |

**Tests.** El backend falso (`detect/ner/fake.py`) no se puede elegir con la configuración: no hay variable para el backend y la pasarela usa siempre el de GLiNER; solo el código (los tests) puede pasar otra ruta de fábrica. Busca nombres de un diccionario y, con palabras clave, se cuelga, muere, lanza una excepción con el texto, escribe el texto en stdout, stderr y el log o responde mal. Con él: el proceso colgado se mata al llegar al tiempo máximo y la siguiente petición funciona; `os._exit` bloquea; ni el log (`caplog`) ni la salida de los procesos hijos (`capfd`) llevan el nombre ni el DNI centinela (invariante 8); con la guardia apagada, el proveedor falso no recibe ningún nombre (invariante 2); `restore(mask(x)) == x` con el NER (Hypothesis); la guardia nunca bloquea lo que produjo el enmascarador con la propagación (Hypothesis). Los tests del modelo real llevan el marcador `ner_model` y se saltan si no hay `ANTIFAZ_NER_MODEL_DIR`.

## NER con el modelo real (issue 6, PR 6b): opcional y apagado por defecto

El modelo de nombres (GLiNER, fijado por su commit en `detect/ner/manifest.json`) se instala con `make ner-model` y se mide con `make bench NER=1`. **Sigue apagado por defecto** (`ANTIFAZ_NER_ENABLED=false`) porque **no cumple el suelo de precisión del 85 % en nombres** que se fijó para elegir el umbral (ADR-0011 y su enmienda del 2026-10-01):

- En la partición dev de MEDDOCAN (2026-10-01), la precisión de PERSON contra cualquier dato personal anotado fue del 67,5–70,9 % según el umbral (~70 %): **cerca del 30 % de las detecciones de nombres tapan texto que no es un dato personal** (416–510 detecciones). Por tipo es aún menor (63–69 %). ADDRESS sí llega (~96 %).
- Por eso el umbral publicado es el de respaldo (el más preciso) y el resultado lleva `floor_met: false`. Las cifras de test están en `docs/benchmark.md`.
- **Actívalo solo si te vale que tape de más**: protege más nombres, pero el modelo de IA recibe más marcadores donde había palabras normales y puede responder peor.
- Coste en el PC de desarrollo (Ryzen 7 5700U, solo CPU), de `evals/results/2026-10-01-0.1.0-ner.json`: **unos 740 MB de RAM (RSS) por proceso** del pool (590 MB en una ejecución anterior: varía con lo que el proceso haya procesado) y, por documento de MEDDOCAN (unos 3.000 caracteres), **p50 1,9 s / p95 3,8 s** con la caché fría (con la caché caliente, 2,9 ms / 5,6 ms). Arrancar el pool (comprobar dos veces el SHA-256 de 1,16 GB y cargar el modelo) tardó **51 s** (`load_seconds`).

**Cómo activarlo.**

```bash
make ner-model   # instala el extra ner (torch solo CPU) y descarga el modelo fijado (1,16 GB)
# en .env:
ANTIFAZ_NER_ENABLED=true
ANTIFAZ_NER_MODEL_DIR=models/gliner_multi_pii-v1
ANTIFAZ_NER_THRESHOLD=0.6          # el umbral publicado en docs/benchmark.md
ANTIFAZ_NER_TORCH_THREADS=0        # hilos de torch por proceso; 0 = los que elija torch
```

Un `uv sync` sin `--extra ner` (por ejemplo `make install`) desinstala el extra. torch 2.14 no publica ruedas para **macOS con Intel** (x86_64): allí el extra no se instala y el NER no está disponible.

**Qué lee el modelo.**

- **Sin red**: Hugging Face en modo offline; el nombre del codificador (`microsoft/mdeberta-v3-base`) se cambia en memoria por la copia local del tokenizador; los pesos con `torch.load(weights_only=True)` y `strict=True`.
- **Vista para el NER** (`detect/ner/view.py`): antes de trocear, las URL largas, los bloques base64/hex de 32 caracteres o más sin espacios y las series de 6 o más cifras pegadas a una letra se cambian por espacios de la misma longitud. Las posiciones no se mueven y los validadores y patrones siguen leyendo el texto entero. Un bloque base64 de 4 KB costaba ~12 s de CPU del modelo, pasaba el tiempo máximo, mataba el proceso y la recarga dejaba bloqueadas todas las peticiones; y "1234567890Jordi" era una sola palabra para el modelo.
- **Ventanas recortadas al límite del modelo**: nuestras ventanas de 200 tokens pueden ser miles de subpalabras (números largos, CJK). Pasado su largo de entrenamiento el modelo deja de ver nombres sin dar error (medido: un nombre tras 190 números de 40 cifras, 2.330 subpalabras, no se veía). El backend vuelve a cortar cada ventana con el tokenizador real en trozos de 384 tokens como máximo (prompt incluido) que comparten 32 palabras (y nunca más de la mitad del presupuesto). Una palabra que no cabe en 384 tokens bloquea la petición.
- **Presupuesto por llamada**: si una llamada necesita más de 4 trozos por ventana de media (texto que cuesta muchas más subpalabras que palabras: CJK o emoji al azar), el backend la rechaza **antes** de ejecutar el modelo. El proceso responde un error fijo y sigue vivo (no cuenta para el cortacircuitos); la petición se bloquea con 400. Un texto normal es un trozo por ventana. Una petición legítima muy grande puede seguir pasando el tiempo máximo (el fallo seguro de siempre).
- Las detecciones de los trozos vuelven sin unir; el motor las une después de filtrar por su umbral. Así la respuesta a un umbral es la de uno más bajo filtrada por puntuación, y el benchmark ejecuta el modelo una sola vez por ventana para todos los umbrales candidatos (`ScoreCache`, probado igual que ejecutar cada umbral).

## Lista de modelos, `/antifaz/scan` y `openapi.json` (issue 29)

**`GET /v1/models`** devuelve la lista de modelos del proveedor configurado, detrás de la puerta (pide la clave como todas las rutas). El SDK de OpenAI pide `GET {base}/models` y el de Anthropic `GET /v1/models` con `anthropic-version`: es la misma ruta, así que **esa cabecera decide el proveedor**:

| La petición trae `anthropic-version` | Va a | Con | Parámetros de consulta permitidos |
|---|---|---|---|
| Sí | `ANTIFAZ_ANTHROPIC_BASE_URL` + `/v1/models` | `x-api-key` de `.env` + `anthropic-version` y `anthropic-beta` comprobados | `limit` (1–1000), `after_id`, `before_id` (letras, dígitos, `. _ : -`, hasta 200) |
| No | `ANTIFAZ_OPENAI_BASE_URL` + `/models` | `Authorization: Bearer` de `.env` | ninguno |

- Si el proveedor elegido no tiene clave → 503 `not_configured` (el otro sigue funcionando). `anthropic-beta` sola no cambia de proveedor.
- Consulta con **lista de permitidos**: un nombre que no está en la lista, repetido, en mayúsculas, vacío o con otros caracteres (`/`, `&` codificado, `%0d%0a`, espacios, `@`…) → 400 `invalid_query`, y no sale nada. La consulta que se envía se **reconstruye** con los valores ya comprobados. Un valor que contiene una clave configurada también → 400, y lo mismo si la clave llega **partida** entre varios valores (en cualquier orden) o aparece en la consulta reconstruida.
- Los valores de la consulta pasan por el **detector** (en el mismo hilo limitado que el proxy, con el NER si está activo): un id no se puede enmascarar, así que un dato personal (un DNI como `after_id`) → 400 `antifaz_blocked`. No se envía cuerpo, así que no hay bytes que revisar con la guardia de salida.
- Cabeceras: `anthropic-version` y `anthropic-beta` con la misma regla que en `/v1/messages` (letras, dígitos, `. _ - ,`, hasta 200); repetidas, o con una clave configurada dentro (también partida entre las dos) → 400 `invalid_header` (desde este issue, también en `/v1/messages` y `count_tokens`). Ninguna otra cabecera del cliente llega al proveedor.
- Respuesta: un 401 o 403 del proveedor → el mismo estado con `upstream_auth_failed` fijo (issue 76); otro error del proveedor (4xx/5xx), su cuerpo tal cual si es JSON (si no → 502); si es de éxito, tiene que ser un objeto JSON (si no → 502 `bad_upstream_response`). En los dos casos se descarta con 502 si repite una clave configurada o un trozo reconocible de una, también escritos con escapes JSON (invariante 13). Una redirección → 502 `upstream_redirect`. No se reenvía ninguna cabecera del proveedor.
- Es un `GET`: la puerta no le pide `Content-Type`. `HEAD`, `POST` u otros métodos → 405 `method_not_allowed` (con clave).
- Todas las respuestas de la pasarela llevan `X-Content-Type-Options: nosniff`: el navegador nunca interpreta un cuerpo como HTML.

**`POST /antifaz/scan`** dice **dónde** hay datos personales en un texto, nunca cuáles son:

```bash
curl http://localhost:8000/antifaz/scan -H "Authorization: Bearer $ANTIFAZ_API_KEY" -H "Content-Type: application/json" \
  -d '{"text": "Mi DNI es 12345678Z"}'
# {"entities":[{"type":"ES_DNI","start":10,"end":19}]}
```

- Cuerpo: un objeto JSON con **solo** `text` (una cadena). Cualquier otra clave (`texts`, `image_url`, `source`, `file_id`…), un `text` que no sea cadena o un cuerpo que no sea un objeto → 400 `invalid_request`. Se lee con las reglas del proxy: tope `ANTIFAZ_MAX_BODY_BYTES` (413), UTF-8, sin claves repetidas, sin `NaN`.
- Usa **el mismo detector que el proxy** (`find_spans` en `mask/`, con el NER si está activo y la propagación de los nombres que encuentra), en el mismo hilo limitado. Si el detector falla o devuelve posiciones imposibles → 400 `antifaz_blocked` con mensaje fijo.
- La respuesta solo lleva `type`, `start` y `end` (`[start, end)`) por detección, también de los tipos que la política deja pasar (dice qué encontró; enmascarar lo decide la política). Las posiciones son **caracteres Unicode** (índices de Python): en JavaScript, un emoji cuenta como 2.
- No llama a ningún proveedor ni escribe el texto en ningún log.
- **Riesgo aceptado**: quien tiene la clave puede usarla para probar el detector (qué encuentra y qué se le escapa). Es lo mismo que puede hacer con la librería o con `antifaz scan`, que ya tiene.

**`docs/openapi.json`**: la pasarela sigue sin servir `/docs`, `/redoc` ni `/openapi.json` (ADR-0015; un test lo comprueba también con la clave). El esquema se publica como archivo estático, generado desde la propia app con `make openapi` (`scripts/export_openapi.py`, con una clave aleatoria que se tira: el esquema no lleva ninguna configuración). Un test compara el archivo del repo con el generado, así que nunca se queda atrás: si cambias una ruta, ejecuta `make openapi` y súbelo.

**Tests.** Las dos rutas entran solas en el test de la invariante 12 (recorre las rutas registradas). Además, cada ruta con clave, por pareja (ruta, método), tiene que estar en una de tres clases: envía un cuerpo al proveedor (pasa por la guardia), solo envía una consulta (que pasa por el detector) o no llama a ningún proveedor; una ruta nueva sin clasificar hace fallar el test. La invariante 13 tiene escenarios canario propios para las dos (consulta con la clave, cabeceras, errores y respuestas del proveedor con la clave, detector roto). Los ataques están en `tests/redteam/test_models_and_scan.py` y la prueba con los SDK oficiales (`models.list()`) en `tests/contract/`.

## La puerta cerrada por defecto (issue 20)

Decisión en [ADR-0015](adr/0015-puerta-cerrada-por-defecto.md) (propuesta). Todo pasa por un solo middleware (`api/gate.py`) antes de llegar a ninguna ruta, así que una ruta nueva queda protegida sin hacer nada.

**Arranque.** Antifaz se niega a arrancar, y dice qué variable falla sin mostrar su valor, si:

- `ANTIFAZ_API_KEY` falta, tiene menos de 32 caracteres o menos de 8 caracteres distintos, es el valor de `.env.example` (`change-me`, también escrito `change_me` o `ChangeMe`) o no es ASCII imprimible sin espacios. Genera una con `openssl rand -hex 32`;
- `ANTIFAZ_OPENAI_API_KEY` o `ANTIFAZ_ANTHROPIC_API_KEY` están definidas pero vacías, son el valor de ejemplo o no son ASCII imprimible sin espacios;
- `ANTIFAZ_ALLOWED_HOSTS` está vacía, tiene `*` o un comodín con menos de dos etiquetas detrás (`*.com`), o `ANTIFAZ_ALLOWED_ORIGINS` tiene algo que no sea `http(s)://host[:puerto]` (sin ruta ni barra final; `*` y `null` tampoco).

La app ya no se crea al importar el módulo: `uvicorn --factory antifaz.api.app:create_app` (es lo que hace `make dev`).

**Variables nuevas** (listas separadas por comas, o en JSON: `[ "a", "b" ]`):

| Variable | Por defecto | Qué hace |
|---|---|---|
| `ANTIFAZ_ALLOWED_HOSTS` | `localhost,127.0.0.1,[::1]` | Valores aceptados en la cabecera `Host` (sin el puerto y sin distinguir mayúsculas). Otro → 400. Admite `*.ejemplo.com`, no `*` ni `*.com` |
| `ANTIFAZ_ALLOWED_ORIGINS` | vacía | Orígenes de navegador aceptados, exactos y sin barra final (`https://intranet.ejemplo.com`). Vacía: toda petición con `Origin` → 403 |
| `ANTIFAZ_ADMIN_TOKEN` | sin definir | Token que abre el panel en `/panel` (ADR-0018, issue 53). Sin la variable, el panel no existe. Mismas reglas que `ANTIFAZ_API_KEY` y distinto de ella y de las claves de los proveedores. Vacía (`ANTIFAZ_ADMIN_TOKEN=`) es un error: "is empty: set a value or remove the variable" |
| `ANTIFAZ_TRUSTED_PROXIES` | vacía | IP exacta del proxy inverso que tiene delante el panel (por ejemplo `172.20.0.10`, una /32; nunca la puerta de enlace de Docker ni la red entera). Solo una conexión desde ellos puede fijar `X-Forwarded-For` y `X-Forwarded-Proto` para el panel. Se rechazan `0.0.0.0/0`, `::/0`, rangos con bits de host (`10.0.0.1/8`) y cualquier otra cosa |

**En cada petición**, en este orden:

1. `Host` en la lista (si no, 400), **antes** que la clave. Protege del DNS rebinding: una web ajena que apunta su dominio a la IP de la pasarela.
2. Ruta pública solo `/healthz`, con coincidencia exacta sobre la ruta ya decodificada (`scope["path"]`). Cualquier otra ruta, exista o no, pide la clave: `/healthz/`, `//v1/messages` o `/docs` también.
3. **Clave** en `Authorization: Bearer` o en `x-api-key` (en todas las rutas), con `hmac.compare_digest`. Si la cabecera viene dos veces, o si vienen las dos y no llevan las dos la clave → 401.
4. **`Origin`**: si viene y no está en `ANTIFAZ_ALLOWED_ORIGINS` → 403. No hay CORS: el navegador nunca recibe `Access-Control-Allow-Origin`, así que una web ajena no puede leer la respuesta ni pasar el preflight.
5. **`Content-Type`**: en todo lo que no sea `GET`, `HEAD` u `OPTIONS`, debe ser `application/json` (con `charset=utf-8` como único parámetro opcional). Un formulario o `text/plain`, que el navegador manda sin preflight → 415.
6. Al leer el cuerpo, un objeto con **claves repetidas** → 400. Si solo cambian en mayúsculas o anchura (`content` y `Content`) también, cuando es una clave que Antifaz lee (`READ_KEYS` en `providers/json_walk.py`), porque unos programas las leen como la misma y otros no. Un esquema con `Name` y `name` pasa.
7. Las claves de adjunto (`source`, `data`, `image_url`, `file`…) bloquean también en mayúsculas (`SOURCE`, `Data`).

Además: `X-Request-ID` siempre lo genera la pasarela (el del cliente se ignora); sin `/docs`, `/redoc` ni `/openapi.json` (el esquema está en [`docs/openapi.json`](openapi.json)); sin redirecciones de barra final (`/v1/messages/` → 404); los WebSocket se cierran siempre; el log de cada petición solo escribe la ruta si es una ruta registrada (si no, `-`), para que una clave o un DNI pegados en la URL no acaben en el log; y si el proveedor devuelve en su respuesta alguna de las claves configuradas (tal cual o con escapes JSON como `\u0061`), se descarta con un 502 fijo.

**Detrás de Docker o de un proxy inverso** (nginx, Traefik, Caddy):

- Pon en `ANTIFAZ_ALLOWED_HOSTS` el nombre con el que llegan los clientes (`antifaz`, el nombre del servicio en compose, o `antifaz.ejemplo.com`). `X-Forwarded-Host` no se mira.
- **Con el panel, el proxy tiene que mantener el `Host` original** (en nginx, `proxy_set_header Host $host;`; Caddy ya lo hace por defecto). El login compara `Origin` con el esquema y el `Host` que llegan: si el proxy lo reescribe (por ejemplo a `antifaz:8000`), el login responde 403. Para la API sola basta con poner en la lista el `Host` que llegue.
- El proxy no debe añadir cabeceras CORS ni un `Origin` propio.
- `/healthz` es pública: si el proxy la expone, solo dice la versión.
- `root_path` no está soportado: si la sirves bajo un prefijo (`--root-path`), `/healthz` puede pedir clave, porque la lista pública compara la ruta exacta y, si no coincide, falla cerrada. El panel sí decide sobre la ruta sin el `root_path` (la misma que usa el router), así que un prefijo nunca deja llegar a una ruta del panel sin pasar por su puerta; la redirección a `/panel/login` no lleva el prefijo.

**Tests.** `tests/redteam/test_invariants_12_13.py` recorre las rutas que la app registra de verdad (con `iter_route_contexts`, porque en FastAPI `app.routes` guarda los routers incluidos y no sus rutas), cada una con GET, HEAD, POST, PUT, PATCH, DELETE y OPTIONS y con alias (barra final, doble barra, mayúsculas, último carácter codificado): sin clave, 401 salvo `/healthz`. Cada ruta del proxy pasa por la guardia de salida con los mismos bytes que recibe el proveedor, y si la guardia bloquea no sale nada (invariante 12). Otro test usa claves canario y recorre 401, 400, 403, 404, 413, 415, 502 y 504, errores del proveedor y un proveedor que devuelve las cabeceras que recibió, con los loggers en `DEBUG`: ninguna clave aparece en logs, cuerpos ni cabeceras (invariante 13). Los ataques están en `tests/redteam/test_gateway.py`; los de trozos de clave (proveedor que responde 401/403 citando prefijo y últimos 4, con y sin streaming, y una propiedad con claves aleatorias), en `tests/redteam/test_key_fragments.py`.

## Puerta del panel (issue 53): configuración (11b-1)

Primer PR de la puerta del panel ([ADR-0018](adr/0018-el-panel-y-su-puerta.md)). **No añade ninguna ruta ni toca `api/gate.py`**: la pasarela se comporta igual que antes. Solo deja lista la configuración y las piezas puras que usará la puerta en el PR 11b-2.

- **Variables**: `ANTIFAZ_ADMIN_TOKEN` y `ANTIFAZ_TRUSTED_PROXIES` (tabla de arriba), en `config.py`, `.env.example` y la plantilla de `init` (un test impide que estas dos copias se separen). `check_safe_to_start` comprueba el token con las mismas reglas que la clave de la API, que sea distinto de ella y de las dos claves de proveedor (con `hmac.compare_digest`). Cada proxy pasa por **una sola regla**, `antifaz/trusted_networks.py`, que usan a la vez `config.py` y la puerta del panel: `ipaddress.ip_network(strict=True)`, sin `/0`, sin zona `%` y sin rangos IPv6 con IPv4 dentro (`::ffff:…`), que nunca coincidirían porque la IP de la conexión se lee como IPv4. Los mensajes nombran la variable, nunca el valor.
- **Invariante 13**: `configured_keys` incluye el token, así que `KeyWatch`, `client_values_hold_a_key` y el 502 por clave repetida del proveedor lo vigilan igual que a las otras claves (`tests/redteam/test_admin_token_watched.py`). `antifaz verify` también pone un token canario y comprueba que no sale.
- **`antifaz init`** genera siempre el token, igual que la clave (`secrets.token_hex(32)`, y otra vez si saliera igual que la clave). Lo enseña con la misma regla que la clave: solo en un terminal o con `--show-key`. Dice la URL del panel (`http://localhost:8000/panel`) y cómo apagarlo: borrar la línea `ANTIFAZ_ADMIN_TOKEN` de `.env` y reiniciar. Si hace copia del `.env` anterior, recuerda que la copia guarda las claves y el token antiguos y que hay que borrarla después de rotarlos (ADR-0017).
- **`antifaz doctor`** añade "panel: on/off" y "trusted proxies: N" (solo el número, nunca las IP), y avisa, también solo con el número, si algún rango es más ancho que /24 (IPv4) o /64 (IPv6).
- **Qué poner en `ANTIFAZ_TRUSTED_PROXIES`**: la IP **exacta** del contenedor del proxy (una /32), fija en Compose con `ipv4_address`. **Nunca** la puerta de enlace de Docker (`172.x.0.1`) ni la red entera: con el puerto publicado, las peticiones que entran por él llegan desde esa puerta de enlace, así que cualquier cliente podría falsear `X-Forwarded-For` y `X-Forwarded-Proto`. El proxy tiene que añadir `X-Forwarded-For` (al final, no en una línea nueva delante); si no lo añade, todos los clientes cuentan como el proxy y comparten el límite de intentos.
- **`antifaz.web`**, solo biblioteca estándar (más `antifaz.trusted_networks`, que también lo es):
  - `forwarded.py`: `client_ip` recorre `X-Forwarded-For` de derecha a izquierda y devuelve la primera IP que no es de un proxy de confianza. Si la conexión no llega de un proxy de confianza, la cabecera se ignora. Se saltan los elementos vacíos (RFC 9110 §5.6.1) y se aceptan entradas con puerto (`a.b.c.d:puerto`, `[v6]` y `[v6]:puerto`), porque algunos proxies las escriben así. Si todas son de confianza, no hay ninguna o la primera que no es de confianza es basura (`unknown`, `%zona`, un puerto fuera de 1–65535, texto), se usa la IP de la conexión. Lo que hay a la izquierda del cliente ni se lee: así un cliente no puede añadir basura para que todos cuenten como la IP del proxy (y bloquear el login de todos). Tiene tope: como mucho 16 entradas y los últimos 8 KiB del texto, leyendo las líneas desde la última y solo hasta donde hace falta (una cabecera de 2 MB o 100 000 líneas repetidas no cuestan más); lo que queda cortado a la izquierda no se lee, y el corte por sí solo no hace volver a la IP de la conexión. Varias líneas se leen en orden (RFC 9110): un proxy que pone su línea **delante** deja a la derecha la línea que escribió el cliente, así que solo hay que fiarse de proxies que añaden al final. Las IPv6 con IPv4 dentro (`::ffff:a.b.c.d`) se leen como IPv4. `effective_scheme` solo acepta `X-Forwarded-Proto` de un proxy de confianza, una sola cabecera y exactamente `https` o `http`; si no, "no es HTTPS". `is_local_host` solo es cierto para `localhost`, `127.0.0.1` y `[::1]`, sin puerto o con uno de 1 a 65535: `localhost.evil.com` o `127.0.0.2`, no.
  - `sessions.py`: `SessionStore` (interfaz) y `MemorySessionStore`. El identificador sale de `secrets.token_urlsafe(32)` y solo se guarda su huella SHA-256, con la hora de creación, el último uso y el token CSRF, en un `Session` inmutable cuyo `repr` no enseña ni la huella ni el token CSRF. 8 horas como máximo y 30 minutos sin uso, comprobado al consultar (sin temporizadores). `on_close` avisa con el motivo (`logout`, `expired`, `evicted`; desde 11b-2b también `replaced` y `scheme_mismatch`) para cortar las conexiones de «En directo»; si un suscriptor falla, se registra un mensaje fijo con el tipo del error y se sigue avisando a los demás: cerrar, consultar o crear una sesión nunca falla por eso. Con 32 sesiones, al crear otra se expulsa la más antigua: **el login nunca se rechaza porque esté lleno**.
  - `login_limit.py`: como mucho 5 fallos en cualquier ventana de 60 s, `Retry-After` redondeado hacia arriba, sin límite global. Cuenta por IP en IPv4 y por /64 en IPv6 (una máquina suele tener una /64 entera). Cada IP guarda como mucho la hora de sus 5 últimos fallos y la tabla 10 000 IP, ordenadas por el último fallo; al llenarse se sacan por delante las caducadas y luego la del fallo más antiguo (coste constante amortizado): una IP nueva siempre puede intentarlo.
  - Ninguna de las tres usa cerrojos: son correctas solo si todo corre en el mismo bucle de eventos y sin `await` a mitad de una llamada. Por eso las rutas del panel que las usan son `async def` (desde 11b-2a), y los avisos de `on_close` son síncronos y no bloquean (el SSE de «En directo», en 11e, solo marcará un `asyncio.Event` o usará `call_soon`).
- **Tests**: unitarios de cada pieza, propiedades con Hypothesis (la IP elegida nunca está a la izquierda del primer no confiable desde la derecha, con puertos y el tope de 16; el esquema de un par no confiable es siempre el de la conexión; validez de la sesión con relojes aleatorios; nunca más de 5 fallos en 60 s, también si se registran fallos estando bloqueado) y tests de AST: `antifaz/web` no llama a `get_secret_value`, no lee `admin_token`, `_secret_value`, `model_dump` ni `__dict__`, no llama a `vars` ni a `getattr` con un nombre que no sea literal y no importa `antifaz.config` ni `pydantic` (en 11b-2 el panel solo recibirá la huella). `scripts/check_coverage.py` exige un 90 % en `web/`.

## Puerta del panel: entrar (11b-2a)

Segundo PR de la puerta del panel ([ADR-0018](adr/0018-el-panel-y-su-puerta.md) y su addendum del 2026-10-13). Añade la entrada: login, sesión y una página provisional. Sin cierre de sesión (11b-2b), sin estáticos y sin JavaScript (11c).

- **Dónde se decide.** `GateMiddleware` (`api/gate.py`) mira la ruta ya decodificada y sin el `root_path` de ASGI (`route_path()`, la misma regla que el router de Starlette) justo después de comprobar que es HTTP y **antes** de la lista pública y de la clave: `/panel` o lo que empieza por `/panel/` va a la puerta del panel y **nunca** a las reglas de la clave. `/PANEL`, `//panel` o `/panelx` siguen en la pasarela (401 sin clave). `/panel%2Flogin` llega ya decodificado como `/panel/login`, la misma ruta que ve el router. `gate.py` no importa `antifaz.web`: la app le pasa la puerta como una función.
- **Sin `ANTIFAZ_ADMIN_TOKEN`** no hay puerta: todas las rutas `/panel*` dan el mismo 404 JSON que una ruta desconocida, con o sin clave, y `antifaz.web` no se importa (un test lo comprueba en un subproceso). Las rutas registradas son las de siempre.
- **Con el token**, `create_app` importa `antifaz.web` dentro de una función y construye un `PanelState`: la huella SHA-256 del token (bytes, nunca el token), las redes de los proxies de confianza, un `MemorySessionStore` y un `FailureLimiter`. Es **lo único** que reciben la puerta y las rutas. Las rutas del panel no salen en el OpenAPI (`include_in_schema=False`).
- **La puerta** (`web/door.py`), en este orden:
  1. Envuelve `send` para que toda respuesta de `/panel*` lleve las cabeceras del ADR (`web/headers.py`): la CSP exacta, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `nosniff`, COOP y CORP `same-origin`, una `Permissions-Policy` que apaga cámara, micrófono, geolocalización, pago, USB, Bluetooth, HID, puerto serie, WebAuthn, realidad virtual… y `Cache-Control: no-store`. Si la respuesta ya traía una de esas cabeceras, se sustituye. **Excepciones**: el 400 de un `Host` no permitido (lo responde `TrustedHostMiddleware`, antes de la puerta) y cualquier cosa que se responda fuera de la puerta. Un error inesperado **dentro** de la puerta sí las lleva: si aún no se ha enviado nada, la puerta responde un 500 JSON fijo (`internal_error`) con ellas y vuelve a lanzar el error para que el servidor lo registre una vez.
  2. HTTPS o `localhost`: si el esquema (el de la conexión, o `X-Forwarded-Proto` de un proxy de confianza) no es `https` y el `Host` no es `localhost`, `127.0.0.1` o `[::1]`, responde con una página fija 403 que explica cómo ponerlo detrás de HTTPS. No llega a ninguna ruta, así que nunca pone una cookie, tampoco en `POST /panel/login`.
  3. Rutas públicas, por (ruta, método) exactos: `GET /panel/login` y `POST /panel/login`. `/panel/login/` o `HEAD` no lo son.
  4. El resto necesita una sesión viva, leída **solo** de la cookie del esquema de la petición. Sin ella, `GET /panel` responde 303 con `Location: /panel/login` (fija y relativa, nunca construida con el `Host`) y cualquier otra ruta, 401.
- **La cookie según el esquema** (`web/cookies.py`): por HTTPS, `__Host-antifaz_session` con `Secure; HttpOnly; SameSite=Strict; Path=/`; en `http://localhost`, `antifaz_session` sin `Secure`, con `HttpOnly; SameSite=Strict; Path=/panel`. Las dos con `Max-Age=28800` y sin `Domain`. La cabecera `Cookie` se lee a mano juntando todas sus líneas; el nombre se compara exacto; si el nombre del esquema aparece dos veces, no hay sesión; y el valor tiene que tener la forma de un identificador (`[A-Za-z0-9_-]`, 128 caracteres como mucho). Por qué dos cookies: WebKit no guarda cookies `Secure` por `http://localhost` (tabla en el addendum del ADR).
- **`POST /panel/login`** (`web/routes.py`):
  1. CSRF capa 3 y JSON (`web/csrf.py`): una sola `Sec-Fetch-Site: same-origin`, un solo `Origin` igual a `esquema://Host` (con el puerto) y `Content-Type: application/json`. Si no, 403 `csrf_rejected`, y **no cuenta** como fallo.
  2. El cuerpo se lee como stream y se deja de leer al pasar de 1 KiB, venga con `Content-Length`, sin él, en trozos o con un `Content-Length` falso, y con un plazo de 5 s (`anyio.fail_after`). Si el cliente se desconecta a medias o no termina a tiempo, recibe el mismo 401 fijo y **no cuenta**: no se ha probado ningún token, y una línea lenta no debe poder bloquear al administrador. Sin 500 ni traza en el log.
  3. El límite de intentos (5 fallos por minuto por IP del cliente, `forwarded.client_ip`) se mira **antes** de comparar: bloqueado es 429 con `Retry-After`, también con el token bueno, y no se llega a comparar.
  4. El cuerpo tiene que ser exactamente `{"token": "..."}` (sin claves repetidas: `json` de la biblioteca estándar con un `object_pairs_hook`) y el token, de 256 caracteres como mucho. Se compara su SHA-256 con la huella guardada con `hmac.compare_digest`. Cualquier fallo (cuerpo, tamaño o token) da **el mismo 401, byte a byte**, y cuenta.
  5. Si llegaba una cookie de sesión, esa sesión se cierra (contra la fijación de sesión); se crea una nueva y se pone la cookie del esquema. Respuesta: `{"ok": true}`.
- **`GET /panel`** con sesión: una página provisional con `<meta name="antifaz-csrf" content="…">` y `no-store`. Las tres páginas (`web/pages.py`) son fijas, sin `<script>`, `<style>`, `style=` ni `on…=`, y nunca llevan nada que haya escrito el cliente.
- **Módulos neutros.** El panel no carga nunca `antifaz.config` (donde están los secretos), ni directa ni indirectamente. Por eso `route_path()` vive en `antifaz/routing.py` (solo biblioteca estándar) y `AppError`, `error_body()`, `error_response()` y los errores del panel en `antifaz/http_errors.py` (sin imports del proyecto ni pydantic, solo `JSONResponse` de Starlette); `api/gate.py`, `api/errors.py` y `antifaz.web` los importan de ahí. La puerta usa las respuestas de Starlette, no las de FastAPI. Dos tests lo vigilan (`tests/unit/test_web_never_reads_the_token.py`): cada módulo de `antifaz.web` se importa en un intérprete nuevo y no deja cargados `antifaz.config`, `pydantic_settings` ni `pydantic` (salvo `pydantic` en `web/routes.py`, que lo necesita FastAPI); y un recorrido estático de los imports `antifaz.*` (con los `__init__` de los paquetes padre, imports relativos y perezosos) comprueba que ninguno llega a `antifaz.config` ni importa pydantic. `import antifaz` no carga la configuración, así que la comprobación en tiempo de ejecución es exacta. Cada una tiene casos negativos con un paquete falso.
- **Errores.** `AppError` tiene ahora `headers` (vacío por defecto), que usan el manejador de errores, la puerta de la pasarela y la del panel (`Retry-After` del 429). Errores nuevos: `PanelNotFoundError` (404), `PanelUnauthorizedError` (401), `PanelLoginFailedError` (401, cuerpo fijo), `TooManyAttemptsError` (429) y `CsrfRejectedError` (403).
- **Concurrencia.** El almacén de sesiones y el límite de intentos no tienen cerrojos. Son correctos solo porque todas las rutas del panel son `async def` en el único bucle de eventos y, en el login, no hay ningún `await` desde que se mira el límite hasta la respuesta: el cuerpo se lee antes y, desde `limiter.allowed(...)`, todo es código síncrono. Tres tests de AST lo vigilan: todas las funciones de `web/sessions.py` y `web/login_limit.py` son `def` normales y esos módulos no tienen `await`; todas las rutas de `web/routes.py` son corrutinas, así que FastAPI nunca las lleva a su pool de hilos; y en `login` no hay ningún `await`, `async for` ni `async with` en una línea posterior a la llamada a `.allowed(` (con casos negativos que prueban que el test caza uno insertado).
- **Límites conocidos.** En `localhost` las cookies no se separan por puerto: dos instancias de Antifaz en puertos distintos se pisan la sesión, y otra aplicación local con una cookie `antifaz_session` impide entrar hasta borrarla. `SameSite` tampoco separa puertos; protegen el `Origin` con puerto y el token CSRF. En Docker sin proxy, todas las peticiones llegan desde la misma IP y el límite de intentos se comparte; lo mismo detrás de un proxy de confianza que no añade `X-Forwarded-For` (o de una CDN que no está en `ANTIFAZ_TRUSTED_PROXIES`): cualquiera puede dejar fuera al administrador un minuto. Sin el token, el 404 del panel es idéntico byte a byte al de una ruta desconocida, pero un cliente anónimo puede saber igualmente si el panel está encendido (con el token, `GET /panel/login` es público y responde 200). Safari de verdad se comprueba en 11f.
- **Tests**: unitarios (`tests/unit/test_web_door_pieces.py`, `test_web_concurrency.py`), propiedades (`tests/property/test_panel_login_property.py`: `is_panel_path` si y solo si el primer segmento es `panel`; el lector de cookies nunca devuelve otro nombre ni el del otro esquema, y nada si se repite; el `Origin` vale si y solo si es igual; y, contra la app entera, ninguna ruta con sesión da 2xx sin una cookie válida del esquema, solo un login bueno pone cookie y toda respuesta lleva las cabeceras), integración (`tests/integration/test_panel_login.py`) y red-team (`tests/redteam/test_panel_door.py`: cookie del otro esquema, mayúsculas, duplicadas, trucos de ruta con un scope ASGI a mano, CSRF, fijación, fuerza bruta con un espía en `compare_digest`, `X-Forwarded-For` y `X-Forwarded-Proto` falsos, cuerpos enormes y canarios del token, el identificador y el token CSRF con todo en `DEBUG`). La invariante 12 se amplía: con el token, cada (ruta, método) está en una sola puerta, la clave no abre el panel y una sesión del panel no abre la pasarela.

## Puerta del panel: salir y CSRF completo (11b-2b)

Tercer PR de la puerta del panel ([ADR-0018](adr/0018-el-panel-y-su-puerta.md), su addendum del 2026-10-13 y la nota del 2026-10-14). Añade el cierre de sesión, las tres capas del CSRF en todo lo que cambia algo y la sesión ligada a su esquema. Sigue sin estáticos ni JavaScript (11c) y sin «En directo» (11e).

- **El CSRF, en un solo sitio: la puerta** (`web/door.py`), cerrado por defecto. Solo `GET` y `HEAD` son seguros. Cualquier otro método (`POST`, `PUT`, `DELETE`, `PATCH`, `OPTIONS`…) en cualquier ruta `/panel*` pasa, en este orden:
  1. **Capa 3 y JSON**: una sola `Sec-Fetch-Site: same-origin`, un solo `Origin` igual a `esquema://Host` (con el puerto) y `Content-Type: application/json`. Si no, 403 `csrf_rejected`, **antes de mirar la sesión**: una petición de otro origen nunca refresca el último uso de una sesión.
  2. **Sesión viva del esquema de la petición** (ver abajo). Si no, 401.
  3. **Capa 2, el token CSRF**: exactamente una cabecera `X-Antifaz-CSRF`, ASCII y no vacía, igual al token de la sesión (`hmac.compare_digest` sobre bytes; `web/csrf.py`, `has_csrf_token`). Si no, el mismo 403 que en el paso 1. La capa 1, `SameSite=Strict`, va en la cookie.

  El login ya no comprueba el CSRF por su cuenta: lo hace la puerta. Es **la única excepción a la capa del token** (no tiene sesión todavía) y conserva origen + JSON. La lista de excepciones es explícita y por (ruta, método) exactos: `CSRF_TOKEN_EXEMPT = {("/panel/login", "POST")}`, y las rutas públicas se construyen a partir de ella (`PUBLIC_ROUTES = {GET /panel/login} ∪ CSRF_TOKEN_EXEMPT`): una ruta que no es segura solo se salta la sesión y el token si está en esa lista. Un test de red-team recorre todas las rutas `/panel` registradas en la app, ahora y en el futuro, y para cada (ruta, método) que no es `GET` ni `HEAD` comprueba que o es exactamente el login o, con una sesión válida y todo lo demás bien pero sin token, responde 403. `OPTIONS` no es seguro: 403 sin la capa 3 y 405 del router con todo bien; nunca hay cabeceras CORS. `HEAD` es seguro: 401 sin sesión y 405 con ella.
- **`POST /panel/logout`** (`web/routes.py`, `async def` sin ningún `await`): la puerta solo lo deja pasar con sesión viva y token. Borra la sesión del servidor (motivo `logout`; sus suscriptores se enteran antes de que salga la respuesta) y responde 200 `{"ok": true}` con **exactamente una** `Set-Cookie`, la cookie caducada del esquema de la petición (mismo nombre y atributos, valor vacío y `Max-Age=0`: `cookies.expired_cookie`), y `Clear-Site-Data: "cache"` exacto. Nunca `"cookies"`: en `localhost` borraría las cookies de todas las aplicaciones de todos los puertos. No lee el cuerpo (la puerta ya exigió JSON). Sin sesión viva: 401 y no toca ninguna cookie. Una segunda vez, o la cookie vieja después: 401 (303 en `GET /panel`).
- **Qué cuenta como uso de la sesión.** La puerta busca la sesión con `peek()` (comprueba caducidad y esquema sin tocar el último uso) y solo cuando la petición ha pasado todas sus comprobaciones llama a `touch()` para contar el uso, y únicamente si viene de la propia página del panel o de un cliente que no es navegador: `Sec-Fetch-Site` `same-origin` o `none`, o sin esa cabecera (`csrf.counts_as_use`). Así, una petición rechazada (por ejemplo, con un token CSRF equivocado) o una página de otro puerto de `localhost` (`same-site`, que sí lleva la cookie) no mantienen viva la sesión: caduca a los 30 minutos sin uso real. Entre `peek()` y `touch()` no hay ningún `await` (test de AST), y la puerta no usa `get()`.
- **La sesión, ligada a su esquema** (`web/sessions.py`): cada sesión guarda el esquema con el que se creó, `"https"` o `"http-local"` (`cookies.session_scheme`). `create(scheme)` y `get(id, scheme)` lo piden siempre, sin valor por defecto. Si un id válido llega por el otro esquema (copiado a mano bajo el nombre de cookie del otro esquema), `get` lo rechaza **y borra la sesión** (motivo `scheme_mismatch`): quien lo hace no sigue las reglas, así que la sesión deja de valer también en su esquema. El nombre de la cookie ya separaba los esquemas; esto cubre la copia a mano.
- **Motivos de cierre**: `logout`, `replaced` (un login nuevo con la cookie de una sesión anterior la cierra; antes se registraba como `logout`), `expired`, `evicted`, `scheme_mismatch` y `gone` (solo para `watch()`: la sesión ya no estaba). `delete(id, reason)` ya no tiene motivo por defecto: cada llamada dice el suyo; si la sesión ya había caducado (aunque nadie la hubiera consultado), la cierra como `expired`, nunca con el motivo pedido. Suscriptores: se avisa a **todos** pase lo que pase. Una `Exception` de uno se registra (solo el tipo) y se sigue; una `BaseException` que no es `Exception` (`CancelledError`, `KeyboardInterrupt`) tampoco impide avisar a los demás: la sesión ya está borrada, se avisa a todos y al final se vuelve a lanzar la primera.
- **El token CSRF no sale del id de sesión** (decisión de Miquel): es un valor aleatorio propio (`secrets.token_urlsafe(32)`, sacado aparte), solo viaja en el `<meta>` de `GET /panel` (`no-store`) y está entre los canarios de los logs. Tests: el token no es el id, ni su SHA-256 (hex o base64), ni otro hash o HMAC del id, ni un prefijo o sufijo; dos sesiones nunca comparten token; y, con todo en `DEBUG`, el token solo aparece en el cuerpo de su página: nunca en cabeceras, en otros cuerpos ni en los logs.
- **Cortar las conexiones, ahora y en 11e.** `watch(store, huella, cut)` es una capa fina sobre `on_close`: solo llama a `cut(motivo)` cuando se cierra esa sesión, una vez, y luego se da de baja sola; devuelve la función para darse de baja antes. Primero se suscribe y después comprueba la sesión: si esa comprobación la encuentra caducada, `cut` recibe `expired`; si no existe (ya cerrada, o nunca existió), `cut("gone")` se llama en el acto y no queda nada suscrito (mil `watch` sobre huellas desconocidas no dejan ningún aviso registrado). Es el gancho que usará el SSE de «En directo» en 11e. Un test sobre la app entera (cambiando `MemorySessionStore` por una subclase con reloj falso) prueba que un suscriptor recibe `logout` antes de que salga la respuesta del cierre de sesión, `expired` en la siguiente consulta tras caducar y `replaced` al volver a entrar, y que un suscriptor que falla no rompe el cierre (200, cookie caducada, sesión borrada y en el log solo el tipo del error).
- **Concurrencia**: `logout` no tiene ningún `await` (test de AST, con caso negativo); `sessions.py` y `login_limit.py` siguen sin `async` ni `await`.
- **Límites conocidos (11b-2b).** Una página de otro puerto de `localhost` lleva la cookie en sus `GET` (`SameSite` no separa puertos) y recibe respuesta, pero ya no cuenta como uso de la sesión; sus peticiones que cambian algo se rechazan por el `Origin` con puerto y el token. Dos cierres de sesión a la vez de la misma sesión pueden responder los dos 200 con la cookie caducada: es idempotente y no hace daño (la sesión se cierra y se avisa una sola vez).
- **Lo que queda para 11e**: el SSE de «En directo» con `watch()`: cerrar la conexión al cerrar la sesión y comprobar la caducidad en cada envío, con su test de red-team (abrir el SSE, cerrar sesión y comprobar que no llega nada más y que la conexión termina).
- **Tests**: unitarios (`tests/unit/test_web_sessions.py`: esquema, borrado por `scheme_mismatch`, motivos, `watch` e independencia del token; `test_web_door_pieces.py`: `expired_cookie` por esquema y `has_csrf_token`; `test_web_concurrency.py`), propiedades (`tests/property/test_panel_logout_property.py`: contra la app entera, con `POST /panel/logout`, `PUT /panel` y `DELETE /panel` como testigos, mezcla esquema, cookie, token, `Sec-Fetch-Site`, `Origin` y `Content-Type`: 2xx si y solo si pasan las tres capas con una sesión viva del mismo esquema; `Set-Cookie` solo en un cierre correcto y exactamente la caducada del esquema; después, la misma cookie da 401), integración (`tests/integration/test_panel_logout.py`) y red-team (`tests/redteam/test_panel_door.py`: variantes del token, capa 3 con cookie y token válidos, formularios, otros orígenes y otros puertos de `localhost`, reutilización de la cookie, doble cierre, id movido al otro esquema, fijación, canarios, `OPTIONS` y `HEAD`, y ninguna ruta salvo el login sin la capa del token). La invariante 12 añade `POST /panel/logout` a las rutas con sesión.

Otro test compara el SHA-256 de cada fuente y licencia con la tabla de `design/README.md`.
- **`panel.css`** es el CSS del prototipo aprobado sin lo que solo usa el prototipo: la barra de controles, los interruptores de móvil y de «menos movimiento», el apartado del logo, la entrada con las puertas y la animación del antifaz (vuelve con la vista «Prueba un texto»). El grano de fondo, que era un SVG `data:` dentro del CSS, es ahora `static/grain.svg` (un test comprueba que es el mismo SVG). Ningún `data:` en el CSS servido.
- **El manifiesto** (`web/assets.py`, solo biblioteca estándar). Una lista explícita de archivos (`SERVED`). Al arrancar se lee cada uno, se le quitan los comentarios (`/* … */` en CSS y `<!-- … -->` en SVG: las notas para quien edita el código fuente no llegan al navegador; los archivos de la carpeta no cambian), se calcula su SHA-256 y se publica como `nombre.<12 hex>.ext` bajo `/panel/static/`. Dentro de un CSS, cada `url("x")` se reescribe al nombre con hash de `x`, y el CSS se hashea después, así que cambia de nombre si cambia un archivo al que apunta. Todo queda **en memoria**, en un diccionario de solo lectura por nombre exacto: servir un archivo nunca toca el disco ni junta el nombre pedido con una carpeta. La pasarela **no arranca** (`AssetError`) si un nombre no es un archivo simple con una de las cuatro extensiones (`.css`, `.js`, `.woff2`, `.svg`, cada una con su `Content-Type` fijo), si es un enlace simbólico o se resuelve fuera de la carpeta, o si un archivo de texto no es UTF-8. Los CSS y los SVG se revisan con **listas de lo permitido**, no de lo prohibido:
  - **CSS**: ninguna barra invertida (los escapes como `u\72l(` o `@\69mport` esconden palabras), nada de `image-set()` ni `-webkit-image-set()`, nada de `data:`, solo las reglas `@font-face`, `@media`, `@container` y `@keyframes` (las que usa el panel; `@import`, `@namespace` o `@supports` paran el arranque) y cada `url()` tiene que ser exactamente otro archivo de la lista (sin esquema, sin `//`, sin ruta, sin `#`).
  - **SVG**: ningún `<!DOCTYPE>` ni `<!ENTITY>` y ninguna instrucción de proceso salvo la declaración XML; se analiza con `xml.etree.ElementTree` (biblioteca estándar; sin DOCTYPE no se puede declarar ninguna entidad) y solo se admiten los elementos SVG de `SVG_ELEMENTS` (los que usan `logo.svg` y `grain.svg`, más `symbol`/`use` para enlaces internos) y los atributos de `SVG_ATTRIBUTES`. `href` y `xlink:href` solo como `#id`, y `url(…)` solo como `url(#id)`. Así quedan fuera `<script>`, `<style>`, `<set>`, `<animate>`, `<foreignObject>`, los elementos de otro espacio de nombres (un `<iframe>` XHTML), cualquier atributo `on…` y el atributo `style`. Un test prueba ataques de cada tipo (SMIL que cambia un `href` a `javascript:`, `<style>@import`, `style=` y `fill=` con `url(https://…)`, entidades, XHTML, `<svg/onload=…>`) y que los enlaces `#id` sí pasan. Las licencias OFL van en la misma carpeta (la OFL pide que viajen con las fuentes) pero nunca se sirven.
- **`GET /panel/static/{name}`** (`web/routes.py`, `async def`): busca `name` en el manifiesto y devuelve sus bytes con su tipo. Si no está, el mismo 404 que una ruta desconocida.
- **La regla pública de la puerta** (`web/door.py`, `is_public_static`): solo `GET` y solo si la ruta es **exactamente** una del manifiesto. Esa petición no mira la sesión (ni la refresca). Cualquier otro nombre bajo `/panel/static/` (el nombre sin hash, una licencia, un truco de ruta) sigue la regla general: 401 sin sesión y 404 con ella. `HEAD` no es público (401 sin sesión, 405 con ella) y un `POST` es una petición que cambia algo: 403 por CSRF. Por HTTP fuera de `localhost`, los estáticos también reciben la página «Solo HTTPS» (403). Pasan por la puerta, así que llevan todas las cabeceras de seguridad, `nosniff` incluida.
- **`Cache-Control` por respuesta**, decidido en la puerta y nunca en una ruta (`web/headers.py`): `public, max-age=31536000, immutable` **solo** para un 200 de un archivo del manifiesto (un archivo nuevo es una URL nueva); `no-store` para todo lo demás, también los errores bajo `/panel/static/`, las páginas HTML y la API del panel. `with_security_headers(headers, cache_control)` solo acepta esos dos valores.
- **Plantillas** (`web/templating.py` y `web/templates/`): `jinja2.Environment` con `autoescape=True`, `StrictUndefined` (un valor que falta es un error, nunca un texto vacío) y sin recarga. Las tres plantillas (`base.html`, `login.html` y `panel.html`, de momento con contenido provisional) se leen una vez al arrancar en un `DictLoader` y se compilan ahí; la de entrar se pinta una vez y la del panel se pinta una vez de prueba, así que una plantilla rota o un estático que no está en el manifiesto paran el arranque. Solo reciben valores del servidor: las URLs del manifiesto y el token CSRF de la sesión. Nunca `Jinja2Templates` ni `request.url_for` (construyen URLs con la cabecera `Host`): las URLs son las fijas `/panel/static/…`. Un test lee las plantillas y prohíbe `|safe`, `{% autoescape false %}` y `Markup`.
- **`pages.py`** se queda solo con la página fija «Solo HTTPS», sin estilos ni enlaces (por HTTP fuera de `localhost` la puerta también rechaza los estáticos).
- **Las piezas puras siguen puras**: `assets.py` entra en la lista de módulos de solo biblioteca estándar y `templating.py` solo puede importar Jinja2, la biblioteca estándar y esas piezas (`tests/unit/test_web_never_reads_the_token.py`). Ningún módulo de `antifaz.web` carga `antifaz.config`, ni directa ni indirectamente.
- **Peticiones condicionales y parciales**: la ruta no atiende `Range`, `If-None-Match`, `If-Modified-Since` ni `Accept-Encoding`: siempre responde 200 con el archivo entero (nunca 206 ni 304), y la respuesta no cambia con la query ni con el `Host` permitido (tests de red-team).
- **Límite conocido (11c-1): las URLs del panel son absolutas** (`/panel/…`, `/panel/static/…`, la redirección a `/panel/login`). Detrás de un proxy que publica Antifaz bajo un prefijo (un `root_path` como `/antifaz`), las páginas cargarían los estáticos y enlaces sin ese prefijo y no funcionarían. Se usa en la raíz del dominio (o con el proxy reenviando `/panel` tal cual).
- **Empaquetado**: hatchling ya mete en la rueda todo lo que hay bajo `src/antifaz` y `.dockerignore` deja pasar `src/`, así que no hizo falta cambiar nada; un test construye la rueda de verdad (`uv build --wheel`) y comprueba que lleva cada estático con sus bytes, cada licencia OFL junto a su fuente y las plantillas. En `make e2e`, otro test arranca la imagen con un token de administrador de usar y tirar, pide un estático (200, `immutable`, los mismos bytes) y comprueba que las fuentes y sus licencias están dentro.
- **Tests**: unitarios (`tests/unit/test_web_assets.py`, `test_web_templating.py`, `test_packaging.py`, `test_web_door_pieces.py`), integración (`tests/integration/test_panel_static.py`), red-team (`tests/redteam/test_panel_static.py`: `../`, `%2e%2e%2f`, `..%2f`, `%2F`, `..\`, `%5c`, `%252e`, caracteres de ancho completo, `%00`, mayúsculas, `//`, barra final, `;param`, el nombre sin hash o con el hash de otro archivo, `__init__.py` y plantillas, como ámbitos ASGI en crudo, con y sin sesión: nunca un 200 ni los bytes de un archivo) y propiedades (`tests/property/test_panel_static_property.py`). El HTML servido se analiza con `html.parser` (`tests/html_rules.py`): ningún `<script>` sin `src`, ningún `<style>`, ningún atributo `style` ni `on…`, nada de `javascript:` ni `data:`, y cada `src`/`href` es un estático del manifiesto, un `#` o una ruta fija del panel. La invariante 12 añade `GET /panel/static/{name}` como clase propia.

## Panel en navegadores reales (11c-2a)

`make panel-check` abre las páginas de hoy del panel (la de entrar y la provisional de `/panel`) en Chromium, Firefox y WebKit con Playwright. No forma parte de `make check`. Sustituye al `check_design --target panel` que estaba previsto para 11f: `make design-check` sigue revisando solo el prototipo.

- **Dependencias aparte.** Playwright 1.63.0 y axe-playwright-python 0.1.8 están en el grupo `panel` de `pyproject.toml`, con versión fija y en `uv.lock` (Dependabot y `make audit` los ven). `uv sync` y `make check` no los instalan, y la imagen tampoco: un test mira el lock, lo que se distribuye y el Dockerfile, y `make e2e` lista los paquetes de la imagen. Sin `--panel`, pytest ni siquiera recoge `tests/browser`, así que `make test` nunca importa Playwright. Los navegadores se instalan una vez (ver `CONTRIBUTING.md`).
- **El arnés** (`tests/browser/`). Cada test arranca su propia pasarela dentro del proceso: uvicorn en un hilo, en un socket de `127.0.0.1` con puerto libre, sin `.env`, con tokens de usar y tirar y sin ninguna variable `ANTIFAZ_*`, `OPENAI_*` ni `ANTHROPIC_*`. El cliente de los proveedores falla si se usa (y el test comprueba que nadie lo intentó) y `forbid_network()` solo deja conexiones a loopback. Cada test usa un contexto de navegador nuevo, con movimiento reducido. Una ruta de Playwright corta y apunta cualquier petición que no vaya a la pasarela; si hay alguna, el test falla. Nada de esperas fijas: se espera a `load` y a `document.fonts.ready`, y los tiempos de Playwright solo evitan que algo se quede colgado.
- **Qué comprueba** en cada navegador: cero infracciones de CSP y consola limpia (sin errores, avisos ni peticiones fallidas) en las dos páginas; ningún código en línea en el DOM vivo; entrar y salir con `fetch` desde la propia página, así que pasan por la puerta con el `Origin` y el `Sec-Fetch-Site` del navegador (el servidor de pruebas apunta lo que llegó); la cookie `antifaz_session` (`HttpOnly`, `SameSite=Strict`, `Path=/panel`, sin `Secure`, sin `Domain`, con `Max-Age`), `document.cookie` vacío y el almacenamiento vacío; 401 sin cookie con un token falso y 429 con `Retry-After` tras cinco fallos; tras salir, ni cookie ni panel, tampoco al volver atrás; y axe-core sin ninguna infracción en claro y oscuro, a 1280 y 390 px.
- **Canarios.** Que la lista de infracciones esté vacía solo vale si el detector funciona. Por eso un test sirve, en la misma dirección, una página con la CSP real del panel y un `<script>` en línea, y exige que cada navegador registre la infracción. Otro hace una petición a una dirección de documentación (192.0.2.1) y exige que la ruta la corte y la apunte.
- **axe, aparte.** axe se inyecta en la página y la CSP podría bloquearlo, así que se pasa en otra sesión del navegador, como dice el ADR-0018, con `bypass_csp` para que la CSP no bloquee el script inyectado. Cada página del panel se comprueba además con su cabecera CSP real, y un canario sirve una página sin CSP para demostrar que esa comprobación la distingue. Se usa el `axe.min.js` que trae la rueda de axe-playwright-python, nunca un CDN.
- **El tema oscuro en Firefox (revisión de 11c-3a)**: Playwright con Firefox pierde el `color_scheme` del contexto en la primera navegación a una página con `Cross-Origin-Opener-Policy: same-origin` (las de la pasarela), así que hasta ahora las pruebas «oscuras» (axe incluido) se pasaban en claro en Firefox: el oscuro no se había comprobado nunca ahí. El arnés guarda el tema pedido, lo vuelve a emular en la página tras cada `goto()` (desde ahí se mantiene en las navegaciones y recargas siguientes) y comprueba con `matchMedia` que la página lo tiene; si no, el test falla. Con el oscuro de verdad, axe no encuentra ninguna infracción en Firefox.
- **WebKit para Windows** (el de Playwright, no Safari) no guarda `SameSite` en su almacén de cookies: la cookie llega con `SameSite=Strict` (el test lo comprueba en la cabecera `Set-Cookie`, en los tres navegadores), pero WebKit la apunta como `None`. En ese motor, lo que frena las peticiones de otra web es la puerta (`Origin` y `Sec-Fetch-Site`) y el token CSRF. Safari de verdad se comprueba en 11f. Al final del registro, el test escribe lo que guardó cada navegador (`stored sameSite on webkit/win32: None`), solo ese atributo.
- **Chromium en Linux** (el «headless shell» de la CI) no conoce la función `bluetooth` de la cabecera `Permissions-Policy` y escribe en la consola un aviso fijo: `Error with Permissions-Policy header: Unrecognized feature: 'bluetooth'.`. La cabecera no cambia. Es la única excepción a «consola limpia»: solo en Chromium sobre Linux y solo ese texto exacto (`tests/browser/console_rules.py`, con tests unitarios que corren también en Windows). Además es estricta: en esa plataforma el aviso **tiene que** salir; el día que Chromium aprenda la función, el test falla y se quita la excepción. Cualquier otro mensaje, en cualquier navegador, sigue fallando.
- **Sin trazas.** Si un test falla, solo quedan una captura y un registro de texto con los tokens tapados, en `test-results/panel-browser/` (fuera de git). Se tapan los tokens de la pasarela, las cookies y el token CSRF que vio cada pestaña, y cualquier tira de 32 o más caracteres de los que usan los tokens. Nunca trazas, vídeos ni HAR de Playwright: guardarían los tokens y las cookies.
- **Nada secreto en un `assert`.** Un `assert` que falla imprime lo que compara, y el registro de la CI es público. Las cookies se miran solo por nombre y atributos, y un test revisa el código para que ningún `assert` toque un token, una cookie, las cabeceras o el HTML.
- **Aislado.** Además de las variables de Antifaz y de los proveedores, la sesión quita `PLAYWRIGHT_*`, `DEBUG`, `DEBUG_FILE`, `PWDEBUG` y los proxies (`DEBUG=pw:*` escribiría cada mensaje del protocolo, tokens incluidos). Chromium arranca con reglas de DNS que no resuelven nada salvo `127.0.0.1`.
- **Para 11c-2b.** Las capturas de vistas que enseñen claves o evidencias tienen que usar la opción `mask` de Playwright sobre esos elementos, o no hacerse.
- **CI**: el trabajo «Panel in a real browser (Chromium)» lo pasa solo en Chromium (su «headless shell», unos 122 MB que se descargan una vez por versión de Playwright y después salen de la caché de Actions, con la versión en la clave y sin claves parciales), sin secretos y con permiso de solo lectura. Si falla, sube solo esas capturas y registros. WebKit en Linux tiene su propio flujo, `.github/workflows/panel-webkit.yml` («Panel in WebKit on Linux»): solo se lanza a mano o en un PR que cambie ese archivo, sin caché, instala WebKit con sus paquetes del sistema y escribe en el registro cuánto ocupan.

## Panel: idiomas, entrar y el esqueleto (11c-2b)

En pocas palabras: el panel ya tiene su pantalla para entrar, las cinco pestañas del diseño aprobado (todavía vacías) y el botón «Salir», y habla español e inglés. Añadir otro idioma es añadir un archivo. Nada se guarda en el navegador. Ver la nota del 2026-10-18 en [ADR-0018](adr/0018-el-panel-y-su-puerta.md).

### Idiomas

- **Un catálogo por idioma**: `src/antifaz/web/i18n/<código>.json`, un objeto JSON plano de clave → texto plano (por ejemplo `"logout": "Salir"`). `en.json` es la referencia. Al arrancar (`web/i18n.py`, solo biblioteca estándar) se leen los archivos cuyo nombre es un código de idioma (`es.json`, `pt-BR.json`; cualquier otro archivo de la carpeta se ignora) y se comprueba que cada uno tiene **exactamente las claves de `en.json`**, los mismos `{huecos}` en cada texto (por ejemplo `{seconds}`), solo texto plano (sin `<`, `>`, entidades HTML, caracteres de control ni llaves sueltas), ningún texto vacío y su propio nombre en `language.name` («Español», «English»). Si algo falla, la pasarela **no arranca** y el mensaje es una sola línea con el archivo y la clave, sin traza encadenada.
- **Añadir un idioma = añadir un archivo**: se copia `en.json` con el código nuevo, se traducen los textos y listo; el selector lo enseña solo. Los tests de paridad recorren todos los catálogos que encuentran, así que el archivo nuevo se comprueba sin tocar ningún test. La rueda y la imagen lo llevan sin cambios (un test construye la rueda y compara la carpeta entera). Ver `CONTRIBUTING.md`.
- **Qué idioma se usa en cada petición**: `?lang=xx` si es un catálogo cargado (el valor que llega nunca se usa ni se repite: solo se compara con la lista); si no, `Accept-Language`, del que solo se miran los primeros 256 caracteres y las primeras 10 entradas no vacías (una entrada cortada por el límite se descarta y, como pide la RFC 9110, los elementos vacíos de la lista no cuentan), con sus pesos `q` (`q=0` es «este no»), y que casa por la etiqueta exacta o por el idioma principal (`es-ES` → `es`); `*` vale por el idioma de referencia (inglés) con su propio peso, así que `es;q=0.5, *` da inglés; si no, inglés. Las dos páginas HTML responden con `<html lang>`, `Content-Language` y `Vary: Accept-Language`, y siguen con `no-store`. Los estáticos (CSS, JS, fuentes) son los mismos en todos los idiomas: mismo hash y caché `immutable`.
- **Páginas por idioma**: la de entrar se pinta entera al arrancar, una por idioma; la del panel se compila una vez y se pinta en cada petición con el catálogo del idioma y el token CSRF de la sesión, como antes. Las plantillas reciben los textos con `t("clave")`.
- **Ningún texto fuera del catálogo**: un test pinta las páginas con catálogos «de fichas» (cada texto es `⟦clave⟧`) y exige que cada nodo de texto y cada atributo que se ve o se oye (`aria-label`, `title`, `alt`, `placeholder`, el `value` de un botón y los `data-text-*` que copian los scripts) esté hecho solo de esas fichas. Solo se admiten además la versión, los dígitos 1–5 de los atajos y los `{huecos}` que rellenan los scripts. Otro test exige que cada clave de `en.json` la use alguna plantilla (ninguna clave muerta).
- **Selector de idioma**, junto al botón del tema: enlaces normales a la misma página con `?lang=<código>`, uno por catálogo, con su nombre propio, `lang` y `hreflang`, y `aria-current` en el actual. No guarda nada (ni cookie ni almacenamiento). Al entrar y al salir se conserva el `?lang` (el código sale del `<html lang>` de la página, no de la URL).
- **Límite conocido**: si alguien abre `/panel?lang=es` sin sesión, la puerta redirige a `/panel/login` sin el `?lang` (la redirección es fija y no se construye con la petición); la página de entrar se elige entonces por `Accept-Language`.

### Entrar (`static/login.js`)

- Formulario con `method="post" action="/panel/login" novalidate`. El campo del token es `type="password"`, **sin `name`** (el formulario no envía nada por sí solo; sin JavaScript, el navegador mandaría un cuerpo vacío que la puerta rechaza), con `autocomplete="current-password"`, `spellcheck="false"` y `autocapitalize="off"`. Lleva además un campo de usuario oculto con `autocomplete="username"` y el valor fijo `admin` (ningún dato personal) para que los gestores de contraseñas puedan guardar el token.
- Al enviar, el script copia el valor a una variable local y **vacía el campo antes de esperar nada**; después hace un `fetch` a `/panel/login` con `credentials: "same-origin"`, `cache: "no-store"`, `redirect: "error"`, `referrerPolicy: "no-referrer"` y el cuerpo JSON `{"token": …}`. Sin `X-Antifaz-CSRF`: el login sigue siendo la única excepción a esa capa. El botón se desactiva mientras espera. Con 200, `location.replace("/panel")` (con el `?lang` si lo había). Con 401, 429 (con los segundos de `Retry-After` si es un entero positivo), 403 o un fallo de red, un mensaje fijo del catálogo en una zona `role="alert"` (con `textContent`) y el foco vuelve al campo. Con el campo vacío no se envía nada.

### El panel (`static/panel.js` y `templates/panel.html`)

- **Las cinco pestañas** del diseño aprobado («Prueba un texto», «En directo», «Claves», «Políticas» y «Estado») con el patrón de pestañas de ARIA: `tabindex` itinerante, `aria-selected` y paneles ocultos; las flechas siguen la orientación de la lista (arriba y abajo en la barra lateral; izquierda y derecha en la barra del móvil, a 640 px o menos, y `aria-orientation` cambia con ella), Inicio y Fin, y las teclas 1–5 sin modificadores. Esas teclas solo actúan con el foco dentro de la lista de pestañas o de la zona de las vistas (`#main`), y nunca en un campo de texto: así cumplen la pauta WCAG 2.1.4 (atajos de un solo carácter, nivel A), que pide que un atajo de una tecla se pueda apagar, cambiar o que solo funcione cuando su componente tiene el foco. Con el foco en el selector de idioma, el botón del tema, «Salir» o en ninguna parte, no hacen nada (test en los tres navegadores). Sin `#` en la URL. Cada vista tiene por ahora su cabecera y el bloque vacío del diseño, que dice qué se verá y que llega en una próxima versión; «Estado» recuerda `antifaz doctor --providers`.
- **«Salir»** al pie de la barra lateral y, en el móvil, en la barra de arriba: `POST /panel/logout` con `X-Antifaz-CSRF` (del `<meta>`) y el cuerpo `{}`. Con 200 o 401, a la pantalla de entrar en el mismo idioma; con 403 (o sin red), un aviso del catálogo. Lo que impide que el botón de atrás enseñe el panel tras salir es la puerta (sin sesión, `/panel` lleva a la pantalla de entrar) y `no-store` en el HTML: eso es lo que comprueba el test del botón de atrás. Como defensa añadida, una página que vuelve de la caché de atrás y adelante (`pageshow` con `persisted`) se recarga; el Chromium de Playwright arranca sin esa caché, así que otro test lanza el evento a mano (con `persisted: true` recarga, con `false` no).
- **Tema**: sigue al sistema (`prefers-color-scheme`) hasta que se pulsa el botón, que cambia `data-theme`. No se guarda.
- **Nada en línea**: ni atributos `style`, ni código en el HTML, ni `on…`. La entrada escalonada de cada vista usa `:nth-child` en `panel.css` (el prototipo usaba `style="--i:N"`, que la CSP prohíbe). Los iconos son un `<svg>` con `<symbol>` dentro de la página.
- **Los scripts no tienen texto visible ni comentarios** (ningún archivo servido los tiene): todo lo que se lee sale de la página, de un `<template>` o de atributos `data-text-*`, con `textContent`. Un test los lee como texto con un pequeño analizador: cada cadena tiene que ser una clave, un selector, un nombre de atributo o evento, una cabecera, una ruta relativa fija o una de una lista corta; prohíbe `eval`, `Function`, `innerHTML` y parecidos, `document.write`, el almacenamiento (`localStorage`, `sessionStorage`, `indexedDB`, `caches`, cookies), `console`, URLs absolutas, manejadores `.onx =`, `.style`, temporizadores, plantillas de texto y `fetch` a una URL en una variable; exige `"use strict"` primero y que `X-Antifaz-CSRF` no esté en `login.js` y sí en `panel.js`. Los dos se sirven del manifiesto byte a byte con `text/javascript; charset=utf-8`.
- **CodeQL** analiza también JavaScript (`javascript-typescript` en `codeql.yml`, con los mismos permisos y versiones fijadas).

### En el móvil (revisión de las capturas, Miquel)

- **Pestañas abajo**: con la ventana a 640 px o menos, las cinco pestañas son una barra fija en la parte de abajo de la pantalla, al alcance del pulgar: icono y un nombre corto de los catálogos (`tab.*.short`: «Probar», «Directo», «Claves», «Políticas», «Estado» / «Try», «Live», «Keys», «Policies», «Status»). El nombre va en `rem`, en una sola línea y nunca partido por dentro de una palabra (11c-3a). La barra deja sitio a la zona de gestos del teléfono (`env(safe-area-inset-bottom)`, con `viewport-fit=cover`) y el contenido lleva un margen abajo para que nada quede debajo de ella. Siguen siendo las mismas pestañas ARIA: flechas izquierda y derecha, Inicio y Fin, y 1–5 con el foco en ellas o en las vistas. Los tests comprueban a 320, 360, 390 y 430 px que la barra toca el borde de abajo y que ningún nombre corto se corta (también con el texto al 200 %), y en pantallas bajas (320×480 y 390×500, donde la página sí se desplaza) que la barra sigue abajo tras bajar del todo y que el final de la vista queda por encima de ella.
- **El foco nunca queda tapado** (WCAG 2.4.11): `scroll-padding-top` y `scroll-padding-bottom` en la raíz dejan sitio a la barra de arriba y a la de pestañas; un test lleva el foco con Tab a un botón al final de una vista en una pantalla baja y comprueba que queda entre las dos barras. Va en una `@media (max-width: 704px)` (la raíz no puede depender de un contenedor; el margen de más donde no hay barras no molesta).
- **Barra de arriba**: solo el logo y un botón de ajustes de 44 px (icono y nombre accesible `settings.label`). El botón abre un menú (patrón de divulgación: `aria-expanded` y `aria-controls`) con el idioma, el tema y «Salir». En el menú, el tema es un interruptor (`role="switch"`, 11c-3a) con una palabra visible fija del catálogo («Tema oscuro» / «Dark theme»), que es también su nombre accesible (WCAG 2.5.3); `aria-checked` dice si el tema oscuro es el que se ve (el del sistema o el elegido) y `panel.js` lo pone al día también cuando cambia el del sistema. El carril y la bolita son decoración (`aria-hidden`): la bolita a la derecha y el carril índigo cuando está encendido, en claro y en oscuro. Espacio e Intro lo cambian (es un `<button>`). En el escritorio y en la pantalla de entrar sigue siendo un botón de icono con `aria-label`. Al abrir el menú, el foco entra en él; Tab sigue dentro y Mayús+Tab vuelve al botón; Escape lo cierra y devuelve el foco al botón; un clic fuera, o sacar el foco del menú y del botón, lo cierra. Si la ventana crece hasta el escritorio con el menú abierto, se cierra (y Escape ya no lleva el foco a un botón oculto). No guarda nada. Si el foco sale de la página sin ir a otro elemento (WebKit no pasa por los enlaces con Tab), el menú no se cierra: Safari no da el foco a un botón al pulsarlo, y un clic dentro del menú no debe cerrarlo.
- **Pantalla completa**: en el teléfono la ventana es la pantalla (sin tarjeta, sin márgenes ni esquinas, `min-height: 100dvh` con `100vh` de respaldo), también en la pantalla de entrar. **Una sola medida decide**: el `body` es un contenedor (`page`) y esa parte va con `@container page (max-width: 672px)`, medida, como la ventana, sin la barra de desplazamiento. Con una `@media`, entre 673 y unos 688 px con barra de desplazamiento clásica (Windows) la ventana ya tenía las reglas del móvil pero seguía con tarjeta y con `backdrop-filter`, que hacía de bloque contenedor de la barra fija: la barra quedaba dentro de la tarjeta, cortada. Un test lo prueba a 640, 660, 680, 688 y 700 px con una barra de desplazamiento simulada. Sin `backdrop-filter` en la ventana ni en la barra lateral del móvil, y sin el «esconder al bajar» del prototipo (ningún script lo activaba y un `transform` también haría de bloque contenedor).
- **Texto al 200 % (11c-3a)**: una sola propiedad, `--tabbar-h` (en `:root`), dice lo alta que es la barra de pestañas: las partes fijas en px (borde, rellenos, icono y hueco: 49 px) más la línea del nombre corto en `rem` (`.8rem`, la misma `line-height` del nombre). La usan el margen de abajo de `.app-content` y el `scroll-padding-bottom` de la raíz, así que crecen con el texto. Si los cinco nombres no caben (texto grande), la lista de pestañas se desplaza de lado dentro de la barra (`repeat(5, minmax(max-content, 1fr))` y `overflow-x: auto`), con palabras enteras (`white-space: nowrap`, sin `overflow-wrap: anywhere`). Un difuminado en el borde avisa de que hay más: `panel.js` pone `is-more-start` / `is-more-end` según el desplazamiento (al desplazar y al cambiar de tamaño, con un `ResizeObserver` sobre la lista y cada pestaña) y el CSS aplica un `mask-image` (solo transparencia, con `-webkit-` para WebKit) en el lado que tiene más; al llegar al final, ese lado deja de difuminarse. Nada se anima, así que no hay nada que parar con movimiento reducido. La pestaña elegida se lleva a la vista (`reveal()`, con `scrollIntoView({inline: "nearest"})`) y la lista tiene `scroll-padding-inline` del ancho del difuminado más 4 px: la pestaña con el foco o elegida nunca queda dentro del difuminado, así que su anillo de foco y su aspecto de elegida no se apagan (WCAG 2.4.7 y 1.4.11); solo se desplaza la barra, nunca la página. La barra esconde su barra de desplazamiento: el aviso es el difuminado (con ratón, Mayús + rueda o un clic en una pestaña que asoma). La orientación (`aria-orientation` y qué flechas valen) sale de dónde están las pestañas (si las dos primeras están a la misma altura, es horizontal), no de un `flex-direction` que en la rejilla del móvil no significa nada; un test lo comprueba forzando `flex-direction: column`. Los tests miden con un `Range` que cada palabra de cada nombre ocupa una línea (es y en, 320 y 390 px), que el difuminado aparece y desaparece en su lado, que el teclado recorre las cinco y que axe da 0, que la pestaña activa queda al menos a la anchura del difuminado del borde que aún tiene más, y que el final de la vista y un elemento con foco quedan por encima de la barra. Otro test, con la CSP de verdad (sin `bypass_csp`) y a 240 px para que los nombres no quepan al 100 %, desplaza la barra y comprueba que las clases cambian sin ninguna infracción de CSP ni petición fuera (espera con `evaluate()` y una promesa por fotogramas: `wait_for_function()` necesita `eval` en la página, que la CSP prohíbe).
- **Todo el texto crece con el tamaño de letra (revisión de las capturas al 200 %)**: el título de cada vista, su descripción y la marca «Antifaz» de la barra de arriba no crecían porque iban en px. Ahora todos los `font-size` de `panel.css` y los tokens de texto de `tokens.css` van en `rem` con el mismo valor a 16 px (14px → .875rem, 12,5px → .78125rem, etc.), así que al 100 % nada cambia: las 28 capturas al 100 % salen idénticas píxel a píxel. El título de vista sigue a la ventana y al texto: `clamp(1.875rem, calc(4.4cqi + (1rem - 16px) * 3.125), 3.125rem)`; el término `(1rem - 16px)` vale 0 con la raíz por defecto (igual que el antiguo `clamp(30px, 4.4cqi, 50px)`) y crece con la letra, porque la parte en `cqi` sola no crecería. El `scroll-padding-top` del móvil crece con la línea de la marca (`max(72px, calc(1.546875rem + 24px))`). Quedan en px los tamaños de iconos, bordes y espacios; las piezas de las vistas que aún no se pintan (`.num`, los contadores de `.found`) tienen alto fijo y se revisarán cuando lleguen.
- **Enlace de salto**: se esconde con `translateY(calc(-100% - 16px))`, que depende de su propia altura, así que no asoma ni con el texto al 200 % (antes asomaba 1 px incluso al 100 %).
- **Pantalla de entrar en el teléfono**: la tarjeta centra su contenido en vertical con márgenes automáticos (`margin-top: auto` en el primer hijo y `margin-bottom: auto` en la nota). La tarjeta también es una `.app-window`, que en el teléfono lleva `min-height: 100dvh`: con la fila del idioma encima, la página bajaba unos 44 px de más. `min-height: auto` en la tarjeta lo deshace (con `flex: 1` sigue llenando la pantalla); `auto` y no `0`, porque con `0` una tarjeta más alta que la pantalla encogería y el `overflow: clip` de la ventana cortaría su final. Un test mide que a 390×844 la página no se desplaza y que el centro del contenido está a 8 px o menos del centro de la pantalla bajo la fila del idioma. Si no cabe (texto al 200 % en 320×568), los márgenes se quedan en cero: empieza arriba, sin cortar nada, y la página se desplaza.
- **Zonas seguras**: con `viewport-fit=cover`, los márgenes laterales de la página (a cualquier ancho) y la barra de pestañas usan `env(safe-area-inset-left/right)`.

Un test que escribe un token falso a propósito dice cuántos rechazos ha provocado, y solo esas líneas exactas (401 y 429), como mucho esas veces, se admiten (`tests/browser/console_rules.py`). Cualquier otra sigue fallando.

Desde ahí se envían al login y al logout de `127.0.0.1` un `fetch` JSON, uno `no-cors` en `text/plain` y un formulario `text/plain` cuyo cuerpo es JSON (con el token bueno en el caso del login). El servidor de pruebas apunta lo que contestó la puerta (el navegador esconde la respuesta `no-cors` por la cabecera CORP): cada `POST` que llega es un 403, no se crea ninguna sesión y la que había sigue abierta. Con la intercepción de peticiones activa, Playwright contesta él mismo algunos preflight CORS (en Chromium), así que el `POST` del `fetch` JSON puede llegar a la puerta según el motor; la puerta lo rechaza igual. Firefox manda `Origin: null` en esos `POST`; Chromium y WebKit, el de `localhost`. Chromium resuelve ahora `localhost` además de `127.0.0.1`. La misma página se sirve también como `http://127.0.0.1:<otro puerto>`: **el mismo sitio** con otro origen, así que la cookie `SameSite=Strict` sí viaja. Ahí solo frenan la comprobación de origen de la puerta (`Sec-Fetch-Site` y `Origin`) y el token CSRF, y cada `POST` (login y logout, con y sin JSON) recibe igualmente un 403 y la sesión sigue abierta, en los tres navegadores. Cuando se llega a ese límite, el resumen del final del registro lo dice (`graceful-shutdown limit hit: <test>`), así que un cuelgue de verdad no se esconde (hoy pasa en Chromium en las pruebas de otro sitio).

## Panel: Estado (11c-3b)

En pocas palabras: la pestaña «Estado» ya enseña datos reales de la pasarela que tienes delante: la versión, cuánto lleva en marcha, cómo se sirve el panel, el estado del detector de nombres, qué proveedores tienen clave y algunas cifras de seguridad. Solo lee el estado local: nunca llama a un proveedor, nunca enseña una clave ni una dirección completa y no se actualiza sola. Ver la nota del 2026-10-19 en [ADR-0018](adr/0018-el-panel-y-su-puerta.md).

### La ruta `GET /panel/api/status`

- **Solo con sesión** del esquema de la petición, como `GET /panel`: la clave de la API no la abre y no está entre las rutas públicas. Es `async def`. **Solo la lee la propia página del panel**: en cualquier ruta `/panel/api/*` (también con `GET`), si llega `Sec-Fetch-Site` y no es exactamente `same-origin` (otra web, otro puerto de `localhost` —`same-site`, que sí lleva la cookie—, o la dirección escrita a mano en la barra —`none`—), la puerta responde 403 `csrf_rejected` antes de mirar la sesión. Sin esa cabecera no es un navegador (curl, un monitor) y decide la sesión, como en el resto. `GET /panel` no cambia: cualquier sitio puede abrir la página, y solo sus propias peticiones cuentan como uso. `POST` y los demás métodos: 403 sin el token CSRF (la puerta) y 405 con él; `HEAD`, 405. Lleva las cabeceras de seguridad de la puerta y `no-store`, y **no** lleva `Vary` ni `Content-Language`: el JSON no tiene idioma (solo enums).
- **Esquema cerrado** (`web/status_response.py`, pydantic con `extra="forbid"` y modo estricto): `{"schema": 1, "version", "uptime_seconds", "panel_scheme": "https" | "http_localhost", "detectors": {"validators": "on", "patterns": "on", "ner": "off" | "ok" | "starting" | "circuit_open" | "closed" | "unknown"}, "providers": [{"id": "openai" | "anthropic", "has_key", "address", "has_credentials"}], "limits": {"allowed_hosts", "allowed_origins", "trusted_proxies"}, "overall": "ok" | "warn" | "danger"}`. Cada hoja es un booleano, un entero no negativo, un enum, la versión (patrón fijo) o una dirección; no hay sitio para un texto libre.
- **La dirección de un proveedor** (`provider_address`): `"default"` si es la URL de fábrica (con o sin `/` final); si no, solo el host y el puerto **que httpx va a contactar de verdad**: `api/app.py` (`base_url_parts`) lee la URL con `httpx.URL`, el mismo analizador que usa el cliente de los proveedores, y toma su `raw_host` (el nombre en ASCII según IDNA2008, una IPv4 o una IPv6, que aquí recibe corchetes) y su puerto; si httpx rechaza la URL (letras de ancho completo, `Ⓐ`, una `é` descompuesta, `[v1.abc]`…), es `"custom"`. Así el panel nunca nombra un host distinto del que se contacta (`ß.example` sale `xn--zca.example`, como lo envía httpx). Después, la pieza pura `web/status.py` exige el patrón estricto; cualquier otra cosa (`%`, guion bajo, etiquetas vacías, puerto 0 o fuera de rango, otro esquema) es `"custom"`, y también una etiqueta de más de 32 caracteres o que empieza por `sk-` (parece una clave). **Nunca** el usuario, la contraseña, la ruta, la consulta ni el fragmento: solo se enseña host[:puerto], así que **el nombre del host no debe llevar nunca un secreto**. `has_credentials` sale del `userinfo` de httpx (también con el truco `https://proxy.example\@evil/`, donde httpx contacta `evil` con usuario): la vista avisa. Un test de propiedades (Hypothesis) comprueba que, con cualquier texto, la salida es `default`, `custom` o un host que pasa el patrón, sin `@ / ? #`.
- **`overall`**: `danger` si el NER está parado (`closed`) o si ningún proveedor tiene clave (sin clave, la pasarela no puede reenviar nada; decisión de Miquel); `warn` si el NER está arrancando, en pausa tras fallos o en un estado desconocido, o si una dirección lleva usuario; si no, `ok`. Con el NER apagado (lo normal), `overall` es `ok` solo si algún proveedor tiene clave y ninguna dirección lleva usuario.

### De dónde salen los datos (sin secretos)

- `create_app` construye en `_panel()` un `StatusFacts` (`web/status.py`, solo biblioteca estándar, pieza pura): si cada proveedor tiene clave, su dirección ya comprobada, los tres recuentos (`len()` de las listas, nunca su contenido), la versión, el reloj (inyectable en los tests) y una función que lee el estado del NER en cada petición y guarda el propio NER, nunca la app (`NER_OFF` si no hay NER; los cuatro estados del pool pasan tal cual y cualquier otra respuesta es `unknown`, nunca el valor crudo). `PanelState` lo lleva al panel; los `Settings` nunca llegan a `antifaz.web`. El tiempo en marcha cuenta desde que terminó el arranque: el `lifespan` llama a `mark_started()` cuando los procesos del NER ya han cargado (antes, 0).
- `NerPool.status()` ya no toma el candado del pool (que se mantiene mientras se lanzan, esperan o recogen procesos): lee atributos escritos bajo el candado sobre una copia de la lista de procesos, así que `/healthz` y esta ruta nunca bloquean el bucle de eventos.
- `web/status_response.py` es el único módulo de `antifaz.web` que importa pydantic, y solo `BaseModel`, `ConfigDict`, `Field`, `StrictBool` y `StrictInt` (nunca un tipo `Secret*`); el test de importaciones lo comprueba, y también que ni `web/status.py` ni el esquema alcanzan `antifaz.config` ni `antifaz.providers`, directa o indirectamente.

### La vista (`templates/panel.html` y `static/panel.js`)

- **Cuatro tarjetas**: la pasarela (estado general, versión, tiempo en marcha en unidades cortas del catálogo —«3 d 4 h», «12 min», «menos de 1 min»—, «Panel servido por» HTTPS o localhost, nombres de host y orígenes permitidos, proxies de confianza, y la nota fija de que las sesiones viven en la memoria de cada proceso), el detector de nombres (sus cinco estados, con el actual marcado con `aria-current` y la etiqueta «Ahora»), los proveedores (con clave o sin ella; dirección oficial, propia o el host; aviso si la dirección lleva usuario o contraseña; la línea de `antifaz doctor --providers`) y Evidencias (de momento, «Llega con el registro de evidencias (punto 9)»).
- **Respecto al diseño aprobado** (decisión de Miquel): fuera «Escucha en», «Base de datos», `/healthz` y las barras de latencia; dentro «Panel servido por», las cifras de seguridad y la nota de las sesiones. Sin píldora en la cabecera, sin punto de aviso en la pestaña y sin contadores: eso llega con 11e, igual que «Comprobar ahora» (que sí llamará a los proveedores, como `doctor`).
- **Cuándo pide los datos**: la primera vez que se enseña la vista, al pulsar «Actualizar» y cuando la página vuelve a estar visible **solo si «Estado» es la vista elegida**. Nunca al cargar la página, nunca con temporizadores (el test de los scripts prohíbe `setTimeout` y `setInterval`) y nunca con la página oculta. Un contador descarta una respuesta que llega tarde.
- **Mientras carga**: `aria-busy` en las tarjetas (se atenúan un poco), el aviso de error se oculta y se vacía, el botón queda `aria-disabled="true"` (nunca `disabled`, que haría perder el foco) y la línea `role=status` dice «Comprobando…»; al terminar, «Comprobado a las 10:44» con `Intl.DateTimeFormat` en el idioma de la página, y el foco sigue en el botón si se pulsó.
- **Una petición cada vez**: pulsar otra vez mientras lee no pide nada; volver a estar visible mientras lee, tampoco; pulsar mientras lee una carga que empezó la página (primera vez o visibilidad) la cancela con un `AbortController` (nunca un temporizador) y pide de nuevo, conservando el foco. El contador descarta cualquier respuesta tardía.
- **Errores**: un 401 lleva a la pantalla de entrar conservando `?lang`. Un error de red u otra respuesta enseña el aviso `role=alert` con el texto del catálogo (como se ocultó al empezar, un fallo tras otro fallo se anuncia de nuevo, WCAG 4.1.3), conserva los últimos datos en gris (solo el color: el texto mantiene su contraste), la píldora de la pasarela pasa a «Sin actualizar» (neutra, nunca verde) y la línea dice «Datos de las 10:44, sin actualizar».
- **Texto**: todas las etiquetas salen de un `<template id="status-messages">` del catálogo y se escriben con `textContent`. Un valor que el script no conoce (un enum nuevo, un tipo raro) enseña «Desconocido», nunca el texto que llegó. El host de un proveedor se enseña solo si tiene únicamente minúsculas, cifras y `.-:[]`.

### Pruebas

- Unitarias: la tabla de `provider_address` (pasando por `base_url_parts`, con `ß`, `faß`, `ς`, ancho completo, `Ⓐ`, `é` descompuesta, `[v1.abc]`, la barra invertida antes de `@`, etiquetas largas y `sk-`) y su propiedad, `status()` del pool con el candado tomado por otro hilo, `mark_started()`, la tabla de `overall`, el reloj inyectado, el esquema (rechaza campos de más y enums desconocidos), los tipos de `StatusFacts` (ningún `SecretStr` ni texto libre salvo la versión y el host), el marcado de la vista y la frase de los scripts.
- Integración: puerta (sesión, sin sesión, solo la clave, cookie del otro esquema, CSRF, 405, `HEAD`, 403 con `Sec-Fetch-Site` que no es `same-origin` sin renovar el último uso, `GET /panel` sin cambios), cabeceras, el arranque y la función del NER, cada estado del NER, proveedores con y sin clave y direcciones propias.
- Red team (`tests/redteam/test_panel_status_privacy.py`): claves, token y URLs canario (`https://user:<canario>@proxy.example/v1/<canario>?key=<canario>`): ni el JSON, ni el panel en los dos idiomas, ni los logs en DEBUG contienen un canario ni **ningún trozo de 6 caracteres o más** de uno. ## Panel: Prueba un texto (API, 11d-a)

En pocas palabras: `POST /panel/api/try` recibe un texto, lo pasa por el **mismo** enmascarado que el proxy (validadores, patrones, el modelo NER si está encendido, la política de la pasarela y la guardia de salida), se inventa una respuesta con **solo los marcadores** que salieron y la restaura. Devuelve qué se encontró, qué recibiría la IA y qué volvería a ti. **No llama a ninguna IA**, no guarda nada y **el proxy va primero**: una petición del proxy espera como mucho un lote pequeño de una prueba. La pantalla llega en 11d-b. Ver la nota del 2026-10-19 (11d-a) en [ADR-0018](adr/0018-el-panel-y-su-puerta.md).

### La ruta

- **Sesión y CSRF**, como «Salir»: la puerta exige sesión del esquema, `X-Antifaz-CSRF`, `Origin` y `Sec-Fetch-Site: same-origin` y JSON; la clave de la API no la abre. `GET` y `HEAD`: 405. Es `async def`. Cabeceras de la puerta y `no-store`; sin `Vary` ni `Content-Language`.
- **En este orden**:
  1. **Límite**: 30 intentos en cualquier ventana de 60 s por sesión (`web/try_limit.py`), con la huella de la sesión como clave (la calcula el servidor; el cliente no elige su cubo). Se toma **antes de leer el cuerpo y antes de cualquier `await`**: comprobar y contar es una sola llamada. Todo intento cuenta, bueno o malo. Al pasarse, 429 `too_many_tries` con `Retry-After`. La tabla está acotada (256 sesiones como mucho, y el almacén guarda 32) y la entrada de una sesión se borra cuando se cierra (`SessionStore.on_close`: salir, otro login, caducidad). **Por eso volver a entrar empieza el límite de cero**: quien tiene el token puede entrar otra vez; el límite frena un script con una sesión robada o una página que se vuelve loca, no al administrador (el login tiene su propio límite de 5 fallos por minuto).
  2. **Cuerpo**: un `Content-Length` declarado de más de 128 KiB es 413 sin leer nada; si no, se lee por trozos y se corta en cuanto pasa de 128 KiB (413), con o sin `Content-Length`, en 5 s como mucho (408 `body_timeout`). Nunca se lee como formulario. En 128 KiB cabe el texto más largo escrito entero con escapes `\uXXXX`.
  3. **Formato**: exactamente `{"text": str, "lang": un idioma cargado}`. Claves repetidas o de más, `NaN`/`Infinity`, surrogates sueltos, tipos que no son texto, BOM o UTF-8 roto: 400 `invalid_try_body` con un mensaje fijo, sin repetir nada de lo recibido. Un texto de más de **20 480 bytes en UTF-8** es 413 `text_too_large`.
  4. **El recorrido** (`web/try_text.py`, `run_try`): `antifaz.mask.mask()` con el detector y la política de la pasarela → `antifaz.guard.check()` sobre el texto enmascarado → respuesta simulada → `antifaz.restore.restore()`. Es el código del proxy, sin copia. Un detector que falla da `outcome: "blocked"`, `blocked_reason: "detector_failed"`; si la guardia aún ve un valor, `"egress_guard"`. Bloqueado es un 200 sin `sent` ni `reply`. Cualquier otro error es un 500 fijo y **una línea de log con el tipo del error, nunca su mensaje** (podría llevar el texto).
- **Ocupado (503, sin cola)**: si ya hay una prueba en marcha, la segunda recibe al momento 503 `try_busy` con `Retry-After: 1`; si el NER no puede atenderla sin hacer esperar al proxy (abajo), 503 `ner_busy` con `Retry-After: 1`; y un texto demasiado largo para el presupuesto del NER, 413 `text_too_long_for_ner`. Se eligió 503 y no un 200 «bloqueado» porque no es una decisión sobre el texto: es «ahora no, prueba en un segundo».
- **La ruta no tiene `response_model`**: la respuesta se valida una vez, dentro del `try` de la ruta (si falla, el 500 fijo), y se devuelve tal cual; FastAPI no la valida ni la serializa otra vez (un test lo fija).

### El proxy va primero

- **Hilos**: `api/app.py` da al panel un `try_runner` (nunca el detector, la política ni los `Settings`). Toma un limitador propio de **una** prueba con `acquire_nowait` (si está ocupado, `try_busy`; no hay cola) y **después** el limitador de enmascarado del proxy (`MASK_THREADS` = 8): el panel nunca ocupa más de uno de esos ocho hilos.
- **NER**: cada prueba usa su propio detector, `ner.for_try(5 s, max_chunks=2, batch_chunks=1)`, sobre el mismo modelo y los mismos procesos:
  - **sin la caché de spans del proxy**: una prueba ni la lee ni la escribe. Con caché compartida, un acierto tarda ~1 ms y delataría que ese texto pasó por el proxy hace poco (un oráculo de pertenencia); además la prueba expulsaría entradas del proxy y dejaría en memoria un resumen y posiciones del texto. Por lo mismo la respuesta **no lleva tiempos** (`elapsed_ms` se quitó);
  - **trabajo a la medida del plazo**: como mucho **2 ventanas** de 200 tokens (`TRY_NER_MAX_CHUNKS`; unas 350 palabras con el solape), **una por lote** (`TRY_NER_BATCH_CHUNKS`), con un plazo de **5 s** (`TRY_NER_SECONDS`). Un texto que necesita más ventanas recibe al momento 413 `text_too_long_for_ner` («demasiado largo para probar con el detector de nombres») **sin pedir nada a ningún proceso**. Sin el NER solo vale el límite de 20 480 bytes. Cómo se eligió: el benchmark midió GLiNER a p95 3,8 s por documento de MEDDOCAN (varias ventanas de 200 tokens cada uno) en la CPU de referencia; 1,5 s por ventana es una cota prudente, así que 2 ventanas son unos 3 s, por debajo de los 5 s. Es una cota derivada, no medida ventana a ventana. **Pendiente antes de la v0.2**: medir los 1,5 s por ventana con el modelo real en la máquina de destino (y antes de subir esos números);
  - **el proxy va primero** (`NerPool.try_predict`): una prueba recibe 503 `ner_busy` al momento si **alguna petición del proxy está esperando un proceso** (el pool las cuenta bajo su candado mientras esperan), si no hay ningún proceso libre, si el libre todavía está cargando (se comprueba sin esperar y se devuelve a la cola), si aún no ha hecho ninguna predicción (la primera de un modelo recién cargado puede ser lenta: siempre es del proxy) o durante el enfriamiento (abajo). Un proceso libre cuya carga falló se sustituye en ese momento (cuenta como fallo de una prueba: enfriamiento, nunca el cortacircuitos), para que ninguna petición del proxy tropiece con él. Esa comprobación se repite **antes de cada lote**, así que una petición del proxy que llega mientras corre una prueba espera **como mucho un lote pequeño (una ventana)**, nunca la prueba entera: la prueba se corta con `ner_busy`. Con un solo proceso, esperar cero es imposible sin matar el lote en marcha (y matar obliga a recargar el modelo), así que la cota es esa: una ventana, ≈1,5 s con la cota de arriba y nunca más que el plazo de 5 s. Una prueba nunca coge un proceso que el proxy está esperando;
  - **nunca cuenta para el cortacircuitos** del NER: una prueba que se cuelga o mata un proceso no suma un fallo (y una que va bien no pone la cuenta a cero). El proceso roto sí se mata y se sustituye;
  - **enfriamiento solo para las pruebas**: si una prueba llega a romper un proceso (plazo vencido o muerte), todas las pruebas con NER reciben `ner_busy` durante **60 s** (`DEFAULT_TRY_COOLDOWN_SECONDS`); el proxy no lo nota. Así una prueba no puede provocar recargas una tras otra (con el límite de 30 por minuto serían 30 recargas).
- **Límites que quedan**: un lote de prueba ya en marcha no se interrumpe (el proxy lo espera, una ventana); y si aun así una prueba rompe un proceso, el nuevo carga en segundo plano (con el modelo real, decenas de segundos) y mientras tanto el proxy bloquea las peticiones que no encuentren un proceso listo a tiempo, como con cualquier proceso sustituido; el enfriamiento impide que se repita durante 60 s. Solo puede provocarlo quien tiene sesión en el panel.

### Sin IA y sin camino hacia una IA

- La respuesta simulada (`simulate_reply(tokens, lang)`) recibe **solo** los tokens (`"ES_DNI_1"`), comprueba uno a uno que lo son y nunca ve el texto ni la tabla de marcadores. Frases fijas por idioma (español e inglés; inglés para otro idioma), nombra cada marcador una vez y como mucho 10 («…y N más»). Las frases viven en el módulo y no en los catálogos: los catálogos son los textos de la página y un test prohíbe claves que ninguna plantilla usa.
- `web/try_text.py` no importa `antifaz.providers`, `antifaz.api`, `httpx`, `socket` ni `ssl`, y no recibe ningún cliente. Un test recorre su **cierre de importaciones** dentro del proyecto (ningún módulo alcanzado importa esas piezas) y otro lo importa en un intérprete limpio y comprueba que no se cargan `httpx`, `antifaz.providers`, `antifaz.api` ni `antifaz.config`. `socket` y `ssl` no se pueden comprobar así: python-stdnum (los validadores) los importa para sus consultas en línea, que el detector nunca usa. Un test de integración arranca la app con un transporte de proveedor que falla en cuanto se usa: cero llamadas.

### La respuesta (esquema cerrado, `web/try_response.py`)

Pydantic estricto, `extra="forbid"`, congelado y con `hide_input_in_errors=True` (un error de validación no imprime los valores):

```json
{"outcome": "masked" | "blocked", "blocked_reason": null | "detector_failed" | "egress_guard",
 "length_utf16": 30,
 "entities": [{"type": "ES_DNI", "start": 10, "end": 19, "hidden": true}],
 "sent":  [{"text": "Mi DNI es "}, {"marker": "[[ES_DNI_1]]", "type": "ES_DNI"}],
 "reply": [{"text": "Respuesta simulada … "}, {"marker": "[[ES_DNI_1]]", "type": "ES_DNI", "value": "…"}],
 "counts": [{"type": "ES_DNI", "found": 1, "hidden": 1}],
 "policy_version": "builtin-1", "ner": "off", "names_checked": false}
```

- `sent` unido es exactamente el texto enmascarado que recibiría el proveedor: los tipos permitidos (el CIF de empresa) siguen en claro y un marcador escrito por el usuario sale escapado (`[[!ES_DNI_9]]`) como texto, nunca como marcador.
- `reply` unido (textos y valores) es exactamente `restore()` de la respuesta simulada entera. Los dos se cortan con el patrón del propio restaurador (`antifaz.restore.placeholder_parts`, junto a `placeholder_tokens`), así que no hay un segundo patrón que pueda discrepar.
- `policy_version` sigue la regla única de `antifaz.policy.VERSION_PATTERN` (1 a 64 caracteres de `A-Z a-z 0-9 . _ -`); `Policy` rechaza cualquier otra versión.
- El texto original **nunca** vuelve como campo: la página ya lo tiene. Tampoco hay tiempos.
- Para saber qué partes del texto se encontraron, `MaskResult` lleva ahora `found_spans` (`FoundSpan`: inicio, fin, tipo, oculto o permitido y token; **sin campo para el valor**), fuera del `repr`. Un test estático impide que lo lea nada fuera de `mask/` y `web/try_text.py` (ni evidencias, ni «Estado», ni el proxy, ni los logs) y otro, que ningún módulo use `dataclasses.asdict`/`astuple`.

### La unidad de las posiciones: UTF-16

Python cuenta un texto por puntos de código; JavaScript, por unidades UTF-16. Un emoji fuera del plano básico (👍, 𝐀) es un punto de código pero dos unidades, así que con posiciones de Python la página marcaría letras equivocadas a partir del primer emoji. Por eso la API **convierte en el servidor** y da `start`/`end` en unidades UTF-16, más `length_utf16`, la longitud UTF-16 del texto que procesó: la página la compara con su copia del texto antes de marcar nada (si no coincide, no marca). Un grupo que se ve como un solo carácter (una familia unida con ZWJ, una bandera, una letra con acentos combinados) son varias unidades; una entidad nunca empieza ni acaba dentro de un par sustituto porque las dos posiciones salen de puntos de código.

Pruebas: una tabla con emoji (astrales, secuencias ZWJ, banderas), acentos precompuestos y descompuestos, CRLF, texto RTL, controles bidi y valores pegados a todos ellos; para cada entidad, el trozo UTF-16 del texto original (simulado con `text.encode("utf-16-le")`) es exactamente el valor detectado. Y dos propiedades con Hypothesis: con cualquier texto alrededor (sin surrogates sueltos), el trozo UTF-16 de cada entidad es su trozo en puntos de código, y las posiciones son crecientes y acaban en la longitud UTF-16.

### Privacidad (la única excepción a la invariante 15)

- El valor solo vuelve en la respuesta a esa misma petición, con `no-store`. Nunca en los logs (todo en `DEBUG`, también los registradores de uvicorn; el log de acceso de uvicorn sigue apagado en `antifaz serve`), en los contadores, en «Estado», en las páginas, en la respuesta de otra sesión ni en ningún cuerpo de error (400, 413, 429, 503 y 500 forzado con un `restore` que falla con el centinela en el mensaje). Un detector que falla con el centinela en el mensaje da `blocked` sin el centinela. Mientras corre una prueba no se escribe nada en disco (el test vigila `open` para escribir, `os.open` con banderas de escritura y `tempfile`). Las evidencias aún no existen (punto 9); el test estático de `found_spans` ya las deja fuera.
- **Memoria, con honestidad**: el texto y los valores viven en cadenas de Python mientras dura la petición. Python no puede borrar una cadena: se libera cuando nadie la usa y el asignador puede reutilizar esa memoria más tarde, pero sus bytes pueden quedar ahí hasta entonces (en un volcado de memoria del proceso, o en el swap si el sistema la saca a disco). Con el NER encendido, el texto además viaja como JSON por una tubería a un proceso del NER: pasa por los búferes de la tubería y vive también en la memoria de ese proceso, con las mismas reglas. Una prueba no usa la caché de spans, así que no queda ningún resumen ni posición del texto después de responder. Nada guarda una referencia después de responder, escribe en disco ni lo registra.
- Las respuestas «ocupado» (`try_busy`, `ner_busy`) revelan que hay actividad, nunca su contenido; hace falta sesión en el panel para verlas y 11e enseñará la actividad de todos modos.
- El contador de «En directo» (11e) todavía no recibe nada de aquí.

## Panel: Prueba un texto (pantalla, 11d-b)

En pocas palabras: la pestaña «Prueba un texto» ya funciona. Escribes o pegas un texto con datos inventados (o usas el ejemplo), pulsas «Probar» (o Ctrl/⌘ + Enter) y ves tres columnas: tu texto con los datos encontrados resaltados, lo que recibiría la IA (con marcadores) y la respuesta simulada con tus datos de vuelta. Nunca se llama a ninguna IA y nada se guarda. Si el texto es demasiado largo para el detector de nombres, la página ofrece probarlo sin él y entonces lo dice bien claro: «Nombres no comprobados». Antes de que caduque la sesión por inactividad, un aviso ofrece «Seguir». Ver la nota del 2026-10-20 (11d-b) en [ADR-0018](adr/0018-el-panel-y-su-puerta.md).

### La API, con dos cambios

- **`"ner": false`**: el cuerpo puede ser `{"text", "lang"}` o `{"text", "lang", "ner"}` con `ner` un booleano JSON de verdad (`type(ner) is bool`). `0`, `"false"`, `null`, una clave repetida o una de más siguen siendo el 400 fijo. Con `false`, la prueba usa el escáner sin NER (`detect.scan.scan`): nunca el NER, nunca el detector del proxy (`app.state.detector`) y por tanto nunca su caché; al NER no se le pregunta nada.
- **`names_checked`** en la respuesta: verdadero solo si el NER de la prueba leyó el texto. Falso con el NER apagado en la pasarela, tras `"ner": false` o si el NER falló. El esquema rechaza `names_checked: true` con `ner: "off"`.
- **Condición: un fallo del NER es un error**: con el NER encendido y sin `"ner": false`, si el NER falla durante la prueba (proceso muerto, plazo vencido, cortacircuitos abierto u ocupado) la respuesta es el bloqueado `detector_failed` (nada enviado, sin entidades) o 503 `ner_busy`, **nunca** un resultado sin nombres. Solo un `"ner": false` explícito da un resultado sin el detector. Lo prueba `tests/integration/test_panel_try_ner_failures.py` con procesos reales y el backend falso.
- **El número de palabras sale de un solo sitio**: `TRY_NER_MAX_WORDS` (`api/app.py`) = `WINDOW_TOKENS + (TRY_NER_MAX_CHUNKS − 1) × (WINDOW_TOKENS − OVERLAP_TOKENS)` (hoy unas 350, derivadas de las ventanas; si cambian las ventanas o el presupuesto, cambia sola). Llega al panel en `PanelState.try_ner_words` (ninguno con el NER apagado) y la página lo pinta en un atributo y en el texto del aviso. Un test comprueba que un texto de exactamente ese número de tokens pasa y uno más da 413, y otro que el número no está escrito en ninguna plantilla, script ni catálogo. La cota de palabras de `TRY_NER_MAX_WORDS` y los 1,5 s por ventana **siguen pendientes de medir con el modelo real antes de la v0.2** (arriba).

### La pantalla

- **El campo** es un `textarea` **sin `name`**, con `autocomplete="off"`, `spellcheck="false"`, `autocapitalize="off"`, `autocorrect="off"` y `writingsuggestions="false"`. El formulario es `method="post"` a la ruta fija `/panel` sin consulta: además «Probar» viene desactivado y solo `try.js` lo activa, así que sin JavaScript no se envía nada; una nota `<noscript>` lo dice.
- **Contadores siempre a la vista**: «N de 20.480 bytes» (el número del servidor, con el formato del idioma) y, con el NER encendido, «Detector de nombres: ≈ N de M palabras» (M es `TRY_NER_MAX_WORDS`). La estimación imita el troceador (`detect/ner/chunker.py`: palabras de hasta 40 letras o cifras de cualquier escritura y cada signo suelto) sobre la vista normalizada, sin expresiones regulares: las marcas combinantes (Mn) y los caracteres de formato (Cf) se ignoran como hace la normalización, las marcas de espaciado (Mc, p. ej. en devanagari), U+FFFD y el uso privado cuentan como signos, y las letras sin mayúsculas (árabe, hebreo, tailandés, devanagari, CJK) como palabras (un test compara con el recuento del servidor en esas cuatro escrituras); por eso lleva «≈» y manda el servidor. Pasada la estimación solo cambia el color y una frase avisa; la oferta solo aparece cuando el servidor responde 413 `text_too_long_for_ner` (aviso con el botón, y el foco va al botón). Tras una prueba sin detector, el contador dice «Detector de nombres: no usado» hasta que cambia el texto. Con más bytes de la cuenta no se envía nada.
- **Resultado**: las marcas salen de las posiciones UTF-16 del servidor después de comprobar que `length_utf16` coincide con la longitud de la copia de la página (si no, aviso y ninguna marca). El tipo de cada marca se pinta con CSS (`attr(data-text-type)`), así que el texto de la columna es exactamente el escrito. **Nada se recorta**: cada columna tiene todo el texto y se desplaza por dentro (`max-height` + `overflow:auto`), y es una región con nombre y `tabindex=0` para que el teclado también la desplace. En pantallas estrechas se ve una columna a la vez («Recibe la IA» primero). Debajo, los datos encontrados por tipo y la línea «N datos ocultados · Política … · Nada ha salido de tu red».
- **«Nombres no comprobados»**: si `names_checked` es falso, un aviso muy visible encima de las columnas y la **misma frase** (la misma clave del catálogo) en la línea de abajo. Con el NER apagado en toda la pasarela, el aviso lleva su propio texto.
- **Bloqueado**: la nota del prototipo en la segunda columna con el motivo (`detector_failed` o `egress_guard`) y, en la tercera, «No hay respuesta». Un bloqueado tras `"ner": false` (no se envió nada) deja «Nombres no comprobados» solo en la línea de abajo, sin el aviso grande: el bloqueado ya dice más.
- **Un intento fallido borra el resultado anterior** (413, cualquier error o un error de la propia página): era de otro texto. «Nombres no comprobados» en la línea de abajo va en el color de aviso de su recuadro.
- **Respuestas viejas**: cada envío lleva su `AbortController` y un número de secuencia. Borrar (salir, caducar, 401) aborta el envío en marcha y sube la secuencia; escribir en el campo también la sube. Una respuesta de otra secuencia o que llega tras borrar se descarta: nunca vuelve a llenar la página, y «no usado» solo se pone si el campo sigue siendo el texto probado. Tras salir no se envía nada más.
- **El foco**: al pulsar «Probar sin el detector de nombres», el foco pasa al campo antes de ocultar el aviso (nunca se queda en el `body`).
- **Se nota que hay más**: las columnas tienen la barra de desplazamiento fina y siempre visible (`scrollbar-gutter: stable`) y sombras de desplazamiento solo con CSS (`background-attachment: local` y `scroll`): la sombra de abajo está mientras queda texto y desaparece al final; no se mueve nada sola.
- **Sin JavaScript no se envía nada**: «Probar» y «Usar el ejemplo» vienen `disabled` en el HTML y `try.js` los activa. Pulsar sin script no manda ni un formulario vacío (test en los tres navegadores).
- **Errores**: un mensaje fijo por caso (400, 403, 408, 413, 429 con `Retry-After`, 503 `try_busy`, 503 `ner_busy`, 500, sin red). Ocupado es un mensaje al momento: nunca se reintenta solo. Un texto con un carácter roto (`isWellFormed()` falso) da el mensaje del 400 sin enviar nada.
- **La región en vivo** (`role=status`) solo recibe recuentos («4 datos ocultados»), nunca un valor.
- **Ejemplos**: en los catálogos, solo con datos que se encuentran sin el NER (DNI, email, IBAN y teléfono; el inglés con un teléfono `+34`). Un test pasa cada ejemplo por el escáner sin NER y exige exactamente esos cuatro tipos y ningún nombre.
- **Fuera del prototipo** (dependen de trabajo futuro): selector de política, `rrhh`, tiempos, modelo, el 504, la cadena rota, la animación y la píldora de la cabecera. En el móvil, la barra inferior real del panel.

### La vida del texto

- Se queda al cambiar de pestaña. Se borra al salir, al caducar la sesión y al cerrar o recargar la página (`pagehide`; el campo sin `name` y con `autocomplete="off"` evita que el navegador lo recupere, también en Firefox, que restaura formularios al recargar). Nada va a `localStorage`, `sessionStorage`, IndexedDB, la Cache API ni a una cookie (tests en los tres navegadores).
- **Lo que no se puede impedir, con honestidad**: una extensión del navegador con permiso para leer la página (correctores como Grammarly, traductores, gestores de contraseñas) puede leer lo que escribes; el panel no puede evitarlo. Usa datos inventados.

### La sesión (`static/session.js`)

- **`SessionStore.seconds_left(clave)`**: (segundos hasta el límite de inactividad, segundos hasta las 8 horas) con el reloj del almacén y **sin contar un uso**. `GET /panel` los pinta en dos `meta` (`antifaz-session-idle`, ya recortado por el final, y `antifaz-session-max`).
- **`POST /panel/api/session`**: sesión + CSRF por la puerta, esquema cerrado `{"idle_seconds", "max_seconds"}`, `no-store`, el cuerpo no se lee. La puerta cuenta la petición como un uso (como cualquier petición del panel), así que **solo alarga la inactividad y nunca pasa de las 8 horas desde el login**: cerca del final `idle_seconds` queda recortado por `max_seconds`, pasado el final es 401 y llamarla nunca mueve el final (tests con un reloj falso). Otra web u otro puerto de localhost no llega (la puerta, paso 2b).
- **El único temporizador**: en todo el JavaScript estático hay exactamente un `setTimeout(`, en `session.js`, y ningún `setInterval` ni `requestAnimationFrame` (test estático). Programa solo el próximo momento (el aviso o la caducidad) y lo recalcula con `Date.now()` cada vez.
- **El aviso**, unos 2 minutos antes de la caducidad por inactividad: «Tu sesión está a punto de caducar» con la hora y «Seguir». Está **en el flujo**, arriba del contenido (no tapa nada), es un `role=status` educado que existe siempre (vacío no ocupa sitio, así que el lector de pantalla oye cuando se llena) y **nunca mueve el foco**. Solo al pulsar «Seguir» se pregunta al servidor; nunca hay llamadas periódicas y el aviso no alarga nada por sí solo. Cerca del final absoluto no hay «Seguir»: «La sesión dura como mucho N horas y termina a las …», con N calculado de `MAX_AGE_SECONDS` al pintar la página. La página da por caducada la sesión **5 s antes** que el servidor (`SAFETY_MS`), para no enseñar nunca una sesión ya cerrada allí.
- **Al caducar**: se borran el texto y los resultados (evento `antifaz:wipe`, **antes** de que la página se vaya; también al salir y con un 401) y se vuelve al login. Un 401 de cualquier llamada del panel hace lo mismo.
- **Cada respuesta del panel que fue un uso** (las que la puerta atendió: 2xx y 4xx salvo 401 y 403; nunca un 5xx) mueve el límite de inactividad en la página: `panel.js` y `try.js` lanzan el evento `antifaz:activity`. Los tres scripts son IIFE independientes que hablan solo con eventos del DOM.
- **Temporizadores frenados**: los navegadores retrasan los temporizadores de las pestañas en segundo plano. Por eso, al volver a ser visible (`visibilitychange`), `session.js` lo recalcula todo: si la pestaña estuvo oculta pasada la caducidad, caduca al momento. El servidor manda siempre: aunque la página llegara tarde, la sesión ya está cerrada allí.

## Panel: En directo (motor, 11e-1)

En pocas palabras: la pasarela ya lleva la cuenta de lo que hace, **solo con tipos y cantidades**: cada petición del proxy, de «Prueba un texto» y de `/antifaz/scan` deja un evento como «OpenAI · Claude Code · ocultados 2 DNI y 1 email · 15:42», y el panel lo puede recibir al momento por `GET /panel/api/live` (SSE). Nada de eso sale de la memoria del proceso: ni a los logs ni al disco. Este PR es solo el motor; la pantalla es la de 11e-2 (abajo). Ver la nota del 2026-10-20 (11e-1) en [ADR-0018](adr/0018-el-panel-y-su-puerta.md).

### El evento (`antifaz/live.py`)

- **Solo enums, enteros y la hora**: `origin` (`openai_chat`, `anthropic_messages`, `count_tokens`, `scan`, `try`), `client`, `outcome` (`masked`, `no_data`, `blocked`, `upstream_error`), `reason` (`attachment`, `detector_failed`, `egress_guard`, `unmaskable_field`, `too_deep`, `none`), `provider` (`openai`, `anthropic`, `none`), `at` y `types` (tipo → cuántos valores **distintos** se ocultaron). El constructor rechaza cualquier otra cosa (una cadena en vez del enum, un booleano, un 0). No hay ningún campo donde quepa un texto.
- **El cliente sale de una lista cerrada** por el principio exacto del `User-Agent` (solo se leen los primeros 32 caracteres): `claude-cli/` → Claude Code, `codex_cli_rs/` → Codex, `open-webui/` → Open WebUI, `OpenAI/Python` y `Anthropic/Python` → los SDK, `curl/` → curl; cualquier otro, o la cabecera repetida, es «otro». **El `User-Agent` nunca se guarda.** Con honestidad: los prefijos no se han comprobado contra cada cliente real (Open WebUI sobre todo); uno cuyo `User-Agent` no empiece así sale como «otro». La lista solo nombra lo que reconoce.
- **Los tipos permitidos no cuentan**: `types` sale de `Vault.type_counts()` (nuevo: valores distintos por tipo, sin valores ni marcadores), y la tabla solo guarda lo que la política oculta; un CIF de empresa no aparece. En `/antifaz/scan`, lo mismo con los spans que la política ocultaría; en «Prueba un texto», con los marcadores distintos que se enviarían.
- **La hora va redondeada al minuto** (decisión de Miquel): `at` es la hora Unix bajada al minuto.
- **Un bloqueo no lleva tipos** (no se envió nada); un fallo del proveedor (`upstream_error`: su 4xx/5xx, plazo, conexión perdida, respuesta que no es JSON, redirección) sí los lleva, porque ya se ocultaron y enviaron.

### El contador (`MemoryLiveFeed`)

- **Los últimos 20 eventos**, los totales de valores ocultados por tipo y de resultados, y el tiempo desde que arrancó. **«Prueba un texto» y `/antifaz/scan` salen en el directo pero no suman a los totales** («datos ocultados» son los que iban a un proveedor); van aparte (desde 11e-2, `tries` y `scans`; antes, un solo `checks`). Desde 11e-2 también se cuentan los bloqueos del proxy por motivo (`blocks`).
- **Por proceso**: el resumen dice cuántos procesos sirven la pasarela (`processes`). `antifaz serve` arranca siempre uno (`SERVE_WORKERS`, igual a `cli/serve.py` con test). Si `WEB_CONCURRENCY` es un entero de 1 o más, se toma ese número (uvicorn lo usa como número de procesos cuando no se le da `--workers`), y con más de uno la pantalla dirá «datos de este proceso». Con honestidad: `antifaz serve` pasa siempre `workers=1` y uvicorn ignora entonces `WEB_CONCURRENCY`, así que si alguien la pone, el panel avisa sin hacer falta (el lado seguro); y un uvicorn arrancado a mano con `--workers N` sin `WEB_CONCURRENCY` no se distingue de un solo proceso.
- **Sin el panel** (`ANTIFAZ_ADMIN_TOKEN` vacío) el contador es un `NullLiveFeed`: no guarda nada.
- Está detrás de una interfaz (`LiveFeed`: `record`, `snapshot`, `subscribe`) que el registro de evidencias (ítem 9) podrá sustituir.

### Dónde se registra: en un solo sitio

- `api/live_record.py` (`LiveRecorder`, middleware ASGI **dentro** de la puerta: lo que la puerta rechaza nunca llega) pone una nota en `scope["state"]` para las cinco rutas, por pareja exacta (ruta, método). La ruta la marca después de enmascarar (`mark_masked`) o al pasar un error del proveedor (`mark_upstream_error`); los manejadores de errores marcan el bloqueo con su motivo (por la clase del error) y los errores del proveedor. **Al acabar la petición** la nota se convierte en un evento y se registra **una vez**. Un stream se registra cuando termina.
- Sin decisión (sin clave, JSON roto, cuerpo enorme, 413/429 de la prueba) no se registra nada; tras un error inesperado (500), tampoco.
- **El contador nunca rompe el proxy**: crear la nota, contar los tipos (`Vault.type_counts` y los del escaneo se calculan dentro de esa protección), marcarla y registrarla van envueltos; un fallo deja una línea de log con el tipo del error y la respuesta sale igual (test con un contador que lanza). Registrar es código plano: sin `await`, sin E/S y con memoria acotada.

### Solo en memoria (condición 3 de Miquel)

- **Los últimos 20 eventos, y cualquier evento, nunca van a un log ni al disco.** `live.py` no tiene E/S de archivos ni registra eventos: solo el tipo de un error (test estático sobre el código). Un test de red team pasa el DNI centinela por todo el recorrido con los logs en `DEBUG` y con `open` y la escritura de archivos parcheados para fallar: ni el centinela ni ninguna palabra de un evento (tipos, orígenes, resultados, clientes) aparece en los logs, y no se abre ningún archivo.
- Como todo lo del proceso, vive en su memoria mientras dura: puede acabar en un volcado o en el swap. Al reiniciar, se pierde.

### `GET /panel/api/live` (SSE)

- **Sesión por la puerta**, como `GET /panel/api/status`: la clave de la API no la abre, la cookie del otro esquema tampoco, y un `Sec-Fetch-Site` que no sea `same-origin` es 403 antes de mirar la sesión. Pide `Accept: text/event-stream` (si no, 406 `not_acceptable`; `*/*` solo no basta: `EventSource` lo pide por su nombre). Solo `GET`: los demás métodos y `HEAD`, 405.
- **200 `text/event-stream`** con las cabeceras de la puerta, `Cache-Control: no-store` y `X-Accel-Buffering: no` (para que un nginx delante no lo acumule).
- **Eventos**, uno por trama (`event:` + una línea `data:` de JSON): `snapshot` al conectar, `request` por cada evento y `end` con su motivo (`logout`, `expired`, `replaced`, `busy`, `max_age`, `shutdown`), y la conexión se cierra. **Nunca `retry:`** (el navegador no reconecta solo) ni `id:`. Esquema cerrado (`web/live_response.py`): **cada hoja del JSON es el valor de un enum o un entero** (test); los tipos y resultados van como listas `{"type", "count"}`, nunca como claves libres.
- **Mirar no es usar la sesión** (decisión de Miquel): `GET /panel/api/live` (y su `HEAD`, que es 405) es la única ruta de `door.NOT_A_USE`, así que conectar y reconectar nunca refrescan el último uso (test con reloj falso). Dejar «En directo» abierto no alarga la sesión.
- **Cuándo termina**: el plazo de cada conexión es el menor de **30 minutos** y **lo que le queda a la sesión** (`seconds_left()`, sin contar un uso). Al llegar al de la sesión se vuelve a mirar: si «Seguir» la alargó, la conexión sigue con el plazo nuevo; si caducó, `end: expired`. A los 30 minutos, `end: max_age`. **El cierre de sesión la corta en el momento** (`sessions.watch`), igual que un login nuevo con la cookie vieja (`replaced`) o una sesión expulsada porque el almacén estaba lleno (también `replaced`).
- **Límites**: como mucho **5 conexiones por proceso y 2 por sesión**. Pasado eso, 200 con un solo `end: busy` y se cierra. `HEAD` (405) tampoco cuenta como un uso de la sesión.
- **Cola de 32 por suscriptor**: si el navegador va lento y se llena, se vacía y llega un `snapshot` nuevo en vez de lo perdido (memoria acotada).
- **Latido**: un comentario (`:`) cada 25 s, solo mientras hay una conexión abierta, para que un proxy no corte una conexión callada.
- **Sin conexiones no hay nada**: ni tareas ni temporizadores (test sobre el bucle de eventos). Con una abierta, un solo `asyncio.timeout` alrededor de su espera.
- **Al apagar, dicho claro**: con `antifaz serve` (uvicorn), uvicorn espera primero a que se cierren las conexiones abiertas, hasta `timeout_graceful_shutdown` (20 s), y **después las corta cancelándolas**; solo entonces avisa al `lifespan`. Así que con un navegador mirando, apagar tarda esos 20 s y el navegador ve la conexión cortada, **no** un `end: shutdown`. El `end: shutdown` (`close_all()` en el `lifespan`) solo llega a los clientes cuando el `lifespan` termina antes que las conexiones, como en los tests en proceso.
- **Ningún sitio queda ocupado**: una conexión ya cortada (cierre de sesión, caducidad, apagado) no cuenta para los límites aunque su último mensaje siga esperando; abrir el stream y suscribirse van dentro del `try` que libera el sitio; la respuesta (`LiveResponse`) cierra los eventos con `contextlib.aclosing` aunque la cancelen en un `yield`; y **cada envío tiene un plazo de 30 s**: un cliente que deja de leer se cae y su conexión se cierra. Al dejarla caer, uvicorn escribe en su log una línea fija («ASGI callable returned without completing response.»); no lleva ningún dato de la petición ni del evento. Para que ese plazo sirva de verdad, el middleware del id de petición pasa a ser ASGI puro (antes era `BaseHTTPMiddleware`, que copiaba cada respuesta por una cola en memoria y dejaba esa tarea esperando para siempre a un cliente atascado).
- **Un límite de disponibilidad, con honestidad**: los 5 sitios son para todo el proceso y solo hace falta el token de administrador para ocuparlos; varias sesiones abiertas (2 conexiones cada una) pueden dejar a otra sesión sin «En directo» (`end: busy`) mientras sigan mirando. Es una molestia, no una fuga: quien puede hacerlo ya tiene el token.

### Lo que la hora puede delatar (con honestidad)

El evento no lleva ningún valor, pero **llega al panel en el momento**: quien mira «En directo» y sabe cuándo alguien mandó una petición puede atar ese evento a esa persona (por ejemplo, «a las 15:42 Ana usó Claude Code y se ocultaron 2 DNI»). Redondear `at` al minuto no lo evita en directo; lo que reduce es la precisión de lo que queda en el resumen (los últimos 20) para quien se conecta después. Por eso «En directo» solo lo ve quien tiene el token de administrador, nunca enseña valores ni el `User-Agent`, y todo se pierde al reiniciar.

### Lo que se ve

- **La píldora** dice solo la conexión (cambio de Miquel: «desde el arranque» va con las cifras): «Conectando…» (punto ámbar), «Conectado» (verde) o «Desconectado» (rojo), con su palabra siempre. Es un `role=status`. Con «Desconectado» aparece «Volver a conectar».
- **Las cifras** (ocultas hasta el primer `snapshot`), en una tarjeta con cuatro partes:
  - «Datos ocultados desde el arranque»: el total y una barra por tipo (de mayor a menor; la barra se dibuja con `data-v` de 0 a 20, veinteavos del mayor, y una regla CSS por paso: nada de estilos en línea, que la CSP no deja).
  - «Bloqueos»: el total y sus motivos («1 adjunto · 1 JSON demasiado anidado»).
  - «Peticiones a la IA»: el total, sus partes («2 con datos · 2 sin datos · 2 bloqueadas · 1 error del proveedor»), la regla de qué cuenta y aparte las pruebas y los escaneos («Aparte: 1 prueba y 1 escaneo, que no suman.»).
  - «Cadena de evidencias»: «Llega con el registro de evidencias (punto 9).».
  - En la tarjeta de los datos ocultados, como en el diseño aprobado: «En este proceso, en marcha hace … Cada proceso cuenta lo suyo y empieza de cero al reiniciar.».
- **«Últimas peticiones»**, las más nuevas arriba (un `role=log` educado que anuncia solo lo nuevo): la hora al minuto, el cliente (lista cerrada, «Otro» si no se reconoce; «Prueba un texto» para las pruebas), el proveedor si lo hay, los tipos («DNI ×2 · Email ×1» o «sin datos»; en un bloqueo, el motivo) y una etiqueta: «Ocultados N», «Bloqueado», «Sin datos», «Error del proveedor», o «Prueba» / «Escaneo» con «no suma al total». En el móvil, cada fila en dos líneas con la hora y la etiqueta a la derecha.
- **Estados**: vacío (ceros y «Aún no ha pasado ninguna petición desde el arranque…»); desconectado (aviso «Se ha perdido la conexión», las cifras de antes atenuadas y «Volver a conectar»; si nunca llegó un `snapshot`, el aviso no habla de «las cifras de antes»); demasiadas vistas abiertas (`end: busy`, que sale de cualquiera de los dos límites: «… como mucho 2 por sesión y 5 en total…», sin cifras; los dos números son los límites que aplica de verdad esta pasarela (`per_session` y `max_streams` de su `LiveStreams`, por defecto `MAX_PER_SESSION` y `MAX_STREAMS` de `web/live_limits.py`), pintados en la página por la ruta, nunca escritos en el catálogo ni en el script); cerrada a los 30 minutos (`end: max_age`, con las cifras de entonces); varios procesos (aviso azul «Antifaz corre con N procesos: estos son los datos de este proceso», condición de Miquel). Un `end` de `logout`, `expired` o `replaced` sale del panel como una sesión caducada (borra la vista y `session.js` vuelve al login).
- Los números, con el formato del idioma de la página (`toLocaleString`); la hora con `Intl.DateTimeFormat`.

### Qué cuenta «Peticiones a la IA» (la regla, condición de Miquel)

- **Peticiones a la IA** = solo las del proxy (Chat Completions, Messages y `count_tokens`) = **con datos + sin datos + bloqueadas + error del proveedor**. Las bloqueadas **sí** cuentan (llegaron a Antifaz para ir a la IA y no salieron).
- **Bloqueos** = las bloqueadas del proxy = **la suma de sus motivos**.
- **Datos ocultados** = **la suma de las barras** (valores distintos por petición, como en 11e-1; un bloqueo no lleva ninguno).
- **«Prueba un texto» y `/antifaz/scan` no suman** a ninguno de los tres (como los datos ocultados): salen en «Últimas peticiones» y en la línea «Aparte».
- Para que esto se pueda enseñar, el `snapshot` lleva ahora `blocks` (motivo → cuántas, solo los que tienen alguna) y `tries` y `scans` por separado (antes, un solo `checks`). Cada hoja sigue siendo un enum o un entero.
- Lo comprueban un test de propiedad sobre el contador (`tests/property/test_live_totals_property.py`: para cualquier serie de eventos, cada total es la suma de sus partes) y uno de navegador que lee los números de la pantalla, en los dos idiomas, al llegar uno a uno y otra vez tras un `snapshot` nuevo (`live.js` suma cada `request` con la misma regla).

### `static/live.js`

- **Independiente**, como los otros tres: habla con ellos solo por eventos del DOM. **No pide nada con `fetch`** y es el único script con un `EventSource`, siempre sobre la cadena literal `"/panel/api/live"` (test estático). **No añade temporizadores** (sigue habiendo un solo `setTimeout`, el de `session.js`), ni `setInterval`, ni `requestAnimationFrame`; nada de almacenamiento ni de `innerHTML`: solo `textContent` y `createElement`.
- **Cuándo se conecta**: solo con la pestaña elegida **y** la página visible (un `MutationObserver` mira el `hidden` de la vista). **Cuándo se desconecta**: al cambiar de pestaña, al ocultarse la página (`visibilitychange`), en `pagehide`, con `antifaz:wipe` (salir o caducar) y ante **cualquier** `error`, con `close()`: así el navegador nunca reconecta por su cuenta (el servidor no manda `retry:`). Vuelve a conectar solo con «Volver a conectar» o al volver a ser visible con la pestaña elegida (o al volver a entrar en ella).
- **«Volver a conectar» mira antes la sesión** (cambio de Miquel): `live.js` no pide nada; dice `antifaz:live-check` y `session.js` lo comprueba con su misma petición de siempre, `POST /panel/api/session`. Con un 401 sigue su camino de caducidad (`antifaz:wipe` y al login); con un 200 dice `antifaz:live-ok` y solo entonces `live.js` abre el stream; con un error de red o cualquier otra respuesta dice `antifaz:live-failed` y la vista sigue «Desconectado» con el botón. **Ese clic alarga la inactividad de la sesión**, como «Seguir»: es un clic de la persona, no algo que haga la página sola. Solo pasa al pulsar el botón; volver a la página (o a la pestaña) reconecta sin preguntar, como antes. Sin temporizadores nuevos: `session.js` sigue teniendo el único `setTimeout`, y cada script pide solo su URL.
- **Mirar no es usar**: `live.js` nunca dispara `antifaz:activity`, así que no mueve el aviso de caducidad (y el servidor tampoco cuenta la conexión como un uso, `NOT_A_USE`).
- **Solo el esquema cerrado**: cada valor se compara con su lista; uno desconocido sale con una etiqueta genérica («Otro», «Otro proveedor», «Otro dato», «Otro motivo», «Desconocido»), nunca tal cual; una cantidad que no es un entero válido no cuenta. Los textos salen de `<template id="live-messages">` (catálogo del idioma) y los nombres de tipo, de la plantilla de «Prueba un texto».
- **«Salir» corta el directo antes de preguntar**: el servidor manda `end: logout` antes de la respuesta del cierre de sesión, y si llegaba primero, `live.js` mandaba la página al login mientras el `POST /panel/logout` seguía pendiente (Firefox lo cancelaba). Ahora `panel.js` dice `antifaz:logout` justo antes de su `fetch` y `live.js` cierra el stream en ese momento (si el cierre de sesión falla, la vista queda «Desconectado» con «Volver a conectar»). Además, `panel.js` ya no navega si otro script ya ha dicho `antifaz:wipe`: la página sale una sola vez.

### Limitaciones (con honestidad)

- **`EventSource` no ve el código de la respuesta**: un 401 (la sesión ya no existe en el servidor), un 406 o un corte se ven igual, como un `error`. Así que tras un reinicio de la pasarela (las sesiones viven en memoria) o un cierre de sesión en otra pestaña que no llegó como `end` (por ejemplo, con la conexión ya cortada), la reconexión **automática** (al volver a la página o a la pestaña) vuelve a fallar y la vista dice «Se ha perdido la conexión», **hasta que** `session.js` llega a su plazo, otra petición del panel recibe un 401 o se pulsa «Volver a conectar», que sí comprueba la sesión (arriba) y lleva al login. `live.js` sigue sin hacer `fetch`.
- Una hora fuera de lo que una fecha de JavaScript puede guardar (`at` mayor que 8,64 × 10¹² s) deja la hora vacía; nunca rompe la vista.

## Cómo se prueba la velocidad

Un test que dice «esto tarda menos de 2 segundos» de reloj falla en un portátil cargado o con la cobertura activada, y en cambio deja pasar una expresión regular cuadrática en una máquina rápida (ya pasó en la CI: 5,17 s contra un límite de 5). Por eso los tests de velocidad miden **tiempo de CPU** del proceso (`time.process_time`), no tiempo de reloj: esperar a que otro programa suelte el procesador no cuenta. Incluye los hilos del proceso (el TestClient atiende la petición en otro hilo) pero no los procesos hijos, y por eso el pool del NER se prueba de otra forma. Las ayudas están en `tests/timing.py`.

- **Lo que se cuelga con textos maliciosos (ADR-0008)** se mide por su **forma** (`assert_linear`): el mismo trabajo con un texto de tamaño n y con uno 4 veces mayor. Si el coste es lineal, el grande tarda unas 4 veces más; si es cuadrático, 16; si hay retroceso catastrófico, muchísimo más. El test exige que la proporción quede por debajo de 8. Cada ejecución recibe una entrada nueva (algo con estado, como una tabla que se llena, nunca se mide «en caliente»); n se ajusta solo (se dobla hasta que la mejor de 3 ejecuciones dura al menos 0,1 s, para que el redondeo del reloj de Windows no cuente, con un máximo de 20 veces) y el tamaño grande es al menos el que usaba el test antiguo. Sus propios tests comprueban, con canarios reales, que una expresión que reintenta desde cada posición, un retroceso catastrófico y un bucle cuadrático fallan.
- **Lo lento pero lineal** (un camino 10 veces más lento) no cambia la forma, así que los tests de DoS de tamaño fijo tienen además un **presupuesto de CPU** (`cpu_budget`). El tiempo de CPU no cuenta la espera, pero tampoco es inmune a la carga: con todos los núcleos ocupados el procesador baja de frecuencia y comparte núcleos, y el mismo trabajo gastó el doble de CPU. Los límites dejan al menos 2,4 veces el peor caso medido (con cobertura y 15 procesos quemando CPU, en un PC de sobremesa, el 2026-10-18).

  | Test | CPU con cobertura (libre / cargada) | Límite de CPU | Antes (reloj) |
  |---|---|---|---|
  | Cuerpo de 4 MiB por el proxy | 3,2 / 6,2 s | 15 s | 30 s |
  | Historial de 3.000 turnos | 1,6 / 3,1 s | 10 s | 30 s |
  | 5.000 DNI distintos en `mask()` | 0,22 / 0,45 s | 2 s | 20 s |
  | Guardia con 1 MB y 200 valores | 0,09 / 0,17 s | 1 s | 2 s |

  Con el escáner 10 veces más lento, el cuerpo de 4 MiB gasta unos 30 s de CPU: pasaba el límite antiguo de 30 s y falla el de 15. Los otros tres no lo pillan (el escáner es solo parte de su coste); son una red contra algo mucho más lento.
- **Los límites de tiempo del NER** se prueban con **hechos**: el error exacto (`DetectorFailed`), cuántas veces el pool dejó cada línea en el log («went past the time limit», «died or broke the protocol», «NER circuit open»), qué procesos siguen vivos (comparados como objetos, nunca por su número, que el sistema puede reutilizar), si una petición llegó o no a un proceso (con el circuito abierto, ni lo pide ni lo espera) y qué plazo recibió cada llamada (en un texto largo, el mismo para toda la petición). Si el vigilante mata el proceso, el log dice «went past the time limit» aunque la tubería rota llegue antes que el final de la espera de la respuesta (un test adelanta el vigilante para que ocurra siempre); «died or broke the protocol» queda para una tubería rota sin que el vigilante haya actuado y para una respuesta completa que no es JSON, haya actuado o no. Si el vigilante actúa justo después de leer la respuesta entera (`cancel()` no detiene uno que ya corre), el pool lo espera con `join()`, la petición conserva la respuesta y el proceso muerto se sustituye en vez de volver a la cola, sin contar como fallo para el circuito (un test hace que el vigilante actúe al cancelarlo). Antes de pedir algo a un proceso nuevo se espera a que esté listo (`when_ready` en `tests/nerfakes.py`): arrancar un proceso en Windows con la máquina cargada puede tardar varios segundos.

**Márgenes de reloj que quedan**, todos de la forma «el plazo más un margen» o «muy por debajo de lo que tardaría el fallo»:

| Test | Margen | Por qué |
|---|---|---|
| Proceso colgado (`test_pool.py`) | plazo (2 s) + 3 s | matar y sustituir el proceso tardó menos de 0,2 s con 47 procesos quemando CPU; un cierre lento o un vigilante tardío tardan varios segundos más |
| Proceso cargándose | plazo (0,5 s) + 3 s | la carga dura 6 s |
| Texto con muchas ventanas (`redteam/test_ner.py`) | plazo + 3 s (desde el plazo) | con un plazo por llamada tardaría más de 6 s (600 ventanas; cada llamada de 16, 0,16 s). La carga solo decide dónde se corta: un proceso matado en el plazo (una línea «went past the time limit») o el motor que ya no hace la llamada siguiente (ninguna); nunca una muerte |
| Cerrar durante una llamada | 30 s | el falso dormiría 60 s y el plazo es de 60 s |
| `doctor --timeout 1` | 6 s (antes 4) | el servidor de prueba gotea 10 s; con un plazo por lectura no acabaría antes. Se subió de 4 a 6 para dejar sitio a una máquina cargada sin acercarse a los 10 |
| Ejecuciones de `assert_linear` y `cpu_budget` | 120 s de reloj | guarda contra cuelgues |

La guarda de 120 s se comprueba cuando la ejecución termina: si acaba pero tardó más, falla con un mensaje claro. No puede parar algo que no termina nunca; para eso haría falta un tiempo máximo por test (por ejemplo pytest-timeout, que el proyecto no usa).

Lo que no cubre: un coste cuadrático muy barato por paso, que en el tamaño probado sume menos del doble del trabajo lineal, no llega a la proporción de 8 (y, si es pequeño, tampoco al presupuesto). Los fallos reales del ADR-0008 (reintentar una tira larga desde cada posición) cuestan órdenes de magnitud más y se ven enseguida.

## Telemetría

Antifaz no envía nada a ningún sitio salvo a los proveedores configurados en `.env` (`ANTIFAZ_OPENAI_BASE_URL` y `ANTIFAZ_ANTHROPIC_BASE_URL`). La única conexión de salida de la pasarela es su cliente HTTP hacia esas URL; no hay analítica, ni comprobación de versiones, ni informes de errores. El healthcheck de Docker solo llama a la propia pasarela en `127.0.0.1`. El NER opcional funciona sin red: los procesos del pool ponen Hugging Face en modo offline y con su telemetría apagada (`HF_HUB_OFFLINE`, `TRANSFORMERS_OFFLINE`, `HF_HUB_DISABLE_TELEMETRY`), y el modelo solo se descarga con `make ner-model`. FastAPI trae la API de OpenTelemetry (sin SDK ni exportadores) para su telemetría nativa; Antifaz la apaga de forma explícita en `create_app` (`telemetry` con trazas, métricas, logs, `operation_spans` y `auto_configure` a `False`, y `exclude` que salta todas las peticiones), así que ni `FASTAPI_OTEL_AUTO_CONFIGURE` ni un `traceparent` entrante hacen nada, y lo prueba `tests/integration/test_fastapi_telemetry_off.py`. Esa API sí lee dos variables al importarse FastAPI: un `OTEL_PROPAGATORS` que no existe hace que `import fastapi` falle y la pasarela no arranque (falla cerrada; comprobado con 0.143.0 y opentelemetry-api 1.45.1), y un `OTEL_PYTHON_CONTEXT` que no existe solo deja una traza en el log y vuelve al contexto por defecto; el entorno del contenedor se da por fiable. Si algún día Antifaz envía algo más, será opcional y con la tabla de campos en `SECURITY.md`.

## Limitaciones

- Docker: la imagen solo se ha probado y se publica en `linux/amd64` (en local y en la CI), no en ARM.
- Docker: la imagen es distroless (Debian 13) y aun así lleva paquetes de sistema con vulnerabilidades altas que Debian no arregla (5 CVE el 2026-10-16: zlib, glibc y las librerías de GCC). La CI solo falla con las que tienen arreglo; el informe completo queda como artefacto. Sin shell, depurar dentro del contenedor pide un contenedor auxiliar (ver «Problemas frecuentes» en instalacion.md). Los parches de Debian solo llegan con un digest nuevo de la base.
- Docker: la imagen no trae `ctypes`, `sqlite3`, `lzma`, `bz2`, `readline`, `curses`, `dbm.gnu`/`dbm.ndbm` ni el `_uuid` compilado (`uuid` sigue funcionando sin él; ADR-0019). Si una dependencia futura los necesita, el test de importación de `make e2e` falla y hay que volver a traer el módulo con su librería y su registro de dpkg.
- `POST /antifaz/scan` devuelve posiciones en caracteres Unicode (índices de Python), no en unidades UTF-16 como JavaScript ni en bytes.
- `GET /v1/models` elige el proveedor por la cabecera `anthropic-version`: un cliente de OpenAI que la mande por error recibe la lista de Anthropic.
- El proxy habla OpenAI Chat y Anthropic Messages (con y sin streaming). Hay una prueba real con OpenAI y sus respuestas grabadas (2026-09-30); la prueba real con Claude Code y Anthropic está pendiente (sin crédito de Anthropic), y sus tests de contrato usan respuestas escritas a mano.
- En streaming, los argumentos de las herramientas llegan **de golpe al final de su bloque** (o de la `choice` en OpenAI), no poco a poco: así siempre son JSON válido.
- En streaming, un marcador de esta petición con más de ~60 espacios o tabuladores dentro de `[[ ... ]]` sale sin restaurar (como marcador): es el tope de seguridad de lo retenido. Más de 4 MiB de argumentos de herramientas cortan el stream con `stream_limit_exceeded`; el texto ya restaurado de otras choices se envía antes del error.
- Una llamada a herramienta sin `index` en OpenAI pasa sin tocar (sus argumentos no se pueden unir) y se cuenta como desconocida. En Anthropic, `input_json_delta` solo se restaura en bloques `tool_use`; en otros (herramientas del servidor…) pasa sin tocar y se cuenta.
- Argumentos o `input` que no son JSON válido (cortados, texto suelto): cada valor se inserta escapado como dentro de una cadena JSON (comillas y barras con `\`). Así lo que era JSON sigue siéndolo y un marcador dentro de una cadena no la rompe; en texto suelto el valor sale con esos escapes.
- Si un proveedor manda una clave partida en varios eventos, el stream se corta al completarse, pero el trozo ya enviado llega al cliente (no es la clave entera).
- Un proveedor compatible con OpenAI que omite `choices[].index` (o lo manda como `0.0`, `"0"` o negativo) **corta el stream** con el error fijo de stream mal formado: falla cerrado, porque un SDK uniría ese trozo con otro que la pasarela no puede seguir. Lo mismo en Anthropic con un `index` así o un `content_block_*` sin él.
- Un stream con más de 4.096 rutas de texto distintas (o nombres de campo distintos), por ejemplo con `n` alto y `top_logprobs`, se corta con `stream_limit_exceeded`: la vigilancia de claves partidas no olvida nada para no dejar pasar una.
- El tamaño total de un stream no tiene tope (sí cada línea, cada evento, lo retenido y lo acumulado).
- En Anthropic se bloquean las `citations`, los documentos y las herramientas del servidor (búsqueda web…): fallar cerrado es a propósito.
- Las claves de los objetos JSON no se enmascaran: si contienen un dato, se bloquea la petición.
- El detector no decodifica base64, hexadecimal ni otras codificaciones dentro del texto (solo bloquea las URL `data:...;base64,`).
- Los errores del proveedor se devuelven con los marcadores `[[TIPO_N]]` sin restaurar.
- El tamaño de la respuesta del proveedor no tiene tope en v0.1.
- `Bearer` en la cabecera `Authorization` distingue mayúsculas: `bearer` se rechaza.
- Un objeto con dos claves que solo cambian en mayúsculas se rechaza con 400 si es una clave que Antifaz lee (`content` y `Content`); las demás (`id` e `ID` en un esquema) pasan (ADR-0015).
- Los errores del proveedor en JSON se devuelven tal cual, salvo los 401/403, que nunca pasan su cuerpo (`upstream_auth_failed`, issue 76). En sus respuestas se detectan la clave completa y sus trozos reconocibles (10 caracteres seguidos de la parte secreta, o `****...abcd`), tal cual o con escapes JSON (`\u0061`). Si un error que no es 401/403 la devuelve en base64, en UTF-16 o de otra forma codificada, llega al cliente (test `xfail` estricto en `tests/redteam/test_models_and_scan.py`). Tampoco se reconocen: trozos de menos de 10 caracteres (por ejemplo la clave citada en tramos de 9), los 4 últimos sin la forma enmascarada ("acaba en abcd"), ni un trozo transformado: con mayúsculas y minúsculas cambiadas, con espacios o caracteres invisibles (de ancho cero) en medio, codificado con `%` (URL) o con entidades HTML (`&#97;`), o escrito al revés.
- La pasarela no se puede usar desde una web pública: no hay CORS.
- En `tools`, `functions`, `response_format` y `tool_choice` (esquemas del desarrollador) no se aplica la lista de tipos permitidos; sus textos sí se enmascaran.
- Los nombres de persona solo se detectan con el NER, que está apagado por defecto: sin él pasan en claro. Con él, cerca del 30 % de las detecciones de nombres tapan texto que no es personal (no cumple el suelo del 85 %; ver "NER con el modelo real").
- NER: una petición tan grande que no cabe en el tiempo máximo, o con más de 1.024 ventanas, se bloquea (el fallo seguro). Un nombre detectado se enmascara en toda la petición, también donde es una palabra corriente ("Mar") o, si tiene 6 o más letras, dentro de otra palabra ("Marina" en "submarina"): falsos positivos aceptados (ADR-0016).
- NER: cada cadena del JSON se lee por separado. Un nombre partido entre dos campos ("Carmen" en uno y "Prueba López" en otro) no lo ve entero ningún trozo, y cada parte puede salir en claro si el modelo no la reconoce sola (test `xfail` estricto en `tests/redteam/test_ner.py`).
- NER: solo se propaga el valor entero que encontró el modelo. Si ve "Carmen Prueba López" en un mensaje y en otro solo aparece "Carmen", ese "Carmen" suelto no se tapa por propagación; solo si el modelo lo detecta allí (test `xfail` estricto). Buscar las partes de un nombre enmascararía palabras corrientes por toda la petición.
- NER: el modelo no lee las URL largas, los bloques base64/hex de 32+ caracteres sin espacios ni las series de 6+ cifras pegadas a letras (vista para el NER): un nombre dentro de una URL (`/usuarios/jordi-inventat`) o de un bloque así no se detecta. Los validadores y patrones sí leen esos trozos (emails, IBAN, DNI…).
- NER: un texto que cuesta muchas más subpalabras que palabras (más de 4 trozos de 384 tokens por ventana de media: CJK o emoji al azar) se bloquea con 400 sin ejecutar el modelo.
- NER: "Apellidos, Nombre" sin contexto ("Inventat Puig, Jordi") no se detecta como nombre (test `xfail` estricto en `tests/integration/test_ner_model.py`).
- NER: entre la comprobación del manifiesto en el proceso del pool y `torch.load` queda un instante (TOCTOU): aprovecharlo exige poder escribir en la carpeta del modelo, que debe ser de solo lectura para el usuario de la pasarela.
- NER: al cargar el tokenizador, transformers avisa de un "incorrect regex pattern" y sugiere `fix_mistral_regex=True`. Es un aviso pensado para tokenizadores de Mistral: se comprobó que la tokenización de mDeBERTa coincide con la de sentencepiece. Los avisos no salen del proceso del pool (está silenciado).
- Dos identificadores pegados sin separador (`12345678Z12345678Z`): el primero no se detecta (un DNI nunca toca cifras) y la guardia bloquea la petición.
- uvicorn no tiene plazo para leer las **cabeceras** de una petición: un cliente que las manda muy despacio (slowloris) ocupa una conexión de toda la pasarela, no solo del panel. El login del panel sí tiene plazo para el cuerpo (5 s). El tamaño de las cabeceras es otro asunto (issue #57). Detrás de un proxy inverso, el plazo lo pone el proxy.
